# 屏幕、帧与垂直同步

上一篇咱们跟着一次点击把界面更新走到了 DWM（桌面窗口管理器，Windows 里负责把各窗口画面拼成整屏再送出去的系统组件）的门口，结尾丢下一句话：经 DWM 合成上屏的内容没有撕裂，撕裂只出现在绕开合成、直写屏幕的路径上。这句话里躺着几个咱们一直没展开的词：撕裂、垂直同步，外加屏幕自己干活的脾气。本篇笔者就把屏幕摆上解剖台，把它们一个接一个地摊开。

这一篇的样子，咱们开篇交代清楚。本篇的正文里几乎没有代码，讲的全是机制，这些机制在 API 的底下当着承重墙。您把这一篇读顺，后面[交换链与呈现](27_dxgi_swapchain.md)那一篇里 Present（程序画完一帧后提交翻页的那个调用）的参数、缓冲块数、翻转模式这些名字，脑子里就都有了对照的画面。笔者给自己画的线是这样的：只讲机制本身，数字留给您需要时自己测。

## 电子枪一行一行地点亮屏幕

咱们从老得不能再老的设备讲起。CRT 的全称是阴极射线管，它的样子又厚又重，是上一辈的显示器。它的玻璃屏内侧涂着一层荧光粉，电子枪打出的电子束扫到哪里，哪里的荧光粉就被点亮，亮过之后还会自己慢慢地暗下去。

电子束的路线是固定的，它一行接一行地扫。咱们跟着它从左上角看起，扫完了第一行就挪下来扫第二行，就这样一行一行地铺满整屏。屏幕上正在被扫过的发光横线，它的行话名字叫扫描线。

您现在用的液晶屏里已经没有电子枪了，不过“画面按行铺上屏幕”的动作模型没有变。液晶面板上的像素同样是一行一行被写入状态的。您凑近一块老液晶屏能看到像素颗粒，再想想每一帧这些颗粒是按行分批刷新的，这个图像就具体了。

扫完了一整屏，画面就完整出现了一次。您留意“出现”说的其实是一个动作：画面没有被屏幕存住，荧光粉亮了会暗，液晶的状态也要一遍遍重写。想让画面持续地留在眼前，就得一遍接一遍地重扫。屏幕从来靠反复重画骗过您的眼睛，它不是一张摆着不动的照片。

骗术靠的其实是视觉暂留：亮过的东西在视网膜上会停留一小段时间。电影每秒 24 格配上快门的遮断就能显得连续，显示器的刷新率挑得比这高得多，而人凑在屏幕跟前的时候，更低频率的闪烁更容易被眼睛察觉。具体的数字因人和面板而异，笔者不在这里立数字线，您只要知道刷新率管的是“闪不闪、顺不顺”这样的两件事就够。

## 消隐期：扫描之间歇的那口气

扫描的节奏里有两段“不画”的时间，咱们分别认一下。

咱们跟着电子枪走一遍：扫完了一行，折返的路是从最右端回到最左端，折返的时间里束流被关掉、什么都不画。这一段的名字叫水平消隐。

扫完了最后一行，电子枪还得从右下角折回左上角、开始下一遍的整屏扫描，这段折返的时间叫垂直消隐（vertical blanking interval，平常咱们都缩写成 VBlank）。整屏扫描就这样一遍一遍地循环，咱们把每循环一遍算作一次完整的屏幕刷新。

屏幕每秒能完成多少遍整屏的扫描，咱们把这个数叫刷新率，它的单位是赫兹（Hz）。60 Hz 的屏幕每秒把整屏扫 60 遍，144 Hz 对应的就是 144 遍。这个节拍是显示器出厂就定好的，写进了显示器和显卡之间传输信号的时序里。程序改不动它、最多只能在支持的几档里挑一档。

咱们顺手做一道算术。60 Hz 的屏幕，一遍扫描的时长是 1000 除以 60、约 16.7 毫秒，其中消隐期只占很小的一截。您不用记这些数，比例您倒是该记一下：“不能被看见的动作”能用的窗口很窄。

消隐期是整个体系的安全窗口。扫描线不读像素的那段时间，正好留给大家做不能被看见的动作。这个对照值得您留在手边：屏幕的每一遍扫描都是一段长长的“正在读”，中间夹着的则是一小段“没在读”。

至于刷新率的数字为什么常见 60，它牵扯到电网频率和电视制式的历史，与本篇的主线无关，笔者不往下展开，您有兴趣的话可以自己去查这段掌故。

## 逐行与隔行：参数标签里的 i 和 p

您在视频网站或老电视的参数里见过 1080p、480i 这类写法。末尾那个字母说的就是扫描方式，咱们停下来认一认：“一帧”这个词的歧义，就是从这段历史里带出来的。

p 指的是逐行（progressive），一遍扫描从头到尾铺满所有的行，咱们前面讲的就是它。i 指的是隔行（interlace），一遍只扫奇数的行，下一遍再扫偶数的行，相邻的两遍拼起来才是一帧完整的画面。

隔行是带宽不够年代的省法。每遍扫描要传的数据量减半，靠荧光粉的余晖和人眼的惯性，两遍混着看就成了完整的一帧。代价您也猜得到：快速运动的内容里，奇偶行隔了整整一遍扫描的时间，画面会出现梳子一样的横向条纹，老电视里体育画面发毛的就是它。

如今的电脑显示器全是逐行扫描，隔行的老视频源在播放前要做反交错处理、把隔行还原成逐行。本篇往后讲的一切都默认逐行，您要做的只是见到 i 和 p 时认得它们的来历。

## “帧”的两种用法

“帧”这个字在渲染的话题里指的是两样东西，咱们把它们分开认清楚，后面的机制才不会搅在一起。

一样是屏幕的一遍完整扫描，刷新率数的是它。另一样是程序组装出的一张完整画面，帧率数的是它。两个长得像的帧脾气完全不同，您可别把它们混了：屏幕的帧按节拍必到，程序的帧却按工作量的多少交付。

您在别的资料里读到“帧”这个字的时候，不妨停下来问一句：它数的是哪一座钟。比如您听过的“60 帧流畅”，说的就是程序每秒交付 60 张画面帧，而且恰好跟一座 60 Hz 屏幕的扫描帧对上了节奏。十有八九的概念混乱，问完了这一句就解开了。

## 液晶屏把这套节拍继承了下来

咱们讲 CRT 可不是为了怀古。液晶显示器里已经没有电子枪了，不过显卡往屏幕送信号的时序标准，把消隐期这些概念原样保留了下来。面板的驱动框架也沿用按整帧节拍工作的方式。您在 Windows 显示设置里看到的刷新率，调的就是这套节拍的快慢。

所以本篇往后说“扫描线”“消隐期”，说的都是这套沿用下来的时序框架，它描述的是信号和面板层面的真实行为。您要是较真液晶面板内部驱动的门道，那就是一层更深的硬件细节，对写应用的咱们来说不改变模型，笔者就不往下走了。

## 刷新率与帧率是两座各走各的钟

到这里咱们手里有了一座钟：屏幕按刷新率一格一格地走。另一座钟在程序的这边，程序每秒组装出多少张完整的画面，这个数咱们叫它帧率（frame rate，游戏圈里常写的 fps 就是它）。

您把两座钟放到一起就会发现，它们谁也不认识谁：屏幕不管您画没画完、到点就扫。而程序也不管屏幕扫没扫完，画完了就想上屏。谁也不迁就谁的僵局，正是后面一切症状的根源。

窗口程序的钟走得更随性一些。它的绘制由消息驱动，用户不碰它的时候一帧都不出，gui 主线第六篇造的那套属性变了自动冒泡重画，走的就是“有事才有画”的节奏，您可以在[属性与重画](../gui/06_property_repaint.md)里回看。游戏的循环则是每圈必画一帧，帧率跟着循环的速度走。两种程序钟的脾气不同，碰上的是同一座屏幕钟，咱们接着看会碰出什么。

## 错拍的三种图景

咱们把程序交付画面帧的速度和屏幕扫描帧的速度放到一起，相对的位置只可能有三种：快了、慢了、恰好跟上。三种咱们各摆一个现场。

程序比屏幕快的现场：不加节流的动画循环每秒能画几百帧，而屏幕每秒只扫几十遍。多出来的画面帧要么被合并丢弃，等于白画了，要么在直写屏幕的年代里落进扫描的中途，这就是撕裂的入口，咱们下一节进现场。

程序比屏幕慢的现场，咱们也摆一个：一帧画面的活，要用两个甚至更多的刷新周期才干得完。屏幕等米下锅的时候，只好把旧的画面再扫一遍，用户看到的内容停顿，动作一顿一顿的。视频播放的卡、界面的掉帧，都是同一现场的不同扮相。

恰好跟上的现场是咱们想要的理想态：程序能稳定地在一个刷新周期内交付一张画面帧、又赶得上消隐期，屏幕的每遍扫描都有新内容可取。

| 画面帧对扫描帧 | 屏幕那边看到什么 | 您听过的说法 |
|:---|:---|:---|
| 程序更快 | 多余的被合并丢弃，直写屏幕时可能落进扫描中途 | 白画、撕裂 |
| 程序更慢 | 旧画面被重扫一遍 | 掉帧、卡顿 |
| 恰好跟上 | 每遍扫描都有新内容 | 流畅 |

三种图景请您立在脑子里。后面的机制看着多，咱们把错拍修成恰好，就是唯一的目标。

顺着上面的表，咱们把两个常被混着说的词也分开认一认。撕裂是一遍扫描里混进了两代的内容，毛病说的就是那道“缝”。掉帧是屏幕到点取不到新的内容，只好把旧的帧再扫一遍，毛病说的就是“停顿”。前者的画面横向对不上，后者的内容纵向没更新，治法也各归各：撕裂靠的是挑时机，掉帧靠的是赶产量。

## 撕裂是怎么来的

咱们要看撕裂，就得回到没有合成器的年代。DOS 时代的游戏直接往显卡的显示内存写像素，而那块内存同时正被扫描线一行一行地读出去点亮屏幕。读的和写的还是同一块内存，事故的条件就这么凑齐了。

咱们把事故现场摆出来。屏幕扫到第 300 行的时候，前面 300 行读的还是旧画面。此刻程序恰好画完了一帧，把整块缓冲区换成了新画面，于是第 301 行往后读到的就是新画面。同一遍扫描里的上半屏属于上一帧，而下半屏已经属于下一帧，接缝处的内容横着错开，您看到的就是一道裂缝。这个现象咱们叫它撕裂（tearing），它的名字就来自那道缝。

撕裂的另一个特征也值得您留意：帧率和刷新率的错拍只要有一点点，接缝出现的高度就一遍一遍地挪，老游戏里那道上下滑动的横向错位就是它。错拍大的时候，缝就贴着屏幕的边缘或者干脆看不见。错拍小的时候，缝就停在屏幕的中间晃，那是最扎眼的情况。

您要是想自己复现也不难，咱们在文末“您可以自己看的两处”一节里给了复现的办法，窗口模式下您不容易看到它的原因，咱们留到后面讲 DWM 的小节里再说。

撕裂出现的条件只有一条：屏幕正在读的那块内存被中途换了内容。而反过来，只要整遍扫描期间读的那块内存没动过，撕裂也就无处发生了。咱们后面讲的每一个机制，守的都是这个条件。

## 双缓冲与翻页

最老的解法您其实已经用过一次。咱们回到 gui 主线第一篇[裸窗口 demo](../gui/01_naked_win32.md)：它并没有把图直接画在窗口的 DC 上（DC 指设备上下文，代表的是一块能往上画图的表面），而是在离屏位图（内存里一块谁也看不见的画布）上把整帧组好了，再用 BitBlt 一次性地贴过去。

当时的动机是消灭“背景刷完、字还没画上”的中间态，配套的动作是在 WM_ERASEBKGND 里返回 1，把系统擦背景的活拒掉。这套做法的名字叫双缓冲（double buffering），更多的细节写在[裸窗口 demo 那一篇](../gui/01_naked_win32.md)和书架（《Programming GUI with Native Windows》译文系列）的[GDI 双缓冲一章](../native_win32/23_ProgrammingGUI_NativeWindows_GDI_DoubleBuffer.md)里，咱们这里只借它立概念。

GPU 时代的双缓冲是同一思路的放大。显卡侧给程序的两块缓冲，其中的一块是 front buffer（前缓冲），剩下的那块是 back buffer（后缓冲）。前缓冲连着扫描的输出，屏幕读的就是它。咱们画图，画的全部落在后缓冲上，后缓冲的内容谁也看不见。

画完了一帧之后，这对缓冲的交接怎么做？咱们把两种方案摆在一起看。

方案一是把后缓冲整块地复制进前缓冲。复制的动作要花时间和带宽，复制的中途扫描线照样在读、撕裂照样插得进来，咱们等于绕了一圈又回到原地，只是出事的窗口小了些。

方案二干脆就不复制了，咱们改成换指向。两块缓冲的位置原地不动，输出的一侧把“读哪块”的设置换一下，原本读 A 的设置改成读 B。这个动作的名字叫翻页（page flip），换指向花的工夫少到几乎可以忽略。

翻页的干净出在哪里，您想一下就有画面：没有复制的过程就没有半新半旧。翻页发生的一瞬，屏幕要么还在扫旧的缓冲，它本身是完整的一帧，要么已经切到了新的缓冲，那一帧也是完整的。两块缓冲各自都是完整的，缝就这样没了。

几块缓冲加上翻页的规则凑成的整套设施，“交换链”这个名字说的就是它：缓冲连起来的样子像一条链，轮流地当 front 和 back，翻一页、缓冲的角色就轮换一格。这套设施是交换链那一篇的主角，您把它的样子留在脑子里，到时候的那一堆 API 名字就都有处可挂了。

翻页和离屏位图的那套双缓冲，思想上是一家人、做法上分了岔，咱们对照着看一遍：

| | 裸 demo 的离屏位图 | 显卡的翻页 |
|:---|:---|:---|
| 交接方式 | BitBlt 整块复制 | 换指针，不搬像素 |
| 交接期间能否被看见 | 能，复制途中扫描线可能正在读 | 指针一换即生效，没有中间态 |
| 主要动机 | 不让用户看见画到一半的中间态 | 不撕裂，也不让中间态上屏 |

不过咱们要是翻页的时机不对，撕裂的路还是没有被堵死。扫描进行到一半的时候翻页，后半遍扫描读到的已经是另一块缓冲，前半遍读的还是旧的，横向的错位就又回来了。翻页堵住了写一半被看见的问题，还没堵住换到一半被看见的问题。剩下的最后一道缝，咱们得挑准时候去堵。

## 垂直同步：等消隐期再翻页

咱们要问的问题变成了：什么时候翻页才是绝对安全的？答案是垂直消隐期。这个时候的屏幕上没有任何一行在读像素，咱们在这个窗口里换指向，下一遍扫描从头到尾读的都是同一块缓冲。把翻页的动作对准消隐期去执行，这个做法的名字叫垂直同步（vertical sync，咱们常缩写成 vsync，名字里的“垂直”指的就是垂直消隐）。

垂直同步一旦开了，帧率就被刷新率套住了。60 Hz 的屏幕每秒只给出 60 个消隐期，每秒的翻页最多 60 次，帧率的顶就是 60。这既治好了撕裂，也埋下了新的代价，咱们把代价分开看。

## 掉帧的台阶与排队的帧

咱们说的头一个代价是掉帧掉得像下台阶。您的一帧绘制用时比一个刷新周期略长一点点，某个消隐期到站的时候后缓冲还没画完，翻页就只好等到下一站了。结果是帧率从 60 一脚踩到 30，中间没有可站的 45。开了垂直同步的游戏里，您看到的帧率在整倍数之间跳，背后的机制就是它。

咱们把消隐期想成定点班车正合适：它们是离散的时间点，一班一班地发，错过了一班，就得整个周期地等下一班。

咱们再看第二个代价，也就是更隐蔽的排队问题。程序为了赶上定点的消隐期、得提前把后缓冲画好候着。候着的这段时间里，屏幕上挂的还是旧帧，程序却已经开始画更新的帧了。看视频的窗口无所谓，游戏就是另一回事了：玩家此刻敲下的按键，要等排在前面画好的帧全部翻完了，才轮得到被画进新的画面。

从敲键到看见反应之间的这段拖慢，它的行话名字是输入延迟（input latency）。笔者不给具体的毫秒数，它随刷新率、排队深度、游戏自身的工作量变动，各家的测量口径也不同，咱们只把机制摆正：排在前面的帧越多，屏幕一幅一幅放过去的时间就越长，您这一敲才轮得到上屏。您可能听过玩家抱怨“开了垂直同步手感变肉”，肉的就是这一段。

反过来您也就懂了，为什么有的玩家宁可关掉垂直同步。关掉之后的翻页不等消隐期，画完了就立刻翻，队也排浅了、手上的动作兑现得快，代价是撕裂回来了。快和完整的两样好处，直写屏幕的年代里您只能挑一样，这道两难催生了后面的种种折中，咱们马上就能看到。

咱们把一次按键到发光的全程串一遍，您看看延迟都藏在哪几站。手指的按下、设备的采样，属于输入侧的固定开销。游戏在下一轮的循环里读到它，算出世界的新状态。这一帧渲染完了，排进等翻页的队里。

翻页的时刻轮到它了，翻进的是消隐期。屏幕把这一帧扫出来的时刻，光才进到您的眼睛里。每一站都吃掉了一点时间，垂直同步管的是中间“排队等班车”的那一段，但是它管不了两头。能压的是哪一段、压不动的又是哪一段，那是竞技游戏引擎调优的长年话题，咱们知道结构就够用了。

咱们把“画一帧、排一次队”落到代码上的样子，长的是下面这个骨架。它只是示意、仓库里并没有这样的代码：

```cpp
// 一轮带垂直同步的游戏循环，骨架示意
while (running) {
    process_input();   // 玩家这一站敲下的键，在这里被采样
    update_world();    // 按输入推进世界状态
    render_frame();    // 画进后缓冲
    Present(1, 0);     // 第一个参数是 SyncInterval，1 表示等下一个消隐期再翻
}
```

您把循环和上面那串站点对上：采样的位置在循环头，排队的位置在 Present，扫描的位置在循环外。窗口程序的“循环”是消息驱动的，没有这样的 while，但画面帧要走的站一座都不少，咱们在讲帧节奏的小节里回到这里。

## 三重缓冲：多一块画布，手不停工

治排队的办法还有一个：咱们把缓冲再加一块、凑成总共三块，这套做法的名字叫三重缓冲（triple buffering）。其中的一块正挂在屏幕上，另一块画好了排队等翻页，程序立刻切到了第三块接着画，画图的手也不停工。帧率稳住了，台阶也没有那么陡了。

它的代价同样说得直白。排队候翻的帧可能更多，最新画好的那帧在队列里排得更深，输入延迟也跟着变长了。缓冲越多的画面越顺，玩家看到的世界就越滞后。这个取舍没有标准的答案：求跟手的竞技配置宁可要手感的快，求平滑的演出配置宁可要画面的顺，怎么选要看您的产品要什么。咱们把两头的好处和代价都摆出来，选哪头的决定权在您手里。

## 显示器也学会了等人：可变刷新率

这两年还多出了第三条路，咱们顺带认一下。咱们常听到的 G-Sync 和 FreeSync 这类技术，它们的统称是可变刷新率（VRR），思路是把班车改成随叫随到的模式：显示器不再按固定的节拍发起刷新，而是等显卡说“这帧画好了”，之后自己再发起一次新的刷新。

班车不再定点地发，错过班车的概念就消失了，台阶式的掉帧被摊平，排队也能排得很浅了。代价是它要求显示器、显卡、连接线的支持，这就超出了本篇的范围，笔者只把它的位置标出来：它动的是屏幕那座钟的脾气，与前两招动程序这一侧的做法正好互补。

不过咱们也别把它神化：可变刷新率救的是错拍，救不了的是画面帧本身交得太慢。一张画面帧的活超出了一个刷新周期，屏幕等得再久、等来的也还是慢的那一帧。

## DWM 接管以后，窗口程序够不着屏幕

咱们讲到这里，本篇说的这些机制，它们的主语一直是同一个：“直接驱动屏幕的那个程序”。DOS 游戏、独占全屏的 Direct3D 游戏就处在这个位置上。窗口程序站的位置又在哪里？

到了 Windows Vista，窗口程序的手就够不着屏幕了。上一篇里咱们已经走过一遍：咱们画图的终点是重定向表面，把所有窗口的表面拼成整屏一帧、真正面对屏幕的是 DWM。整条链的细节写在[从状态到像素](01_status_to_pixels.md)的第六站（DWM 合成上屏那一段）和[控件如何上屏](../gui/08_widget_on_screen.md)里，咱们不重走，单看它对撕裂的意味。

咱们来看扫描线此刻读的是什么：DWM 合成出来的那一帧，能中途改动这块内存的只有 DWM 自己，而 DWM 按屏幕的刷新节奏整帧整帧地送。窗口程序改的只是自己的表面，改到一半的时候、扫描线也读不着，因为中间隔着合成的这一环。

“经 DWM 合成上屏的内容没有撕裂”，上一篇的这句话咱们现在能把机制指出来了：可能被撕的那块内存，窗口程序的手是根本碰不到的。

Vista 之前是没有这一层的。窗口的画面直接落屏，快速重画的窗口一样撕得难看，那个年代的老书里教的防撕裂手艺，如今在窗口模式下已经用不上了。您读旧资料的时候记得看一眼年代。

窗口模式的 DirectX 程序，咱们看它也是同样的情况。DXGI 是 Direct3D 里管缓冲和呈现的那层接口，它的翻转模型下，程序翻页翻的是自己与 DWM 之间的那一环，屏幕的那一环始终归 DWM 掌管。程序想真正回到直接面对屏幕的老位置，独占全屏是一条现成的老路，垂直同步的开关也才重新落回程序的手里。Direct3D 里控制它的位置是 Present 调用的第一个参数 SyncInterval，这个咱们到交换链那一篇再展开。

独占全屏为什么曾经重要这件事，咱们现在能说全了。它把程序的交换链直接连到屏幕的输出，翻页省掉了 DWM 那一层合成，排队的队列也浅。代价是程序进出全屏的时候要重新协商显示模式，alt-tab 卡一下的老记忆就来自这里。

到了 Windows 10，系统默认对独占全屏做优化的处理，很多情况下画面实际改走了翻转加合成的路，真正老式的独占要程序显式要求才会有。这个行为的描述在 DXGI 的文档里找得到，判定的具体办法，咱们留给交换链那一篇。

独占全屏还有一位现代的亲戚，咱们把它也一并认了。您把窗口开成无边框、铺满整屏，再配合上 DXGI 的翻转模型，驱动在某些条件下会让程序的翻页直通屏幕。DWM 在中间让出了道，这套优化在文档里的名字是 independent flip。触发的具体条件由驱动决定，笔者没有逐机验证过它。

## 帧节奏：撕裂治好了，顺滑还得自己挣

撕裂被合成器治好了，顺滑却没有人白送给您。DWM 在每个刷新周期取一次您表面的最新内容：您更新得比它勤，多出来的更新就被合并掉了，等于白画了。您更新得忽快忽慢，画面的更新就一顿一顿的。用户看到的不会是缝，但看到的会是磕绊，这样的不匀称有个说法，说的是帧节奏（frame pacing）没守住。

咱们的窗口程序尤其容易栽在这里，因为 WM_PAINT 是事件驱动的：有事的时候才画、没事的时候不画，画的时机跟着输入消息走，跟屏幕的节拍没有任何的约定。动画想要匀速地动，咱们就不能指望“消息来了就画”，得自己按节拍器安排重画的时机。节拍器怎么搭、系统的帧回调怎么接，是[动画与帧调度](34_animation_frames.md)那一篇的主场，咱们在这里把问题立起来。

DWM 内部的合成怎么调度、什么时候取各窗口的表面、怎么跟刷新对上，文档里也找不到写死的说法，笔者也没有验证过它的内部时序。对咱们写应用的人来说，“窗口画面进表面、DWM 每个刷新周期合成一次”这个模型已经够用了，剩下的疑问留给[DWM：重定向表面与窗口合成](30_dwm_composition.md)那一篇接着追。

## 这些机制落到 GUI 开发者手里是什么

本线是咱们写给 GUI 开发者的，这些机制并不是游戏圈的私产。您在窗口里做动画、挑重画时机的时候，就已经在跟屏幕的那座钟打交道了。咱们挨个看下来。

头一处的用场是动画。您在窗口里做一个进度动画，用 SetTimer 定时地重画，定时器自身的精度和消息排队的延迟，会让重画的时机忽密忽疏，帧的节奏就坏了。知道了屏幕按固定节拍取内容之后，您就知道动画该瞄准的是节拍本身，而不是“尽快”。

第二处的用场是合成开销。您画的每一帧都要经 DWM 拼一遍，窗口叠窗口、半透明、模糊都是合成那一段的活。您把界面做得层层叠叠，付的就是合成那一段的开销，GPU 忙起来的时候，第一个受损的是动画的流畅。

第三处的用场是读别人的代码。Skia、Direct2D、浏览器引擎的渲染代码里，present、flush、帧回调这样的词到处都是，它们的语义全踩在本篇讲的机制上。您把机制立住了，这些代码读起来就不是天书了，本线后面讲到 Direct2D 和 Skia 的时候，它们还会反复地回来。

## 您可以自己看的两处

有两处观察是您现在就能做的，做完了之后，本篇的机制就落在您自己的眼睛里了。

您打开显示设置，把刷新率从 60 Hz 的那一档挑到 120 Hz，前提是您的显示器支持，然后您再晃一下鼠标。指针每秒被叠加呈现的次数多了一倍，轨迹也密了一倍。它走的是硬件光标的那一层，叠加的活由显示引擎随着每次刷新做、不经程序的手。屏幕的那座钟就这样在您手上拨快了，而指针之外的一切都没换，这就是刷新率作为独立节拍的直观版。

您再找一款允许设置垂直同步的游戏，开着的状态下跑一段、关掉之后再跑一段，把帧率的数字和画面对比着看。关掉了垂直同步之后快速转镜头，留意那道会漂的横向错位。您看到的东西，就是本篇前半的所有机制在同台表演，表演的阵容是直写屏幕的路径、错拍的两座钟、消隐期之外的翻页。窗口模式下您要是看不到，现在也能把原因说出来了。

您要是想看数据、不只想看画面，开源工具 PresentMon 能把每个程序的呈现事件记下来，提交的时刻和上屏的时刻都有时间戳。它是后面[《性能观测：PIX、RenderDoc、ETW》](36_performance_tools.md)一篇的主角之一，交换链那一篇的实验里咱们也会拿它说话。

## 交换链那一篇

咱们本篇讲的翻页、缓冲块数、翻页时机，落到 DirectX 里全都有具体的名字。CreateSwapChainForHwnd 建的那组对象叫交换链（swap chain，替您管着那几块缓冲和翻页时机的整套设施），翻页的方式由 DXGI_SWAP_EFFECT 的几个枚举值来挑：

```
DXGI_SWAP_EFFECT_DISCARD        丢弃式，Direct3D 9 时代的默认，D3D10/11 沿用
DXGI_SWAP_EFFECT_SEQUENTIAL     顺序式，保留旧帧内容
DXGI_SWAP_EFFECT_FLIP_SEQUENTIAL  翻转式，走 DWM 合成
DXGI_SWAP_EFFECT_FLIP_DISCARD   翻转加丢弃，如今的推荐值
```

枚举里两个以 FLIP 打头的就是翻转模型，走的正是本篇讲的翻页，画面也得经 DWM 的合成。前两个是老的路子，靠复制的方式交接，微软的文档把 FLIP 系列列为新代码的推荐选择，推荐的理由以及和老的差别，咱们留给那一篇展开。

Present 的 SyncInterval 管的是翻页要不要等消隐期，排队的深度还能靠等待对象来收紧、从而压低输入的延迟，等待对象用的就是 `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` 这个旗标。这些名字全是本篇机制在 API 面上的投影，咱们在[《交换链与呈现（DXGI）》](27_dxgi_swapchain.md)里逐个对照着讲。
