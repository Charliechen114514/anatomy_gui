# DWM：重定向表面与窗口合成

按[篇目索引](index.md)的登记，本篇开的是第七段“合成与系统”的头一篇。前面的六段里，咱们把 paint 那一段的家什换了一轮又一轮，GDI、Direct2D、Skia、文本、Direct3D 都过了一遍，可[第一篇](01_status_to_pixels.md)把旅程分了站，讲到合成的那第六站，咱们只立了个模型就匆匆赶了路：窗口的画面进了表面，整屏的合成交给了 DWM。模型里的每个词，咱们当时都没来得及细看：DWM 是谁、表面长在哪儿、合成到底是怎么运作的，这些咱们都要在本篇里逐个接住、摊开来看。

本篇的事实底本是前面几篇攒下的观察，加上微软的公开文档与通行的资料。要提醒您的是，DWM 的内部实现细节微软从来没有完整公布过，咱们能拿到的是文档写明的部分和可以亲手观察的部分，两样之外的内容，笔者会在正文里明确标出存疑，您读的时候也请把它们与事实分开称重。

读者设定跟前几篇一致：您会 C++ 和 Win32 的基础用法就够了，本篇不要求您读过 Direct3D 的那几篇，涉及的地方咱们会给一句带过的解释。您要是刚从[交换链与呈现](27_dxgi_swapchain.md)那篇读过来，方向就反过来了。本篇讲的，正是您 Present 出去之后、像素亮起来之前的那一段路。

术语的用法咱们也约好，免得咱们后文含糊。表面的全名是重定向表面，它是系统文档里的本名，咱们直接用。照片是咱们借来的比喻，指的就是它。这个叫法咱们用着顺口，后文咱们当通称用，等提到 API 与内存的时候，咱们再换回表面这个本名。比喻还有一桩好处咱们顺便领了：照片一叠一叠地拼成整屏，这个画面是好记的，往后本线讲到图层和合成树的时候，咱们都还能借它落脚。

## 任务管理器里就能见到它

咱们从最不神秘的地方开始。您打开任务管理器，进程列表里有一行叫作桌面窗口管理器的进程，它的可执行文件就叫 dwm.exe。DWM 就是它的缩写，它的全称是桌面窗口管理器（Desktop Window Manager），从 Windows Vista 起它就在系统里了，每个登录会话各有一个自己的实例。您要是展开它的 GPU 占用看一看，就会发现它平时就占着一份 GPU 的时间，咱们拖动窗口、播放视频的时候，它的占用还会往上跳。

您多半没见过它崩溃的样子，咱们顺路说一句为什么。dwm.exe 要是真的出了事，您会看到整个桌面黑了一下再恢复，咱们还会看到所有窗口跟着重新显示一遍，因为合成器倒了，桌面的画面就没了出处。系统里最不敢出错的部件里，它和显卡驱动是排在一处的，微软对它的保护也足够牢靠，普通开发者一辈子也碰不上它的崩溃，您见不到它崩溃反而算是正常的。

它是干什么的？一句话说，它是整个桌面的合成器。屏幕上所有窗口的画面，最后都由它拼成整屏的一帧、再送给显卡输出，窗口自己是谁也够不着屏幕的。咱们在前面的篇目里反复借过它的名号，本篇咱们就把它请到台前，仔细看看它的活法。

DWM 是跑在 GPU 上的，这件事值得咱们单独停一下。GDI 年代的绘制挤在 CPU 上，一笔一笔地写像素，而 DWM 的活是拿几十个窗口的表面拼一整屏，“把几张图按位置叠起来”的计算恰好是 GPU 最擅长的，于是合成这件事从 Vista 起整个搬到了 GPU 上。您在第一篇见过的边界，画图归了进程、合成归了系统，落到硬件上就是两拨活分给了两块芯片。

还有一位常驻的伙伴：窗口管理里的另一半活，窗口的排布、焦点、菜单的运作，归的是系统里另一套组件的管辖，DWM 只管画面怎么拼。标题栏是最容易让人误会的地方：它的管辖归窗口管理，它的绘制到了本篇后面您会看到，其实也是 DWM 拼的，咱们别把两件事搅在一起。咱们本篇不越界去讲另一半，您只要知道“桌面窗口管理器”这个名字容易让人以为它什么都管，其实它专职的是合成。

## 重定向表面，第一篇留下的那张照片

第一篇讲到合成时咱们提过重定向表面（redirected surface），当时给的说法是“系统替每个窗口存下的一张成品照片”。现在咱们把这句话摊开细看。

Vista 之后的系统里，每个顶层窗口都配了一块离屏的表面，它其实就是一块内存里的位图，而它的掌管权在 DWM 手里。您在 `WM_PAINT` 里拿 `BeginPaint` 交出来的窗口 DC，落笔的地方其实是它，屏幕其实并没有被碰到。[主线第一篇](../gui/01_naked_win32.md)里那个纯 GDI 的 demo，`BitBlt` 把整帧贴进 `window_dc`（demo 里的窗口 DC 变量）的那一刻，像素停在的是照片上，屏幕上什么都没发生。上屏的事由 DWM 另行安排，咱们管不着，咱们也看不见。

这套安排有个历史的来路，咱们把年代也对齐一下。XP 的年代里，窗口 DC 连着的就是屏幕上的那块内存，所以盖住再露出就得重画。Vista 引入了 DWM 之后，GDI 的输出被系统重定向到了离屏表面，老程序的绘图代码一行不改，落笔的终点却换了个地方。

这也是为什么那个 demo 自动就享受了不闪不撕的待遇，您把它放到 Vista 之后的机器上跑，它什么都没做，地基换了。

照片这个比方好在哪儿？好在它把窗口的状态和窗口的呈现分开了。窗口挪了位置，照片是不用重拍的，挪动的只是相框在桌面上的摆位。窗口被别的窗口盖住了，照片其实也还在，盖住它的窗口毁不掉它。窗口半透明地叠着的时候，各自的照片也各画各的，混色的事留给了合成那一步。第一篇里咱们做过一个几十秒的观察：拿别的窗口把咱们的窗口整个盖住再拖开，画面直接就回来了，中间没有一次重画的闪烁。现在咱们能把机制指名道姓地讲出来了：照片一直存在系统的手里，露出来的时候 DWM 把它重新拼上屏，不必劳驾咱们再画一遍。

边框和阴影也归在照片的管辖之外，咱们把它的来路也说清。窗口四周的边框、 Vista 时代起的圆角和投影，您在自己的绘图代码里一笔都没画过，它们是 DWM 在合成时加上去的装饰。[主线](../gui/08_widget_on_screen.md)里咱们说过“窗口外面的那圈圆角和阴影，我一行代码都没碰”，现在咱们知道碰它们的手是谁的了：合成器在整帧拼合的时候，把系统的装饰和您的客户区拼在了一起。

主线的[控件如何上屏](../gui/08_widget_on_screen.md)里画过一条链，从改值一路走到了上屏。本篇等于把链条的最后一节摊开了看，您要是想把整条链在脑子里过一遍，那篇是现成的地图，咱们在这里就不整条重走了。

换过画具的读者可能要问了：Direct2D 和 DXGI 呢？它们的终点其实也一样。[第二篇](02_screen_frame_vsync.md)讲翻转模型的时候说过，DXGI 的翻页翻的是程序与 DWM 之间的那一环，屏幕的那一环始终归 DWM 掌管。Direct2D 经渲染目标画进窗口的交接，走的也是重定向表面。所以咱们这一路换画具，换的都是怎么把照片画好，而照片的交接对象，其实从来都只有 DWM。

当然也有例外，咱们把它的名字提前立在这儿。窗口的样式里有一个扩展样式位 `WS_EX_NOREDIRECTIONBITMAP`，挂上了它，系统就不再替窗口配重定向的表面。主线的[控件如何上屏](../gui/08_widget_on_screen.md)里咱们见过它的用途：拿掉了照片，程序改走了 DirectComposition，自己维护起一棵叫 visual 树的东西。它是本篇之后那一篇的入场口，咱们把名字认下就好，细节就留给下一篇了。

顺着例外咱们再往前翻一段更早的历史：其实在 DWM 之前，系统里就已经铺过一条专门的道，走的就是离屏合成。Windows 2000 引入了 `WS_EX_LAYERED` 这个扩展样式，挂上它的窗口走 SetLayeredWindowAttributes 或 UpdateLayeredWindow 的路子，程序把一张带 alpha 的位图交给系统，合成上屏的活由系统替它包了。

那个年代这是普通窗口获得逐像素透明的唯一办法，代价是窗口的绘制模型整个换了，您想透明就得整个窗口透明。等 DWM 来了之后，所有窗口都过上了离屏照片的日子，layered 窗口的特殊地位也就淡了，但样式位留了下来，老代码里您还会见到它。咱们读老资料时见到 layered window 被当成稀罕物讲解，要知道它稀罕的是那个没有合成器的年代。

表面的尺寸也交代一句。它按整窗的口径算还是按客户区的口径算，文档里其实没有写死，通行的观察是跟着客户区走。窗口缩放的时候，系统会替表面安排新的尺寸，旧的内容在新尺寸下作不作数，取决于您怎么处理 `WM_SIZE` 之后的内容重排，这些是绘制一侧的事。最小化的窗口，按通行的讲法连表面都未必维持。

## 合成一帧：收上来、算遮挡、叠起来、送出去

现在咱们跟着 DWM 走一遍它每帧的活。咱们已经知道，屏幕的每一次刷新，DWM 都得交出一整屏的画面，这个节奏咱们在[第二篇](02_screen_frame_vsync.md)里已经摸熟了。它的活可以拆成四步，咱们一步一步看。

头一步干的是收集。桌面上每个可见的顶层窗口都有自己的表面，DWM 把它们连边框、标题栏那些系统画的部分一起收上来。边框和圆角阴影您在程序里一行都没画过，它们其实也是 DWM 画的，这其实也是“成品照片”里的另一层意思：DWM 手里的素材，比您画的还多一层。

第二步算的是遮挡。窗口谁上谁下是由 z 序定的，这是 Win32 一直就有的概念，SetWindowPos 改的就有它。DWM 按着 z 序从底往上地排开各窗口，逐个算出每个窗口实际露着的部分：被上层窗口盖住的地方不需要采样，完全埋在下层的窗口干脆不进这一帧。这一步对 GPU 来说是裁剪与图元组织的活，而算出来的遮挡关系，后面还要反过来影响窗口的重画，咱们在下下节回到它。

第三步做的是叠合。咱们把每个窗口按它自己的位置摆进整屏的画布，半透明的地方做逐像素的 alpha 混合。混合用的公式就是图形学里最经典的 OVER 运算：结果等于上层的像素，加上下层像素乘以透明度的补。咱们拿一个具体的数过一遍：上层像素的 alpha 是 0.6，那么最终的颜色里，上层占了六成，下层占剩下的四成。窗口叠窗口的圆角、阴影、玻璃效果，全都是 OVER 公式的产出。Vista 当年拿它做出了 Aero 的毛玻璃，后来各代系统的视觉样式换了又换，底下的数学其实一直是这一套。

真实的世界里还有一个小名堂，咱们提前打个照面：DWM 手里的表面普遍用预乘的 alpha（premultiplied alpha，颜色值已经提前乘过了自己的透明度）。预乘之后的 OVER 少乘一次，GPU 的混合单元也更省事，您以后在 Direct2D 的像素格式里见到的 D2D1_ALPHA_MODE_PREMULTIPLIED，说的就是这件事。本篇就不往下展开数学了，您记着“合成的世界默认预乘”的印象，后面读格式文档的时候就不会觉得名字来得没头没尾。

第四步干的是送出。整屏的一帧拼好了，DWM 就对着屏幕的刷新节奏把它交出去，交的时机对的是垂直消隐期，也就是[第二篇](02_screen_frame_vsync.md)讲过的 vsync。屏幕读的内存自始至终只有 DWM 合成好的那一帧，而能中途改它的，咱们反复说过，其实只有 DWM 自己。

四步走完了，咱们再换到 GPU 的视角看一眼，这四步合起来正好是一次完整的绘制。收集到的表面是纹理，遮挡算出的是要不要画、画哪一块，叠合就是带混合状态的绘制调用，最后对 vsync 的送出就是呈现。您在 Direct3D 那几篇里认识的顶点、纹理、混合、呈现，DWM 每帧都在整桌面的规模上过这一套（当作最坏情况的全拼来理解，桌面没变的区域实际会省，细节见下文讲脏跟踪的那一段），所以它吃 GPU 的时间，吃的一点也不冤枉。

鼠标指针是另一位站在合成之外的角色。您晃动鼠标的时候，指针在屏幕上的滑动又快又稳，它走的是一条专线，叫硬件光标：显示引擎在每次刷新的时候把它叠加在 DWM 的帧上面，本机上全程不经合成器的手。远程桌面一类的场合会退回软件光标，那时它也是被画进帧里的。您在[第二篇](02_screen_frame_vsync.md)里其实见过这个观察：刷新率从 60 挑到 120，指针的轨迹跟着密了一倍，而桌面上别的一切都没变。指针是单独走一条道的，那个现象的来路就在这里。

第二篇从扫描线的一侧指过这个机制，咱们现在从 DWM 这侧把它补全：可能被撕的那块内存是 DWM 的整屏帧，窗口程序的手够不着它，而 DWM 又按刷新的节奏整帧整帧地换，扫描线读到的永远是完整的一代画面。您的程序画得再快、画得再乱也没用，撕不了屏幕，因为屏幕只听 DWM 的。Vista 之前窗口直写屏幕、快速重画就撕得难看的年代，也就留在了旧书里。

新旧两个世界咱们并成一张表，您往后翻旧资料的时候拿它对年代：

| | XP 的直写年代 | DWM 的合成年代 |
|:--|:--|:--|
| 窗口 DC 的终点 | 屏幕上的内存 | 离屏的重定向表面 |
| 被遮挡再露出 | 画面丢了，得重画 | 照片还在，直接拼回 |
| 拖动窗口的代价 | 受牵连的窗口全体重画 | GPU 按新摆位重拼整屏 |
| 撕裂 | 直写路径上真实存在 | 合成路径上无从发生 |
| 边框与阴影 | 系统画进窗口自己的地盘 | 合成时由 DWM 加上去 |

## 多显示器：一块屏幕一份帧

咱们一直说“整屏的一帧”，多显示器的读者可能要问了：两块屏幕刷新率不一样，一份帧怎么对两个节奏？答案是 DWM 按显示器各自合成，每块屏幕有自己的合成输出，各对各的刷新节奏。您把一个窗口从 60 Hz 的屏幕拖到 144 Hz 的屏幕，它参与的合成流就换了，而窗口自己对此依然是无需知道的。

跨屏的窗口怎么办？咱们按合成的模型推：它的照片只有一份，两路的合成都从同一份照片里取样，各屏拼各的帧。

窗口一半在一块屏幕、一半在另一块的时候，两边各显示它露出的部分，您天天看着觉得理所当然，背后的安排却是合成器在两头分头干活。

这些说法属于模型与通识的层面，DWM 在多显示器下的具体调度、跨屏窗口的照片是否真的只有一份，微软的文档同样没有写到细节，笔者照旧标注在这儿。不过对写应用的咱们来说，模型这部分是稳的：多显示器不是程序要操心的事，[坐标、DIP 与 DPI](03_dip_and_dpi.md)里真正折磨人的跨屏 DPI 问题，麻烦出在坐标与缩放的那头，合成这边是清白的。

独占全屏的游戏在多屏下的样子，咱们也能用模型推出来了。屏幕上有一个窗口进了独占全屏，按[第二篇](02_screen_frame_vsync.md)讲过的机制，那块屏幕的输出直接归了游戏的交换链，DWM 在那一屏上让了道。另一块屏幕是不受影响的，桌面还是原来的样子，合成也在照常地跑，聊天窗口和任务栏都还活得好好的。这也解释了老玩家的一点旧经验：独占全屏的年代，另一块屏在游戏进全屏的一瞬偶尔会闪一下，闪的那一下，正是 DWM 与游戏交接显示模式的时刻。

咱们把指针、遮挡、多屏摆在一处就能看出来：每一块屏幕的输出都从 DWM 手里出，这是它关不掉的原因。下一篇要讲的应用侧入口，也是打这个位置来的。

## 遮挡之下还画不画

[第五篇《失效、脏区与重绘》](05_invalidation_dirty_region.md)讲遮挡的时候，咱们把知道的和不知道的分开摆过一次，咱们在本篇接着把它往前推一步。当时的结果咱们照旧复述一遍：`WM_PAINT` 的生成条件是更新区域非空且队列空闲，条件本身其实并不关心窗口看得见看不见。而系统对完全被盖住、被最小化的窗口会不会干脆扣下重画，MSDN 的文档没有写死，笔者也没有逐一验证过。

DWM 的模型能帮咱们排除一半猜测，咱们从 DWM 那侧推一遍：它在第二步算遮挡的时候，天然就知道每个窗口被盖住的部分。合成本身不需要被盖的窗口重画，照片是现成的，盖住了就跳过。所以从合成的视角看，被遮的窗口没有任何“必须重画”的压力，这与第五篇的观察是接得上的：盖住再拖开，画面直接就回来了，中间其实没有重画。咱们真正还没把握的，只剩系统会不会扣下 `WM_PAINT` 这一点了。

那被完全盖住的窗口还会不会收到 `WM_PAINT`？通行的讲法是，完全被遮挡的窗口会被标记成遮挡的状态，系统可以据此省掉它的绘制，最小化的窗口更是连表面都未必维持。不过上面的讲法属于通识与合理的推测，微软没有在公开文档里把判定与扣留的机制写死，DWM 内部的遮挡跟踪也属于未公布的部分，笔者照旧不装作知道。

第五篇咱们写过一个小工具，把失效的区域涂成色块摆在窗口上。它在这儿正好还是验证的家什：您拿一个全黑的无边框窗口把目标窗口整个盖住，再给窗口报一块失效的登记，您看色块换不换，眼睛收回来的就是您机器上的答案。

还有一个小方向值得咱们补一句。遮挡的关系是会变的，您把盖在上面的窗口拖开，DWM 会露出底下的照片拼回屏幕，而整个过程对程序是无感的，一条消息也收不到的。在旧世界的年代里，“露出就得重画”的讲法是因为画面真的丢了，而新世界里照片其实没丢，变的只是照片的可见性。咱们读老书遇到遮挡、剪裁、重画挤在一处讲的段落，咱们记得把年代对上。

咱们把遮挡的话题从程序的视角收个尾：您的绘制义务，从旧世界的“屏幕上属于您的每一格”缩到了新世界的“自己的表面”，被谁盖着、盖住了多少，都不改变您欠下的活。可见性影响的是系统的优化空间，您的责任范围是不受它影响的。这就是为什么咱们写 `WM_PAINT` 的时候从来不用问“我现在看得见吗”，问了也没有用，您画的终点永远是自家的照片。

## 拖动窗口时，别的窗口为什么不用重画

咱们拿一个日常的动作把整台机器串起来：您按住标题栏拖动一个窗口，桌上的别的窗口一个字都没重画，甚至被拖的窗口自己也没重画。这件事在 XP 的年代可不是这样的，咱们回头去旧世界看一眼。

XP 的年代没有合成器，窗口的画面直接落屏。您拖动一个窗口，它扫过的每一寸屏幕都属于某个窗口，被扫过的地方起初是被盖住了，扫过之后又露了出来，于是底下所有受牵连的窗口都得重画，系统还得赶在重画之前把露出来的背景擦掉。

机器慢的时候您能看见拖影和一片片的白，拖一个大窗口能让 CPU 的占用窜上去。当年的系统里提供过“拖动时显示窗口内容”的开关，关掉了它，拖动的时候就只画一个空心框，为的就是省下重画的开销。

DWM 的时代整个换了算法。窗口的照片都存着，拖动改的只是相框在桌面上的摆位，也就是合成时的位置参数。GPU 拿着各家现成的照片按新的位置重新拼一帧，被拖的窗口不用重画，底下的窗口更不用，它们的内容一个像素都没变。您现在感受到的拖窗口很顺、桌面很安静，GPU 这头其实并不闲，整桌面的拼合活照跑，安静的是各家的 `WM_PAINT`，咱们挨家挨户地问一圈，被惊动的窗口一家都没有。

窗口的缩放也是同一个道理。您拖窗口的右下角改变尺寸，受影响的是这个窗口自己的内容，它的 `WM_SIZE` 会来、内容得重排，这些咱们在[主线第一篇](../gui/01_naked_win32.md)都走过。桌面上别的窗口的照片和摆位都没变，合成的时候按原样摆回去就行。也就是说拖动和缩放这两件最伤老的渲染模型的事，到了合成器这儿都变成了参数的更新，GPU 的搬运替下了 CPU 的重画。

系统自己做的窗口动画也吃同一碗饭。您最小化一个窗口的时候，它收缩动画的那一小段，出自合成器拿窗口照片做的缩放过渡，您的程序从头到尾没有画过一格。这也是为什么系统动画平时流畅、从来不用劳驾 `WM_PAINT`：动画动的是照片的呈现方式，而照片本身一帧都没换。等您以后做自定义窗口动画，正路是去动呈现层的那一侧，入口咱们下一篇就见。

这里还藏着咱们标题里那个问题的完整答案：程序报的失效只是自家表面的事。您 `InvalidateRect` 报得再大，脏的也只是自己的照片，DWM 关心的是这一帧桌面里哪些地方变了。DWM 自己维护着整桌面的脏跟踪，窗口没变的区域不必重新合成，变了的区域才进这一帧的工作。前面说过的“每帧重拼整屏”，咱们在这里也对齐一下：它是教学模型的上界说法，最坏的情况下当作每帧全拼，实际省下的工夫就省在这段脏跟踪上。这个机制的说法在公开资料里能找到方向性的描述，而具体的聚合算法、缓存的粒度、各代系统的差异，微软都没有写进公布的文档，笔者把它按通识标注在这里。方向对咱们已经够用了：失效是进程侧的登记，合成是桌面侧的生意，两份记录各记各的，中间的桥梁就是表面。

咱们把两份记录分开看，还能解释一个您可能遇过的现象。动画的程序明明每帧都报了失效、也画了，可画面看起来还是一顿一顿的，这是帧节奏的问题，[第二篇](02_screen_frame_vsync.md)的结尾咱们立过它：DWM 每个刷新周期取一次表面的最新内容，您更新得忽快忽慢，取到的内容就一顿一顿。咱们要修它，得动的是更新的时机，失效的面积帮不上忙，家伙什在[动画与帧调度](34_animation_frames.md)那一篇里等着咱们。

## 缩略图与活预览：合成器的现成红利

DWM 手里攥着所有窗口的照片，这个位置让一些功能成了白送的，缩略图就是其中最直白的一个。您把鼠标悬停在任务栏的图标上，弹出的预览小窗里那个窗口是活的：它在动，缩略图也跟着变了。Alt-Tab 的切换界面里同样是活的画面。这些小窗没有一张是程序配合截出来的图，它们是 DWM 直接把自己手里的表面缩了缩摆过去的。

应用侧其实也有一个入口，就是 DWM 的缩略图 API。咱们把调用的骨架摆出来看一眼，它是讲解用的示意，笔者没有在本仓库里编译验证过：

```cpp
// Live thumbnail: DWM composites a scaled copy of the source
// window's surface into our window. It stays live - the source
// keeps animating, the thumbnail keeps following.
HTHUMBNAIL thumb = nullptr;
DwmRegisterThumbnail(hwndDst, hwndSrc, &thumb);

DWM_THUMBNAIL_PROPERTIES props = {};
props.dwFlags = DWM_TNP_RECTDESTINATION | DWM_TNP_OPACITY | DWM_TNP_SOURCECLIENTAREAONLY;
props.opacity = 200;                  // 0-255
props.fSourceClientAreaOnly = TRUE;   // frame stripped, client area only
RECT dst = {0, 0, 240, 135};
props.rcDestination = dst;
DwmUpdateThumbnailProperties(thumb, &props);

// ... when done:
DwmUnregisterThumbnail(thumb);
```

三个函数各管一摊的活：DwmRegisterThumbnail 把目标窗口和源窗口登记成一对，DwmUpdateThumbnailProperties 负责的是摆位、透明度这些属性，DwmUnregisterThumbnail 管的是注销。要点落在一个活字上：登记的关系建立之后，源窗口的每次更新都会自动反映到缩略图里，咱们不需要轮询，也不需要咱们去刷新，因为两头本来就在同一个合成器的手里。GUI 开发里偶尔能借它做出小窗监控类的效果，搭进去的成本几乎为零。任务栏和 Alt-Tab 的活预览走的是同一条路，区别只是调用者换成了 shell，换成咱们的程序，调的也是这一套。

缩略图家族还有个偏门的亲戚，咱们记个名字就好，它的名字叫 DwmInvalidateIconicBitmaps。任务栏有些场合显示的，是窗口的静态 iconic 位图，活画面并不是唯一的选择。您的程序换了图标、或者界面大变样的时候，调它一声通知 DWM 旧的缓存作废就行。日常的 GUI 开发几乎用不上它，您在读别人代码读到它的时候，知道它是替任务栏更新缓存的就够了。

咱们也提醒一句边界：缩略图给您的只是摆位的权利，点击、焦点那些交互的事它一概不管，您要做能点的预览窗，接输入的活得您自己想办法。

## DWM 的 API 面：程序能碰到的那几个把手

DWM 的内部咱们进不去，但它对外留了一小排以 Dwm 打头的函数，GUI 开发里用得上的就下面这几个。它们的行为在公开文档里写得明明白白，其实正好也是“存疑标注”之外咱们能说死的部分。

头一个值得认识的是 DwmFlush。它的作用是等：等到您自己排队的 DirectX 表面更新都画上了屏，并在下一次呈现的时机返回，文档特意写明它不清整个会话的合成批次。什么场合用得上它？咱们画完一帧、想让这一帧确实上屏了再进行下一步的时候，比如音画同步类的场景，咱们拿它对齐一次节奏。不过对多数 GUI 程序来说，[第二篇](02_screen_frame_vsync.md)讲过的 Present 的同步间隔已经管住了节奏，DwmFlush 属于备用的精密家什，咱们知道它在就行。

另一个常用的是 DwmGetWindowAttribute，咱们给它传 DWMWA_EXTENDED_FRAME_BOUNDS 这个属性，它还回来的就是窗口可见部分的矩形，投出去的阴影不算在内。它的用处要从一个具体的错位说起：GetWindowRect 在某些 DPI 的配置下，量出来的窗口矩形带着一圈不可见的边距，那圈边距归 DWM 的装饰管辖。您要是做截屏对齐、或者算窗口的可见区域，用错了矩形就会差出几个像素。咱们在[坐标、DIP 与 DPI](03_dip_and_dpi.md)那篇里碰过 DPI 的门道，这里正好是它在合成时代的一个具体回响。

```cpp
// The visible frame bounds exclude the DWM drop shadow, which
// GetWindowRect may include as invisible margins under some DPI
// settings. Skeleton for illustration - not compiled in this repo.
RECT visible{};
DwmGetWindowAttribute(hwnd, DWMWA_EXTENDED_FRAME_BOUNDS,
                      &visible, sizeof(visible));
```

还有一个偶而用得上的：DwmSetWindowAttribute 配 DWMWA_TRANSITIONS_FORCEDISABLED，它把窗口最小化、还原时的动画关掉。有些工业界面和录屏的场景不想要动画，拿它一声令下就清净了。这排把手的共同点咱们也看出来了：全是围绕窗口的呈现做的小调节，合成的大权 DWM 一样也没撒手。

这排函数里还有一位 Vista 年代的老兵，它的名字叫 DwmExtendFrameIntoClientArea。它把窗口边框的绘制范围往客户区里延伸一段，玻璃年代的程序拿它把标题栏的质感延续进工具栏。玻璃没了之后它退居二线，但自定义标题栏的程序还会用它延伸一窄条，为的是让窗口保住投影和贴边的手感，浏览器的标题栏就是这么做的。它的行为在各个 Windows 版本上有些差别，您真要用的话，请以手头版本的文档为准，咱们这里只认脸。

收紧的也有一位：DwmGetCompositionTimingInfo，它当年把 DWM 的合成节拍信息报给程序，帧率、刷新的统计都有。微软的文档没有把它标成废弃，但用法从 Windows 8.1 起收紧了，查询也只能对整个桌面做了，窗口句柄您必须传 NULL，传了别的值会直接返回 E_INVALIDARG，按窗口问节拍的老用法收不回来了，新的代码不该再依赖它，您在读老代码见到的时候，知道它问的是合成的时刻表就行。咱们要想量节拍，正路是[第二篇](02_screen_frame_vsync.md)提过的 PresentMon 那类工具，咱们拿它从外面看事件，DWM 的里面是问不着的。

## 关不掉的 DWM

聊了这么多 DWM 的好处，咱们把它的地位按年代如实摆一遍，因为它的可选性是变过的。

Vista 和 Windows 7 的年代，DWM 的身份是一项服务，咱们在服务列表里搜 `Desktop Window Manager Session Manager` 就能找到它。您把主题换成基本主题，掉的其实只是玻璃，合成的活多半还在接着干。真正把合成关掉的手，是您停掉这项服务：停了之后，桌面退回直写屏幕的老世界，Aero 的毛玻璃跟着消失，窗口模式下的撕裂理论上也就有了回来的口子。折腾过那两代系统的读者可能还记得：显卡驱动出问题的时候，桌面会整个地掉回基本主题，那是 DWM 降级到了没有特效的合成，合成本身其实没有走。

咱们把分水岭画在 Windows 8。从它起 DWM 改成了常驻，用户界面上不再有关闭它的选项，合成也就永远地开着，Aero Glass 倒是同期被撤掉了。微软这么改的理由，与本篇讲的机制是接得上的：整个视觉栈，从磁贴界面到各窗口的缩放与合成，都建在了 DWM 上，它从一项可停的服务变成了桌面本身的一部分。咱们在[第二篇](02_screen_frame_vsync.md)里说过“窗口模式下您不容易看到撕裂”，在 Win8 之后的机器上，常规路径下咱们可以把话说死：您是看不到的，因为关不掉了。Windows 10 起带 ALLOW_TEARING 旗标的翻转模型交换链是刻意留的可撕裂口子，细节咱们留给讲交换链的篇目。

Server 版的谱系咱们单独交代，也单独标注了不确定。老一代 Windows Server 默认不装桌面体验的安装形态里，图形环境的配置与客户端是不同的，DWM 是否在场、怎么个在场法，各版本与各安装形态的差别，笔者没有逐版验证过，这里就不敢替您下断言了，您真在 Server 上做开发的话，请以手头版本的文档为准。

Win10 和 Win11 的年代，DWM 的地位没有再变过：常驻、关不掉、整桌面的画面都过它的手。变的是它肩膀上的效果清单，亚克力一类的半透明材质、窗口的投影、任务栏的模糊，清单一代比一代地厚，而每一样新效果的底下，走的还是本篇讲的 OVER 混合。您要是觉得某个版本的界面“看起来贵”，贵的部分多半就记在合成的开销上，咱们在后面讲代价的小节里回到它。

## 合成的开销，最终也归咱们付

机制讲完了，咱们把代价也摆到桌面上来，因为它是 GUI 开发里实打实的预算。DWM 替咱们扛住了撕裂和遮挡，扛的方式是把整桌面的拼合活揽到了自己身上，而拼合的每一层都有价钱：窗口叠得越多，OVER 的运算就越多，半透明的区域是逐像素的混合，毛玻璃一类的效果更是要对底下的内容做取样和模糊，GPU 的开销一路往上走。

这些开销平时其实显不出来，因为桌面 GPU 拼几个窗口对咱们来说是轻而易举的事。可是 GPU 忙起来的时候，欠下的开销就显出来了：您的动画想要每帧都有新内容，DWM 的每帧拼合也得跟得上，等合成排不上队了，用户看到的动画就是一顿一顿。[第二篇](02_screen_frame_vsync.md)讲帧节奏时咱们立过这个问题，现在咱们能给它再添一层注脚：帧节奏除了看您画得多快，还得看合成的那一路堵不堵。所以界面做得层层叠叠、效果堆得满满的团队，到头来优化的方向往往是做减法，少一层就省一层的合成。

对咱们写普通窗口程序的读者，落到实践里的含义就两句：一是别把不透明能解决的事做成半透明，二是动画卡的时候，排查的眼光除了自己的绘制，也要分一点给桌面上别的窗口。性能的开销按整张桌面算，您窗口之外的部分也算在里面。

合成开销想量化的话，工具还是咱们的老朋友。[第二篇](02_screen_frame_vsync.md)介绍过的 PresentMon 记的是呈现的事件，您把自己程序的界面从层层半透明改成全不透明，咱们前后各录十秒，帧的时间分布一对比，合成那头省下的工夫就显出来了。测的思路和咱们改代码的思路是一样的：一次只动一个变量，动的是层数还是透明，咱们自己得记清楚。

## 应用侧的入口，留给 DirectComposition

咱们讲到这里，DWM 在咱们眼里的样子就完整了：一个常驻的 GPU 合成器，把各窗口照片的收集、遮挡的计算、逐像素的叠合和整帧的送出全包了。您可能已经咂摸出味儿来了：合成的这么多本事，z 序、透明、变换、模糊的能力，窗口程序隔着 `InvalidateRect` 能摸到的边其实少得很。咱们要是想让程序直接指定谁叠在谁上面、带什么效果，入口就是下一篇的主角 DirectComposition。

它和本篇的交接点，就是咱们前面立过名字的那个样式位。挂上了 `WS_EX_NOREDIRECTIONBITMAP`，重定向的表面就没有了，程序把画面画进自己的 Direct3D 表面，再把表面作为 visual 挂上一棵交给 DWM 的合成树。主线的[控件如何上屏](../gui/08_widget_on_screen.md)里提过，那一篇的 M2 第 2 档（把上屏从 GDI 整条换成 Direct2D 加 DirectComposition 的那一档）换的正是它：换走的代价不小，视觉树、样式、无障碍全得咱们自己接，而换来的东西里，逐像素的 alpha 对 GUI 特别实在。咱们这一篇把照片由谁存、屏幕由谁管的底盘看清了，下一篇再上手开车的活。

您从这里也能看明白 DWM 架构的一层深意：合成器从来不挑照片是谁画的。GDI 画的照片、Direct2D 画的照片、Skia 经 GPU 后端画的照片，到它手里都是同样的一堆像素，所以本线前面换过的那么多画具，才能真正地即插即用。DirectComposition 把同样的待遇开放给了应用侧。您的 visual 树和系统窗口的照片，从此在同一台合成器里是平起平坐的了。

咱们也预告一下那一篇里您会遇到的老朋友：[D3D11 设备](24_d3d11_device.md)那一篇的设备对象会回来当合成设备的底盘，[位图](10_d2d_bitmaps.md)那一篇的表面概念会换一副 visual 的面孔。

## 您可以自己动手看的几处

有几处观察您现在就能做，做完了之后，本篇的机制就落进您自己的眼睛里了。

您打开任务管理器的详细信息页，找到 dwm.exe 的那一行，然后您拖动一个大窗口来回晃，看它的 GPU 占用怎么动。旁边再开一张 GPU 占用的曲线图，您拖与不拖各录一段，咱们对比着看，DWM 整桌面拼合的活就有了直观的读数。

您再拿上头那个缩略图的骨架，随便找两个自己的窗口登记成一对。源窗口里放一段动画、或者一个一直在变的画面，缩略图自己就跟着动了，而您全程没有写过一句刷新的代码，两头在同一个合成器手里的道理，就变成了手上的经验。

您还可以做一个透明度的对照。找一个支持窗口透明度设置的程序，把透明度从全不透明慢慢地调到半透明，同时盯着任务管理器里 dwm.exe 的 GPU 占用。调到了半透明之后，DWM 对这个窗口底下的内容也得逐像素地混合了，占用的变化您多半看得见。

`DWMWA_EXTENDED_FRAME_BOUNDS` 那个把手也值得您亲手量一次。您写十行的小程序，咱们把 GetWindowRect 和 DwmGetWindowAttribute 两个矩形都打出来，对一对它们的差。差值是窗口样式和 DPI 缩放一起决定的，带边框的窗口通常不是零，无边框的窗口两边才相等，看过了这个差，您以后算窗口的可见区域就不会再拿错矩形。

咱们还能做个小实验，用的就是 `DWMWA_TRANSITIONS_FORCEDISABLED` 那个把手。您把动画关掉再最小化窗口，过渡就没了，画面就直接切换了。观察本身没什么学问，它给您的手感是：系统动画原来是一直住在合成器里的，关掉的那一刻，住处就露出来了。

还有一处对照留给您怀旧。您在系统里找一找还跑着 XP 的老机器或者虚拟机，截一张它拖动窗口时的图，再回到自己的机器上拖同一个窗口。旧世界的拖影和白块、新世界的整窗顺滑，两幅画面摆在一起的时候，比本篇里的任何一段文字都更有说服力。

您要是想看数据而不只想看画面，[第二篇](02_screen_frame_vsync.md)里介绍过的 PresentMon 还能帮上忙。您开着它拖一轮窗口再停一轮，事件流里呈现最勤的，多半就是 DWM 自己的合成，普通窗口在您不碰它的时候是安安静静的。把工具的输出和本篇的模型对上，您就等于亲手摸了一回合成的脉搏。

## 自查几问

您读到这里，下面几个问题应该都能凭本篇的机制答上来了，答不上的那一段值得回去再看一遍。

1. 重定向表面存的是什么？窗口移动和被遮挡，各自会不会让它重拍？
2. DWM 合成一帧的四步是什么？其中哪一步产出了遮挡的关系？
3. 窗口程序为什么撕不了屏幕？可能被撕的那块内存归谁管？
4. 鼠标指针为什么不归 DWM 画？它走的是哪条通道？
5. 拖动窗口时别的窗口为什么不用重画？XP 的年代为什么就得重画？
6. 进程侧的失效和桌面侧的合成，两份记录各记的是什么？谁在两头传递？
7. DwmFlush 与 DWMWA_EXTENDED_FRAME_BOUNDS 各解决什么问题？
8. 系统的最小化动画为什么不劳驾您的 `WM_PAINT`？
9. 独占全屏的游戏把一块屏幕拿走了，另一块屏幕上的桌面归谁？
10. 基本主题与停用服务，各自关掉的分别是什么？
11. `WS_EX_NOREDIRECTIONBITMAP` 拿掉的是什么？拿掉之后程序得改走哪条路？
12. Win8 之后为什么找不到关闭 DWM 的选项？
