# HDC 与 GDI 对象模型

您要是刚写下自己头一段 GDI 绘图代码，咱们马上能做一个几十秒就有结果的观察。您把程序跑起来，打开了任务管理器，在它的详细信息页签里勾出 GDI 对象的那一列，然后拖动窗口的边框逼它连续重画。正常程序的计数会在一个不大的范围里待着，而泄漏中的程序一格一格往上爬，松了手也不回落。新手的第一段绘图代码，十有八九是后者的样子：画面的表现毫无异常，系统资源却在底下悄悄地漏。它为什么会这样？这不是哪一行写错的事，得把 GDI 的整套绘制模型摊开看才知道，咱们这一篇就来干这件事。

GDI 是 Windows 最老的一套二维绘图接口（Graphics Device Interface），它的绘制模型是一台状态机。状态机的说法听着玄，其实意思很朴素：所有的绘图设置都存在系统那边。您每次调用绘图函数，函数本身带的只有画在哪、画多大的信息，用什么画，全看系统里存着的当前状态。HDC 就是它的操作面板，画笔、画刷、字体、位图是拧在面板上的零件。咱们把面板和零件一件一件认过去，开头那个泄漏的来路自然就显形了。

咱们对 GDI 其实不是初次见面。这套教程有两条线：本线是您正在读的渲染管线，主线是搭骨架的 gui 线，咱们在那里从零搭了一个真程序。本线第一篇追像素去向的那一段，`CreateCompatibleDC` 和 `SelectObject` 已经在离屏画布里露过了面，主线第一篇的 demo 里，画那一行自绘文字走的也是 GDI。本篇要做的是把它们背后的整套对象模型认齐，您以后读任何 GDI 代码，认得出哪些调用动的是面板，哪些动的又是零件。

## 一段正在泄漏的代码

咱们把一段典型的反例写出来，它的出场率特别高，您以后见到就能认出同类：

```cpp
case WM_PAINT: {
    PAINTSTRUCT ps;
    HDC hdc = BeginPaint(hwnd, &ps);

    HPEN pen = CreatePen(PS_SOLID, 2, RGB(200, 40, 40));
    SelectObject(hdc, pen);
    Rectangle(hdc, 20, 20, 220, 120);

    EndPaint(hwnd, &ps);
    return 0;
}
```

它编译和运行都过得好好的，矩形也确实画出来了，毛病却藏在了底下。每一轮 `WM_PAINT` 的处理里，`CreatePen` 都会造出一支新的画笔，而它造出来的所有笔，删它们的代码一行也没有。您拖一下窗口的边框，系统就送上一轮接一轮的重画，笔就一支一支漏进了系统。任务管理器里爬个不停的那一列，爬的就是它们。

它的来历也值得咱们看一眼。咱们写 C++ 的直觉是样式跟着函数走，画红矩形就该有一个红色的参数，而 GDI 偏偏不认参数，只认面板上的当前拧法。新手照自己的直觉写代码，就会漏掉换零件的那几步，因为他的心智模型里压根没有那几步。

您可能想给结尾补一句 `DeleteObject(pen)` 了事。这里咱们卖个关子：补了照样漏，而且漏的原因比忘了删有意思得多，等咱们讲到删除的地方再揭开。眼下咱们得从面板说起，认清楚 `HDC` 到底是个什么样的东西。

## HDC：画往哪儿去的手柄

HDC 的全称是 Handle to Device Context，翻译过来是设备上下文的句柄。设备上下文（DC）是 Windows 对一个可以画图的目的地的抽象，目的地可以是整个屏幕、窗口的客户区、内存里的一块位图、甚至打印机。绘图函数认的是 DC，而不是具体的设备，您手里递过去哪个 `HDC`，您的画就落在哪个目的地。

为什么非要隔这么一层？因为输出的设备实在五花八门：显示器和打印机的分辨率差着好几倍，颜色深度也各有各的讲究，有的设备还画不出某些花样。没有这层抽象的话，咱们得为每种设备写一套绘制代码。有了 HDC，咱们只需要说画个红矩形，把它翻译成写像素、喷墨还是改内存的活，都是系统按目的地的脾气去办的事，咱们的代码一行都不用改。

面板上都存着什么？一个 DC 里放着当前选中的画笔、画刷、字体、位图、区域，再加一批散装的旋钮：文字颜色、背景模式、绘图模式、坐标映射方式。画笔管线条的颜色和粗细，填充的事归画刷，文字长什么模样，看选的是哪支字体。位图咱们单拎出来说，它就是内存 DC 的画面本身，离屏画的东西全落在它身上。区域则圈住允许落笔的范围。这些设置放在系统管理的内存里，`GetDC` 或 `BeginPaint` 的时候系统替咱们备好默认值，您改一处，后面的所有绘制就跟着变了。

咱们拿 `TextOutW` 的参数表来查证样式的下落，您看它长这副样子：

```cpp
BOOL TextOutW(HDC hdc, int x, int y, LPCWSTR lpString, int c);
```

五个参数里您找不到颜色，字体您也找不到。参数表里没有它们的位置，它们的住处是面板。您想让文字变红，您得去拧 `SetTextColor`，想换字形的话，您得把一支新字体拧进字体槽。状态机的脾气全在这里了：按按钮的是绘图函数，拧旋钮管的是样式，它们俩各管各的。

## DC 的四条来路

面板是系统的，咱们手里的面板要么借来，要么自己造。拿到 DC 的路子有四条，还法咱们归成三种，因为 `GetDC` 和 `GetWindowDC` 还的时候共用同一个 `ReleaseDC`，咱们就把它俩归成一类，下面咱们一对一对认。

| 拿法 | 还法 | 用在哪 |
|:---|:---|:---|
| `BeginPaint` / `EndPaint` | 两个调用之间 | 只在 `WM_PAINT` 分支里 |
| `GetDC` / `ReleaseDC` | 同一线程内配对 | 想画客户区的任何时候 |
| `GetWindowDC` / `ReleaseDC` | 同上 | 要画标题栏、边框这些非客户区 |
| `CreateCompatibleDC` / `DeleteDC` | 自己创建，自己注销 | 内存里的离屏绘制 |

总的原则其实就一条，咱们借的面板要还回去，咱们造的面板要注销掉，而把借与造混在一起的话，还法也就会跟着配错了。

`BeginPaint` 和 `EndPaint` 是只在 `WM_PAINT` 里合法的一对，[第一篇](01_status_to_pixels.md)讲 `BeginPaint` 交出脏区的那一段里，咱们见过它的全套动作：交出的是 HDC，把裁剪区域设成了更新区域，还把更新区域也验证掉了。这里要补的是它跟别的来路不一样的地方：它交出来的 HDC 只在两个调用之间有效，等到 `EndPaint` 调完的那一刻，句柄就作废了，想存下来下回再用是存不成的。还有一条反方向的红线：在 `WM_PAINT` 里改用 `GetDC` 的画法，更新区域就没有人验证了，`WM_PAINT` 会一条接一条地发下去，CPU 就烧起来了。

`BeginPaint` 交出来的画布还带着一块值得咱们认的记号：`PAINTSTRUCT` 里的 `rcPaint`，它圈住的是本次真正要画的脏区。主线 demo（gui 那篇的示例程序）的绘制没理会它，每次画的都是整个客户区，因为整个客户区一起失效是主线框架的取舍。等脏区的计算精细起来，只画 `rcPaint` 圈住的那一块才有意义，那是下一篇的事。

`GetDC` 借的是窗口客户区的 DC，您随时能借，画完了就得在同一线程里还回去。它不碰验证的事，所以适合画此刻就想上屏的东西，比如不等消息队列闲下来的一个动画帧。有朋友会想把它缓存起来省调用的开销，咱们把 native_win32 那套参考文档叫作书架，书架的[HDC 完全指南](../native_win32/18_ProgrammingGUI_NativeWindows_GDI_HDC.md)提醒过它的代价：窗口销毁前必须释放，窗口大小变了缓存还可能失效，省下的开销换回来的全是隐患。`GetWindowDC` 是它的放大版，把标题栏和边框也一起交给您，还的时候用的仍是 `ReleaseDC`，不过跟系统的非客户区绘制打架的风险您得自己扛，完全指南对它有整节的展开。

四种来路里最特殊的是 `CreateCompatibleDC`：它造的 DC 不连任何真实设备，是一块纯内存的操作台，而且出生时怀里只有一块 1×1 像素的单色位图。您想在它上面画出像样的东西，得拿 `CreateCompatibleBitmap` 造一块足够大的位图，装上去用的就是 `SelectObject`。不装的话，画什么都落进仅有的一个像素里，画面上也就什么都看不见了。它是双缓冲的主角，主线 demo 的 `WM_PAINT` 里干活的正是它，书架的[双缓冲专章](../native_win32/23_ProgrammingGUI_NativeWindows_GDI_DoubleBuffer.md)把它单独讲了一整篇。它的还法也换成了另一副：借来的 DC 用 `ReleaseDC` 归还，自己造的 DC 用 `DeleteDC` 注销，两套词是不能混用的，配错了的调用会直接失败。

四对函数、三种还法都摆在上面了，您交一段绘图代码之前可以按还法挨条核对：

1. 每个 `BeginPaint` 都在同一个分支里等到了 `EndPaint`，中间没有提前 `return` 把它跳过去。
2. 每个 `GetDC` 和 `GetWindowDC` 在同一线程里还了 `ReleaseDC`，走错误返回的路径上也要还。
3. 每个 `CreateCompatibleDC` 用 `DeleteDC` 注销，它身上选过的位图，按下一节的顺序处理。

清单里的第二条值得咱们单独说说，因为错误路径是泄漏的重灾区。您的绘制函数要是在中间就返回了，还 DC 的那一行根本轮不到执行，借出去的面板就悬在了半路。函数的返回点越多，这样的口子就越多。RAII 说的是构造时获取资源、析构时自动释放的封装手法，等咱们讲到它的时候，再回头看这些口子怎么堵。

## SelectObject：拧上去，换下来

咱们想让零件上面板，走的是 `SelectObject`：

```cpp
HGDIOBJ SelectObject(HDC hdc, HGDIOBJ h);
```

签名里真正要紧的是返回值。您把新对象拧进槽位的同时，函数把槽里原来那个旧对象递还给您，槽位永远是满的。这个进出各一件的设计带来了两条直接的后果，咱们一条一条看。

面板上的槽位有好几个，而入口只有一个。`SelectObject` 的参数类型是 `HGDIOBJ`，画笔、画刷、字体的句柄都能往里传，返回的旧对象也是同类型的。所以存旧对象的变量，咱们得把类型跟槽位对齐，画笔槽退回来的就转成 `HPEN` 收着。

旧对象攥在咱们手里，就是还原的凭据。标准的使用节奏长这样：

```cpp
HPEN pen = CreatePen(PS_SOLID, 2, RGB(200, 40, 40));
HPEN old = (HPEN)SelectObject(hdc, pen);   // slot in the new pen, get the old one back
Rectangle(hdc, 20, 20, 220, 120);
SelectObject(hdc, old);                    // put the old pen back into the slot
DeleteObject(pen);                         // now the pen is safe to destroy
```

画完了之后，咱们把 `old` 选回去，面板就恢复了出厂的拧法，自己造的笔也才删得掉。最后两行的顺序为什么是死的，这就接到了第二条后果上：槽位永远是满的，意味着被选着的对象删不得。

为什么要把样式做成槽位，而不是做成参数？书架的[GDI 对象专章](../native_win32/19_ProgrammingGUI_NativeWindows_GDI_Objects.md)解释过它的用意：GDI 对象是可复用的绘图属性模板，一支画笔造好了，可以在多个 DC 的身上轮流用，系统也只需要维护一份画笔的定义。当然复用的好处，咱们要到对象多起来的程序里才体会得到，眼下咱们只要认下进出各一件的节奏就够了。

咱们再把主线 demo 里那段真实代码看一遍，[第一篇](01_status_to_pixels.md)讲像素写进哪块内存的那一段里它一闪而过，现在它的每个动作都能对上号了：

```cpp
HDC     buffer_dc = CreateCompatibleDC(window_dc);
HBITMAP buffer    = CreateCompatibleBitmap(window_dc, client.right, client.bottom);
HGDIOBJ previous  = SelectObject(buffer_dc, buffer);
// ... 把整帧画面画进内存位图 ...
BitBlt(window_dc, 0, 0, client.right, client.bottom, buffer_dc, 0, 0, SRCCOPY);

SelectObject(buffer_dc, previous);
DeleteObject(buffer);
DeleteDC(buffer_dc);
```

头一处 `SelectObject` 把大位图装上内存 DC 的同时，也把 DC 出厂自带的那块 1×1 原件攥在了手里。收尾处的 `SelectObject` 把原件装回去，然后位图的删除和 DC 的注销才轮得上。装上、画、换回、删的四步里，上一篇没细讲的就是换回，现在您知道自己看到的是什么了。

## 删不掉的被选对象

`DeleteObject` 的规范是死的：对象只要还选在某个 DC 的槽位上，这个调用就删不掉它了，函数报回的是失败，对象继续占着系统的配额。所以咱们不能把恢复与删除的顺序反过来。反了的话程序不会崩溃，您也听不到任何报错，笔就这么安静地漏下去。

咱们把顺序写反的版本也摆出来：

```cpp
HPEN pen = CreatePen(PS_SOLID, 2, RGB(200, 40, 40));
HPEN old = (HPEN)SelectObject(hdc, pen);
Rectangle(hdc, 20, 20, 220, 120);
DeleteObject(pen);                          // the pen is still selected: FAILS
SelectObject(hdc, old);                     // the pen leaves the slot, too late
```

跑到删除那一行的时刻，槽里待着的还是它，调用报的是失败。后面一行把旧笔换了回去，笔倒是离开了槽位，可删除的机会已经过去了，咱们谁也不会回头再补一句 `DeleteObject`，笔就这么漏在了系统里。

编译器在这里是帮不上忙的，咱们得说清楚为什么。`HGDIOBJ` 是个不透明的值，咱们从类型上知道的只有手里握着一个句柄。它选没选进 DC、借的面板还没没还，这些状态咱们在类型里都找不到，配对错了编译器自然查不出来。配对的纪律全压在咱们自己头上，工具链替咱们把关的成分是零。

现在咱们把开头卖的关子揭开。那段反例漏掉的笔，它的代码里连 `DeleteObject` 的影子都没有，这当然漏。您要是按直觉在 `EndPaint` 前面补一句 `DeleteObject(pen)`，结果它照样漏：笔此刻还选在 DC 的槽里，删除的调用会失败，而函数的返回值您也没接住，失败就无声无息了。咱们要把它修干净，就得按上一节的节奏来：把默认的笔换回槽位，然后删掉自己的笔，两步里省了哪步都不成。

不走这套流程的零件也有，咱们管它们叫库存对象（stock object），都是系统预造好、全体进程共享的现成件。`GetStockObject` 领到的就是它们，名单里有 `WHITE_BRUSH`、`BLACK_PEN`、`DEFAULT_GUI_FONT` 这些现成的件。咱们不创建它们，删除这事也永远轮不到咱们。

主线 demo 给三个控件发的是 `WM_SETFONT`，领的正是 `DEFAULT_GUI_FONT`，[主线第一篇](../gui/01_naked_win32.md)里咱们还特意提醒过：领到的是共享对象，删除的调用在它们身上不起作用，因为系统手里握着的也是同一份。`GetSysColorBrush` 给的系统色画刷同理，用完了也不删。常用的几件库存对象，咱们列在下面，您要用的时候直接领：

| 常量 | 是什么 |
|:---|:---|
| `WHITE_BRUSH` / `BLACK_BRUSH` | 白色、黑色的实心画刷 |
| `HOLLOW_BRUSH` | 空心画刷，画只带边框的图形 |
| `DC_PEN` / `DC_BRUSH` | 颜色能在线改的画笔、画刷 |
| `DEFAULT_GUI_FONT` | 控件默认的界面字体 |

恢复的习惯倒值得您保持：库存对象被选进了 DC，用完了把它选回去，槽位里留着的才是系统默认，别的代码才不会替您承受意外。

书架的[GDI 对象专章](../native_win32/19_ProgrammingGUI_NativeWindows_GDI_Objects.md)把画笔、画刷、字体、区域一类一类摊开讲了各自的创建函数，本篇讲的是它们共用的模型，细节您可以去书架的对应章节里查。

## 一万件的配额

为什么漏几支笔也值得咱们认真对待？因为 GDI 句柄是系统级的资源，每个进程能握住的件数有上限。按文档的老说法，GDI 对象的历史上限是一万个，咱们记的是量级，精确到个位的数字谁也不敢担保。一个界面当然用不了一万支笔，不过泄漏会累积：一次重画漏掉的虽然只有一件，一段拖拽攒下的就有几百件，攒到配额耗尽的那一刻，`CreatePen` 一类的创建调用全体开始失败。那时候的症状，是界面上什么都不再出现了，而您在代码里找不到哪一行错了，排查的方向感，全靠今天认过的模型给。

咱们手头有现成的排查路子。任务管理器的那一列是一个，代码里更直接的是这个：

```cpp
DWORD count = GetGuiResources(GetCurrentProcess(), GR_GDIOBJECTS);
```

在怀疑泄漏的调用前后各读一次，您就拿到了前后两个时刻的 GDI 对象数。数字只涨不跌的话，泄漏就算确认了。书架的 HDC 完全指南还给了 Application Verifier 的路子，程序退出时它能把没释放的对象连同分配时的调用栈一起报出来，您按着栈就能找到漏点。

读数的时机也是有讲究的，咱们挑的是同一条绘制路径的前后，比如同一个 `WM_PAINT` 分支的开头和结尾，不相干的两个时刻是比不出名堂的。您比出来的差值要是零，干净路径就到手了：路径创建了多少件，也就注销了多少件，没有一件是赖在系统里的。调试输出里各打一行的话，中间夹住的代码越少，您下判断的底气也就越足。

任务管理器的那一列要看准对象，咱们看的是自己进程的那一行数字，别的进程是当不了参照的，因为各家的基线本来就不一样。您在列标题上右键打开选择列的菜单，那一列就是这么勾出来的。

这一套谁创建谁注销的纪律，C++ 的惯用解法是 RAII 包装，书架的 HDC 完全指南讲对象生命周期的那一步里，有一个 `GDIObjectGuard` 的样例可以参考。您在绘制函数里提前返回的时候，析构还是会照跑的，前面悬在半路的面板也就能被它接住。不过咱们得提醒一句：包装替咱们兜住的只是别忘删，而删得掉删不掉，仍取决于选入与选出的顺序。模型本身是绕不开的，认模型的功夫也就省不掉。

## 面板上剩下的旋钮

`SelectObject` 管的是槽位，面板上还有一批直接拧的旋钮。demo 里真用过的旋钮是 `SetBkMode`：画那行自绘文字之前调了 `SetBkMode(buffer_dc, TRANSPARENT)`，它决定文字背后的底色填不填。`SetTextColor` 咱们上文刚认过，管文字的颜色，`TextOutW` 的参数表里没有颜色，颜色拧的正是这个旋钮。

映射模式是逻辑坐标落到设备的换算设置（mapping mode），咱们一句话带过它：默认的 `MM_TEXT` 就是像素坐标，右是 x 的正方向，下是 y 的正方向，咱们在主线和本线里都没动过它，所以所有坐标按像素理解就行。别的模式本篇就不碰了，逻辑像素和物理像素之间的那层换算，[第三篇](03_dip_and_dpi.md)里咱们专门算过。

旋钮多了以后，咱们就会想要存档。`SaveDC` 把当前全套设置压进 DC 自带的状态栈，而 `RestoreDC` 再把它弹回来，中间随咱们怎么拧：

```cpp
int saved = SaveDC(hdc);
// ... 随便改面板上的设置，画图 ...
RestoreDC(hdc, saved);
```

绘制流程长了起来以后，函数入口存档、出口弹回是很实用的纪律，主线 demo 里没见它的影子，只是因为它的绘制短到咱们还用不着。

## 您可以动手的三处

下面三处的指向都很具体，您做的时候能把机制摸到手：

1. 把开头那段反例敲进主线 demo 的 `WM_PAINT` 里跑起来，照本篇开头说的方法看任务管理器。您拖一下窗口边框，那一列爬起来的速度比想象中快。
2. 给反例补上 `SelectObject(hdc, old)` 和 `DeleteObject(pen)`，跑通了，再把换回旧对象的那行注释掉。您把 `DeleteObject` 的返回值接住打出来的话，里面报的失败，就是本篇讲的删不掉本人。
3. 把 `GetGuiResources` 的读数打在调试输出里，每次重画报一回，您看着数字跟着重画的次数走，泄漏的节奏就摆在眼前了。

## 附录：修干净的反例

咱们把开头那段反例修完整，节奏就是本篇讲的全套：

```cpp
case WM_PAINT: {
    PAINTSTRUCT ps;
    HDC hdc = BeginPaint(hwnd, &ps);

    // Create a pen, slot it in, and keep the old one - it is the
    // receipt for restoring the panel afterwards.
    HPEN pen = CreatePen(PS_SOLID, 2, RGB(200, 40, 40));
    HPEN old = (HPEN)SelectObject(hdc, pen);

    SetBkMode(hdc, TRANSPARENT);
    Rectangle(hdc, 20, 20, 220, 120);

    // Restore the old pen, then destroy ours: the reverse order
    // fails silently and leaks the pen.
    SelectObject(hdc, old);
    DeleteObject(pen);

    EndPaint(hwnd, &ps);
    return 0;
}
```

这套顺序咱们从借面板一路走到还面板，中间每一步都有它的位置。您把它跟开头的反例并排放着看，多出来的就是保存旧对象的 `old`、把背景模式调成透明的一行，再加上换回和删除的两步收尾，节奏还是本篇讲的全套，换画刷再走一遍也是一样的。

## 状态机的标本

咱们管 GDI 叫标本，是因为它把状态保留的设计推到了头，推到了连颜色都不随调用走的地步。后面的 API 多多少少都带着它的影子，Direct2D 的互操作章节里咱们还会跟它打照面。

咱们再给这套设计补一个名字叫 retained-state，直译过来是状态保留：样式统统留在绘制目标的那一头，调用走了它也不跟着变。它的代价咱们这一篇从头到尾都在领教。咱们既然不能靠调用参数带样式，就得把进出与配对的纪律全背在自己身上，因为每漏掉一步都会在系统里多出一件删不掉的对象。

两边的差别，咱们摆成一张表看得更清楚：

| 对照的点 | GDI | Direct2D |
|:---|:---|:---|
| 画刷在哪 | 拧在 DC 的槽位上，`SelectObject` 换进换出 | 每次调用的参数 |
| 文字颜色在哪 | `SetTextColor` 一类的旋钮 | 画刷自己带着 |
| 忘了恢复的后果 | 删除失败，配额悄悄地漏 | 没有可忘的状态 |
| 状态存在哪 | DC 的面板里 | 基本不存，随调用走 |

表里的每一条，咱们到 Direct2D 那几篇里都会亲手摸到，眼下记个大概的样子就够用。

后面的 Direct2D 会把模型整个反过来：画刷成了每次调用的参数，`FillRectangle` 的参数表里写着刷子本身，画完了也不留。到时候咱们会看到，命令流式的模型是怎么把忘了恢复的这一类错误从语法上抹掉的。当然，Direct2D 也不是全无状态的，坐标变换这样的状态仍设在目标上，不过绘制属性基本随调用走，两边对照着读的话，各自的得失咱们才看得清。它的正面出场在[工厂、设备与渲染目标](06_d2d_targets.md)那一篇，是本线的第六篇。

下一篇咱们还留在 GDI 的世界里再挖一层，[失效、脏区与重绘](05_invalidation_dirty_region.md)那篇讲的是 `BeginPaint` 交出来的更新区域从哪儿来、怎么攒、怎么算精细，咱们到那边接着看。
