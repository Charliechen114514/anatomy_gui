# 架构对照：场景图、显示列表、即时模式

[动画与帧调度](34_animation_frames.md)的结尾咱们预告过本篇：画具一件件地摸完了，镜头也该拉远了。从[开篇](01_status_to_pixels.md)的 `InvalidateRect` 一路到[Skia 的 GPU 后端](16_skia_gpu_backend.md)，咱们练的都是同一层的手艺，也就是怎么把一帧画面又快又好地填进表面。可真到了要写一个完整的 GUI 时，您面对的问题就换了样子：界面的描述放在谁的手里，重画的活由谁来接，命令的攒法又归谁管。这些问题的答案就叫渲染架构，本篇把常见的四种摆上桌对照着看，咱们挨个认识。

四个名字咱们挨个交代。保留模式的英文是 retained mode，它说的是界面里的每个对象作为常驻的东西活在系统或框架的手里，画面则是常驻描述投出来的像，而咱们从头到尾走的就是它。场景图的英文是 scene graph，它是为 GPU 的时代重新设计过的保留树，树上挂的是绘制单元、变换和材质。

显示列表的英文是 display list，它说的是命令的组织方式：把一帧要画的命令按顺序录成一串，录好了交给渲染的一方去回放。即时模式的英文是 immediate mode，它干脆没有常驻的界面对象，每一帧都把界面的描述重来一遍，重画也是整帧的。四位咱们各认一遍，篇尾咱们再把同一个小界面塞进两种循环里做对照。

## 保留模式：咱们一路走来的老路

咱们从最熟悉的一路开始。它的形状您其实早就见过：界面上每个控件都是一个常驻的对象，对象活在持有它的一方手里，画面则是对象的像。应用要干的事是改对象，改完之后重画的活归谁接，就是各家架构的分水岭了。

Win32 的原生控件是它最老牌的标本。您在[主线第一篇](../gui/01_naked_win32.md)里亲手用过它：咱们一句 `CreateWindowExW` 调下去，`EDIT`、`BUTTON`、`STATIC` 就作为真实的窗口住进了系统，画它们的代码在系统的窗口过程里（这几个是 user32 一侧早就注册好的系统类），咱们一行绘制代码都没写，按钮照样有模有样地站在了窗口里。您调 `SetWindowTextW` 改标签文字的时候，函数给控件发的是 `WM_SETTEXT`（这是 MSDN 的 Remarks 写明的行为），控件收到了消息就自己安排重画，咱们的代码从头到尾都没碰过画笔。

咱们再把另一半也翻出来看：控件失效之后，谁挑起重画的时机？答案您在开篇里已经见过，消息队列空闲的时候系统才生成 `WM_PAINT`，`UpdateWindow` 还让头一帧插了一次队。咱们在这里重提它，为的是把重画的时机也归到指挥权的名下：在保留模式的世界里，连重画的时刻都是系统说了算的，应用交出去的只是变化的登记。您把这幅图记在心里，后面三种架构对照的全是同一件事，也就是指挥权的归属。

它在 Windows 上其实还不止控件这一层。咱们在[开篇](01_status_to_pixels.md)里看过 DWM 的做法：每个窗口的画面都被存着一整份重定向表面，系统的手里握着的是一张成品照片。您拿别的窗口把咱们的窗口盖住再拖开，画面直接就回来了，咱们谁也不用重画。连画面本身都被系统保留了下来，Windows 的原生体系在保留的路上走得比多数框架都远。

Qt Widgets 走的是同款路线，只是把常驻的对象从 HWND 换成了 C++ 的对象。按 Qt 公开文档的说法，每个 `QWidget` 都是常驻在内存里的对象，它们一层层地嵌套，组成了一棵对象树，内容变了就走 `update` 一路登记，`paintEvent` 里的代码再按需重画。您把它跟 Win32 的控件摆在一起看，骨架是同一副的：常驻的树，外加一条失效增量更新的通路。

失效的通路，咱们在本线上花过整整一篇去解剖，那篇的题目是[失效、脏区与重绘](05_invalidation_dirty_region.md)。它的好处跟它的代价都从常驻两个字里来。好的一头是增量：界面静止的时候开销接近零，系统是知道哪些东西没变的，[开篇](01_status_to_pixels.md)讲过的更新区域攒批，说的就是它怎么把零散的变化并成一次重画。

代价的一头是状态和画面分了家：您改的是变量，屏幕上的却是像素，中间的失效接线谁也不替您保证。主线第六篇（[属性与重画](../gui/06_property_repaint.md)）造框架时收拾的头一个痛点就是它，`lstrcpynW` 拷完字符串就停手的那个反面教材，咱们在开篇里对着它看了很久。

增量的能力也有它的边界，咱们在[失效、脏区与重绘](05_invalidation_dirty_region.md)里见过重绘风暴的说法：失效报大了、报多了，代价都落在重画的那一头，包围盒白算的面积就是这么来的。您从架构的视角再看一遍，它说的其实是保留模式的一条暗线：系统替咱们省力的能力，取决于咱们报失效报得准不准。框架层为它做的努力，主线第六篇的自动接线是一路，脏区算得精细的功夫是另一路，两路奔的都是让登记别冤枉了没变的像素。

## 场景图：为 GPU 重新设计的保留树

保留模式的老骨架是在 CPU 画图的时代定型的，GPU 来了以后，同一副骨架就得重新考虑了。咱们得从 GPU 的脾气说起，不然就说不清场景图为什么存在了。

GPU 画图吃的是批量这一口。一次绘制调用怎么把顶点送上去，您在[GPU 管线](23_gpu_pipeline.md)那篇见过它的样子。这里要紧的是另一件事：CPU 与 GPU 每打一次交道都有固定的开销，所以同样的画面，把命令合成了一大笔提交，远比拆成几百笔的小提交划算。

这个思路的名字就是批（batch，GPU 一次吞下的一组绘制命令），批里的纹理和状态都不换，批越整的时候 GPU 跑得就越快。麻烦在于失效增量的省钱逻辑是反着算的：它省的是 CPU 的画图面积，画的部分越少越好，GPU 却宁可一帧全量地重画一整批，也不想零敲碎打地伺候几十次小更新。您拿失效的省钱逻辑对着 GPU 的脾气看一看，就会发现老的控件树直接搬过去并不合算，咱们得换一棵为批而生的树。

Qt Quick 换出来的就是它。按 Qt 官方 scenegraph 文档的说法（笔者没有翻源码逐条核实，咱们认的是公开文档的表述），`QQuickItem` 在 UI 线程里组成界面的描述，渲染的时候同步成一棵 `QSGNode` 树，树上挂的是几何、变换、材质这一级的绘制单元，遍历树、把绘制命令批量提交给 GPU 的活，跑在一条独立的渲染线程上，跟 UI 线程分了家。文档还写明了它对相同材质的节点做合并提交，这正是冲着批去的。

渲染线程独立这件事咱们得单独说说，因为它换的是卡顿由哪段代码负责。您回想一下保留模式的世界：重画的活跑在 UI 线程上，界面里的哪个画得慢，输入也就跟着卡了，开篇讲消息循环的时候咱们记过它的单行道脾气。场景图把提交绘制的那一程搬去了另一条线程，UI 线程忙着改描述的时候，渲染线程照样出它的帧，两条线各忙各的。Qt 的文档把两边的同步点也写了出来，也就是渲染前那一次树的同步，其余的时刻两边谁也不等谁。当然独立也带来了新的复杂度：跨线程去看同一棵树是要出事的，所以才有两棵树加同步的形状，便宜从来都是拿复杂度换的。

细心的您可能想问：场景图里就没有失效的影子了吗？有一点，但换了住处。按 Qt 公开文档的说法，`QQuickItem` 的身上还是留着一个 `update` 方法，它标记的是这个条目需要重新同步到场景图，同步的粒度停在条目的一级，条目内部的几何与材质怎么重算，是渲染那边的事。Win32 的失效登记的是屏幕上的矩形，这里的 `update` 登记的是树上的节点，粒度和消费的人都换了。失效的思想没有消失，它只是从像素的一级挪到了树的一级，改名叫了同步。

Flutter 的形状是它的近亲。按 Flutter 官方架构文档的笔者认知，咱们的代码描述 Widget，框架把它展开成 Element 与 RenderObject 的树，渲染的那一程再合成一棵 layer tree（图层树），交给 Skia 在一条独立的 raster 线程上光栅化。

您看，树还是常驻的，这一头是跟保留模式一脉相承的，可树上挂的东西从控件降到了图层和绘制单元，重画的粒度也从失效登记变成了整帧的重新提交。Flutter 近年还在把 Skia 换成自家的 Impeller，这一层的替换咱们点到为止，架构的谱系不受它影响。

咱们把场景图跟保留模式摆到一起：留着的都是树，差别落在树里装的东西和换帧的方式上。保留模式的树挂在控件的一级，变化走的路是失效，增量是它最在乎的东西。场景图的树是绘制级的，失效的事情整个淡出了，换成了渲染线程每帧批量地提交，增量的工作如果还留着，也只做到图层的一级。代价是常驻的东西更多了：树的两头（UI 线程一份、渲染线程一份）外加中间的同步，内存和复杂度都比裸 Win32 的年代贵。

## 显示列表：录命令与回放分家

场景图的树是常驻的，每次的换帧都要重新遍历整棵树。还有一种更轻的组织方式：咱们不养树，只录命令的清单。每帧把要画的命令按顺序录成一串，录好了交给渲染的一方去回放（replay 的字面意思是重放，照着录好的清单逐条执行），录好的清单本身就是显示列表。它跟场景图的分家就落在常驻两个字上：场景图是一份常驻的结构，咱们改的是节点的属性，显示列表是一次性的清单，每帧的活都是重新录一遍。

眼下最常见的活标本是 ImGui 的 draw list，它就是显示列表在 ImGui 里的叫法。ImGui 是一个以工具界面出名的 C++ GUI 库，它的全名是 Dear ImGui，咱们马上就讲它的用法。按 ImGui 公开头文件与官方后端示例的笔者认知，每帧的界面绘制会被录进 `ImDrawList`，录进去的每一条都是 `ImDrawCmd`，它记的是一段顶点的裁剪矩形、纹理和偏移。一帧录完了，`ImGui::Render` 之后 `ImGui::GetDrawData` 交出来的是 `ImDrawData`，里面装着本帧全部的 `ImDrawList`。

接下来的活归平台后端：以官方的 DirectX 11 后端为例，它把顶点和索引都写进了 `ID3D11Buffer`，再按命令逐段地 `DrawIndexed`。您看整条流水线，ImGui 的本体只管录，回放整个交给了后端，录制与回放是分家的两半。

一条 `ImDrawCmd` 的定义里就能看出显示列表跟批的关系。后端回放的时候，一条命令对应一段顶点的提交，命令与命令之间不换纹理、不换裁剪矩形的话，相邻的段是可以合起来画的。ImGui 的官方文档说过它的 draw list 会在录制的时候做同款的合并，合出来的每一段就是一次 `DrawIndexed` 的活。您把它跟场景图一节的批对上号，就会发现两边奔的是同一个目标，只是一边靠的是渲染线程在树上攒，另一边靠的是录制端在清单里攒。

咱们再给显示列表记一条天生的性格：它记得住顺序。录制的顺序就是绘制的顺序，后录的盖住早录的，遮挡关系直接写在了清单的次序里。保留模式的遮挡靠的是树的层级，兄弟节点谁盖谁的事由 z 序决定，Win32 的重叠窗口还要靠系统裁剪来仲裁。显示列表把这件事办得特别地直白，画家算法的名字说的就是它：像画家画油画一样，远处的物件画在前面，近处的盖着画上去。您读 ImGui 的代码时不会有谁盖谁的疑问，`AddRectFilled` 调用的次序就是答案。

咱们本线上其实早就见过同款的思想，只是当时的咱们没叫它这个名字。[Skia 三件套](13_skia_surface_canvas_paint.md)里咱们说过，raster 表面上的每个 draw 调用都会当场落进像素，攒命令的事在 CPU 的表面上不存在，那是 CPU 的好消息。到了[GPU 后端](16_skia_gpu_backend.md)那边，事情就变了：Skia 在 GPU 的表面上把 `SkCanvas` 的调用录成内部的命令序列，攒着的命令由 `DirectContext` 统一冲给显卡。按 Skia 公开源码与文档的笔者认知，Skia 里另有一套正牌的录制回放叫 `SkPicture`：画的东西被录成一份可复放的 `SkRecord`，录出来的就是一份显示列表，只是住在库的内部，咱们平时不直接碰它。

Direct2D 也备了一件同款的画具。SDK 里的 `ID2D1CommandList` 就是它：您把它设成渲染目标画东西，画完的命令就被录进了列表，之后再把列表回放到真正的目标上。它是显示列表的思想在 D2D 里的官方入口，本线讲 D2D 的篇目里没有用到它，您知道有这门亲戚就好。

显示列表的力气花在哪、省在哪，咱们顺着 ImGui 的流水线看就最直白。录制的一半是纯 CPU 的活，录的环节快得很，而且录制的代码跑在咱们的线程里。回放的一半可以整个搬去渲染线程甚至 GPU 的那一侧，录制和回放就 pipeline 起来了，[动画与帧调度](34_animation_frames.md)里咱们为动画发愁的节拍问题，在这套分家的结构里天然好办，录的人和放的人各干各的。代价是每帧的重录：清单是一次性的，界面上没变的东西下一帧也得重录一遍，好在录一条命令的代价比画一遍像素低，这笔开销多数时候是划算的。

## 即时模式：没有失效这回事

前面三位再怎么换骨架，都留着一份常驻的界面描述。即时模式把这个前提整个掀了：它不常驻任何东西，每一帧都把界面的描述重来一遍，重画也是整帧的。界面的状态不在渲染层的手里，它就在您自己的变量里，画面每帧都是从变量现场重新生成的。

ImGui 的编程模型是它的教科书。咱们的代码每一帧都跑一遍界面的描述，按官方示例的笔者认知，它的骨架大致长成下面的样子（讲解用的示意，咱们没有在本仓库编译验证）：

```cpp
// Immediate-mode UI: describe the interface every frame.
// Skeleton for illustration - not compiled in this repo.
static char buf[256] = "";
static bool  shown = false;   // the state lives in your variables

ImGui::NewFrame();
ImGui::Begin("Demo");
ImGui::InputText("text", buf, sizeof(buf));
if (ImGui::Button("show")) {   // the return value IS the event
    shown = true;
}
if (shown) {
    ImGui::Text("pressed");
}
ImGui::End();
ImGui::Render();
```

您盯着这段骨架看，最容易愣住的是 `ImGui::Button` 的用法：它是一个每帧都调的函数，返回值就是点击这件事的本身。没有常驻的按钮对象，也没有 `WM_COMMAND` 那样的通知信封，事件就是一次函数调用的返回值，排队进消息队列的事在它的世界里不存在。命中测试（hit testing 的直译，判断的是鼠标点到了哪个东西身上）也整个反了过来：保留模式里是系统拿着常驻的控件几何替咱们查，即时模式里是绘制的时候记下每个东西的位置，下一帧的查询按记下的位置现算。

状态的住处也跟着换了主人，咱们拿骨架里的两个 static 摆开看。保留模式的世界里，输入框的文字是住在控件身上的，您要用 `GetWindowTextW` 去问它，框架是状态的保管员。即时模式的世界里，文字就住进了 `buf`，它是您的一个普通数组，绘制的代码每帧都读它，事件的代码每帧都写它，保管员的位置没有了。您写保留模式的代码时养成的习惯，比如从控件身上取回状态的那一步，到了即时模式里全都不需要，状态本来就是您的。

您可能纳闷：没有常驻的控件，鼠标点按的归属靠什么决定？按 ImGui 公开文档的认知，答案说的是后端替它喂：平台后端把鼠标位置、按键状态写进 `ImGuiIO` 这个结构，ImGui 每帧拿现成的输入状态跟本帧描述的界面几何对号，命中了谁，谁就是事件的得主。您对照保留模式的 `WM_COMMAND` 信封看，差别的位置只有一处：信封是系统塞进队列的，而这里的对号是每帧现算的。输入的通路没有变魔术，它只是也被塞进了每帧一遍的循环里。

现在咱们把[开篇](01_status_to_pixels.md)的老熟人请出来对照。`lstrcpynW` 拷完字符串没人失效、那行字纹丝不动的反面教材，在即时模式里连出场的资格都没有：反正每一帧都是全量重画的，改了变量，下一帧的画面就是新的，失效的事情压根不存在。开篇咱们追了一整篇的通路，失效、更新区域、`WM_PAINT` 的排队脾气，在即时模式的世界里整个都用不上。您要是被失效这件事绊过（当然您读完了本线的前几篇，多半已经不绊了），第一次写 ImGui 的时候会有一种奇怪的轻松，它就是从这里来的。

轻松的代价也得摊开看。每帧全画意味着界面静止的时候它也在烧：CPU 的录制加 GPU 的回放，一个挂在后台不动的工具窗口每帧照样全套跑一遍。您拿任务管理器看一个跑着 ImGui 的空闲界面，它的 CPU 占用通常不是零。界面小的时候这点开销无所谓，界面大了、控件上千了，每帧全量的描述本身就成了负担，ImGui 的官方文档也把大列表的裁剪当成正经的课题讲。所以即时模式在工具界面、调试面板这类个头小、变化多的场合如鱼得水，您拿它撑一个常驻的大型应用界面，就得自己想办法了。

咱们把四种架构的取舍并成一张表，您回头翻的时候对着看：

| | 保留模式 | 场景图 | 显示列表 | 即时模式 |
|:--|:--|:--|:--|:--|
| 常驻的东西 | 控件树（系统或框架的手里） | 两棵树加同步（UI 线程与渲染线程） | 每帧的命令清单，帧后即弃 | 只有您的变量 |
| 增量能力 | 强，失效的粒度可以到矩形 | 弱到图层的一级，换帧整批提交 | 无增量，整帧重录 | 无增量，整帧重画重描述 |
| 静止时的开销 | 接近零 | 渲染线程仍按帧提交 | 每帧重录，录制本身便宜 | 照样每帧全额 |
| 编程直觉 | 状态与画面分家，得记着失效 | 描述式的，改属性等结果 | 录制式的，关心顺序 | 一遍代码就是界面本身 |
| GPU 批友好度 | 差，零散的小更新最容易吃亏 | 好，为批而生 | 好，清单天然整批 | 好，整帧天然整批 |

四种架构气质的分界线在静止开销那一行。保留模式为静止优化到了极致，把记得失效的负担压给了您。即时模式把负担免了个干净，代价则是不停歇的每帧。场景图和显示列表住在中间的地带，各自把某一头的开销换成了架构自身的复杂度。您以后掂量一个框架合不合自己的用时，把表里的几行对照一遍，方向上的判断通常就不会错。

内存的视角跟咱们的直觉有点拧。您可能以为最省内存的是什么都不常驻的即时模式，其实不见得：即时模式每帧重录，录制用的顶点缓冲和命令数组得按整帧的规模备着，ImGui 的文档也写过它的内存增长跟界面规模挂钩。保留模式常驻的只是一棵控件树，控件对象本身是不大的，DWM 替咱们存着的照片才是大头，而 DWM 的开销四种架构谁都躲不掉，只要咱们的窗口还在屏幕上，DWM 的照片也就一直在。

## 本系列的 API 住在哪一层

认完了四种架构，咱们回头就能看清一件事：GDI、Direct2D、Skia、D3D 这几位咱们在本线上挨个摸过的画具，全都住在 paint 的那一层。开篇的三段分工表（layout、paint、compose）咱们还记得，架构是不住在任何一段里的，它是由这些 API 搭起来的，住在段与段之间的组织方式上，而 API 本身并不规定架构。

咱们把本线认过的画具按层归一遍位，您回头查的时候对着用：

- [HDC 与 GDI 对象模型](04_gdi_objects.md)：paint 层的画具，GDI 的命令式调用
- [工厂、设备与渲染目标](06_d2d_targets.md)：paint 层的画具，D2D 的目标与 `EndDraw` 提交
- [Surface、Canvas、Paint 三件套](13_skia_surface_canvas_paint.md)：paint 层的画具，Skia 的表面与画布
- [交换链与呈现](27_dxgi_swapchain.md)：paint 通向 compose 的交接处，`Present` 的翻页
- [DWM：重定向表面与窗口合成](30_dwm_composition.md)：compose 层的系统合成器
- [DirectComposition：visual 树](31_directcomposition.md)：应用侧伸进 compose 层的一棵树

从名单里您也看得出来，本线的篇目本来就是按层铺开的，架构的谱系并没有给它们另立门户。名单里的 DirectComposition 还多一层意思：它的 visual 树是一份常驻的、由合成器保管的描述，咱们在[动画与帧调度](34_animation_frames.md)里挂过属性动画，它其实是保留模式的思想在合成层的一次露面。同一个思想可以在不同的层里安家，这也是咱们把层分清楚的原因。

顺着谱系看咱们自己造的东西，位置也就清楚了。主线（gui 目录里从零造框架的教程线）造的骨架是保留模式：控件树常驻在咱们的进程里，属性变了自动冒泡失效，[主线第三篇](../gui/03_widget_tree.md)的树和第六篇的接线都是它的零件。它跟 Win32 的差别只在保管员换了人，控件从系统的 HWND 换成了咱们自己的 C++ 对象，架构上的谱系没有变。您以后给这套骨架接 Skia 的画具，走的就是保留模式配光栅画具的路子，跟如今 Qt Widgets 配自家 raster 引擎的配法，是同一格的。

几个真实的搭法摆在下面，您来对号。Flutter 拿 Skia 当它的画笔，在它上面搭起了 layer tree 加 raster 线程的场景图架构，咱们在场景图的一节认过了。ImGui 的本体一个像素都不画，它的后端把 draw list 交给 DirectX 或 OpenGL，显示列表的回放就落在您选的画具上。Chrome 按 Chromium 公开设计文档的笔者认知，用 Skia 承担页面的光栅化，再由自家的合成器把各个图层拼上屏，合成那一段的思路跟 DWM 是同宗的。您看，同一支画笔的上面可以搭出不同的架构，这也是咱们把画具一层一层分开讲的道理：画具认清楚了，架构的差别才看得清。

Windows 原生这一侧的分层，咱们在本篇里再对一遍，因为它正好是四种架构公共的地基。咱们进程里的代码往自己窗口的表面上画（paint），DWM 把所有窗口的表面拼成整屏（compose），这两段的边界，咱们在开篇里划清过。不管上面的框架选了哪种架构，画完的终点都是那块重定向表面，剩下的路就归了系统。

## 同一张小界面的两种循环

空口的对照不过瘾，咱们拿一张真实的小界面塞进两种循环里看。素材还是主线教程配套的 demo 程序里的三样老熟人，也就是输入框、按钮和一行自画的文字。咱们想把差别看得纯一些，所以两种循环里都自己画三样，不请系统的控件帮忙。

失效驱动的版本是咱们练了一路的路数：界面静止的时候什么也不干，状态变了才报失效。它的骨架长成下面的样子（讲解用的示意，咱们没有在本仓库编译验证）：

```cpp
// Retained-style loop: draw only when something changed.
// Skeleton for illustration - not compiled in this repo.

// State change: update the variable, then register the dirty area.
void on_button_clicked(HWND hwnd) {
    wcscpy_s(g_line_text, g_edit_buffer);
    InvalidateRect(hwnd, &g_line_rect, FALSE);   // only this line repaints
}

// The paint handler draws everything that intersects rcPaint.
case WM_PAINT: {
    PAINTSTRUCT ps{};
    HDC hdc = BeginPaint(hwnd, &ps);
    if (IntersectRect(&overlap, &ps.rcPaint, &edit_rect))   draw_edit(hdc);
    if (IntersectRect(&overlap, &ps.rcPaint, &button_rect)) draw_button(hdc);
    if (IntersectRect(&overlap, &ps.rcPaint, &line_rect))   draw_line(hdc);
    EndPaint(hwnd, &ps);
    return 0;
}
```

每帧全画的版本把消息循环整个换了形状，也就是[Skia 实战篇](18_skia_win32_loop.md)里用过的同款循环：咱们排空消息，然后无条件地画一整帧（讲解用的示意，咱们同样没有编译过它）：

```cpp
// Per-frame full redraw loop: describe and draw the whole UI every frame.
// Skeleton for illustration - not compiled in this repo.
bool running = true;
while (running) {
    MSG msg;
    while (PeekMessageW(&msg, nullptr, 0, 0, PM_REMOVE)) {
        if (msg.message == WM_QUIT) { running = false; break; }
        TranslateMessage(&msg);
        DispatchMessageW(&msg);
    }
    if (!running) break;   // quit skips the final frame
    draw_edit(frame_canvas);    // every frame, changed or not
    draw_button(frame_canvas);
    draw_line(frame_canvas);
    present(frame_canvas);
}
```

两个循环里画三样东西的活是一样的，咱们把它也写成骨架，您看一眼“自己画的三控件”到底长什么样（讲解用的示意，咱们没有在本仓库编译验证）：

```cpp
// The three widgets drawn by hand - skeleton, not compiled in this repo.
// State: plain globals, one HWND for the whole window, none per widget.
static wchar_t g_edit_buffer[256] = L"";
static wchar_t g_line_text[256]   = L"";
static bool    g_button_hover     = false;

void draw_widgets(HDC dc) {
    // The "edit": a white box with a sunken border, the buffer's text inside.
    RECT edit_box{20, 20, 420, 48};
    FillRect(dc, &edit_box, (HBRUSH)GetStockObject(WHITE_BRUSH));
    DrawEdge(dc, &edit_box, BDR_SUNKENINNER, BF_RECT);
    SetBkMode(dc, TRANSPARENT);
    DrawTextW(dc, g_edit_buffer, -1, &edit_box,
              DT_LEFT | DT_SINGLELINE | DT_VCENTER);

    // The "button": a raised box; hover state comes from the frame's input.
    RECT button_box{20, 56, 140, 92};
    DrawEdge(dc, &button_box, g_button_hover ? BDR_RAISEDINNER : BDR_RAISEDOUTER,
             BF_RECT);
    DrawTextW(dc, L"show", -1, &button_box,
              DT_CENTER | DT_SINGLELINE | DT_VCENTER);

    // The "line": one row of text below.
    RECT line_box{20, 100, 420, 128};
    DrawTextW(dc, g_line_text, -1, &line_box,
              DT_LEFT | DT_SINGLELINE | DT_VCENTER);
}
```

这段骨架里没有一个 HWND 是属于控件的，输入框是一个矩形加一行的字，按钮是另一个矩形加悬停的描边，状态的住处全是全局变量。您把它跟[主线第一篇](../gui/01_naked_win32.md)那个真有 HWND 的版本摆在一起，三样东西的像素可以长得一模一样，底下住着的架构却换了两家。键盘的文字怎么进 `g_edit_buffer`、悬停怎么更新，咱们没有写，那是输入通路的活，您拿咱们在即时模式一节说的 `ImGuiIO` 思路自己也能补上。

咱们把两个骨架并排读一遍。头一个版本的循环里，静止的界面上消息循环空转，CPU 的占用贴着零，您敲一下按钮，走的通路是改变量、报失效、等队列空闲、画一小块，这正是开篇里咱们追过的同一条路。失效和 `WM_PAINT` 在第二个版本里都不见了，每帧照单全画的是输入框、按钮和文字三样，`WM_QUIT` 之外的消息爱来不来，画面更新的节奏跟消息的多少无关。您要是给第二个版本接上[动画与帧调度](34_animation_frames.md)的高分辨率定时器，它就离一个 ImGui 式工具的骨架不远了，差距剩下的那一截，是把绘制录成 draw list 交给 GPU 回放的活。

两个骨架还照出了一件事：即时模式并不是拿 Win32 的零件拼不出来的。上面这个每帧全画的版本，用的全是本线里教过的 API，它就是一套手搓的迷你即时模式。反过来的说法也成立：ImGui 在 Windows 上跑的时候，底下踩的还是消息循环加交换链的那一套，它只是把架构的取舍换到了另一头。您亲手把两个循环各写一遍，体感上得到的东西会比读十篇对照都多。

调试的体感两边也差着脾气。失效驱动的循环出了画面问题，您查的是失效报没报、报大了还是报小了，查的全是登记那一头。每帧全画的循环出了问题，查的是描述本身，某一帧画错了，下一帧重画就自己修好了，闪烁类的中间态在整帧合成的写法里连出现的机会都没有。您以后接手别人的界面代码，看一眼循环的形状，排查的思路就定了。

真实的程序还有第三种样子，免得对照表把您框死：两种循环可以在同一个窗口里分区域地混。工具软件里常见的形状是一个保留模式的常规界面，中间嵌一块每帧全画的画布，图表、预览一类的活区域就归了画布管，按钮和菜单归保留的那一套管。咱们本线的[实战篇](18_skia_win32_loop.md)搭的循环其实就是它的雏形：Win32 的窗口和消息循环照旧，中间的画布每帧重画一遍。混搭的代价在边界上，鼠标的命中、键盘的焦点到了交界处要谁来接，得咱们自己写清楚，两边各管各的管不到对方的地盘。

## 您可以动手看的一处

您开一个记事本，再开任何一个用 ImGui 搭界面的工具（很多图形工具和调试器都是），您让两个窗口都静止地放着，然后拿任务管理器看它们的 CPU 占用。记事本走的是保留模式，静止时的占用贴着零，省钱的正是失效的增量机制。ImGui 的工具每帧都在描述加重画，占用通常停在一个小而不为零的数上，这就是每帧全画的开销。两边的数字您各记一笔，本篇对照表的静止开销那一行，就算您亲眼验过了。

要是您还想看得更深一点，咱们就请[屏幕、帧与垂直同步](02_screen_frame_vsync.md)介绍过、[动画与帧调度](34_animation_frames.md)里用过的 PresentMon 出场：把 ImGui 工具的呈现事件录上十秒，您多半会看到间隔排成整齐的一串，静止的时候也在按帧出。记事本那边走的是 GDI 的重定向，它自己是不调 `Present` 的，在 PresentMon 里能不能录到呈现事件、录到的话归在谁的名下，您不妨亲手试一试。
