# 性能观测：PIX、RenderDoc、ETW

[架构对照](35_render_architectures.md)（下文咱们简称 35 篇）的结尾咱们预告过本篇：四种架构各有各的代价，代价怎么量、每一帧的开销落在哪一段，得请观测的工具出场。咱们把主张立在最前面：卡了别猜，咱们动手去量。猜测的方向总是偏向自己最熟的那几行代码，量出来的方向才值得信。另一个好消息咱们也交代在开头：本线（您正在读的渲染教程线）的篇目到这里全部成了稿，正文里的链接指向的都是真实的文件，您从任何一处跳回去复查都走得通。

本篇请出场的一共五位。PresentMon 已经在[交换链与呈现](27_dxgi_swapchain.md)（下文咱们简称 27 篇）里首演过，PIX 与 RenderDoc 这回是新到的面孔，ETW（Windows 内核级的事件跟踪设施，全名后文展开）连着它的可视化搭档 WPA，外加咱们自制的轻量打点。五位各管的是一摊：有的管一次 Present 隔了多少毫秒，有的管整个系统的调度，一帧之内每次绘制写了什么，又另是一路的活。管的内容差得这么远，挑选的门道就只有一句话，把症状认对了再挑工具。咱们从分诊开始。

自制打点住在本进程的代码里，量的是自己干的活。站在进程边界上看呈现链路的是 PresentMon。站在整个系统上空的是 ETW 与 WPA。PIX 与 RenderDoc 的走法不同，它们走的是纵向的路，纵向地剖开一帧，把帧里的每次绘制摊给咱们看。横着看时间的三位管节奏，纵着切帧的两位管内容，分诊表里咱们按症状挑就行。

## 分诊：症状认对了，工具才挑得对

同样是嘴里的一句“卡”，底下可能藏着完全不同的病。[屏幕、帧与垂直同步](02_screen_frame_vsync.md)（下文咱们简称 02 篇）里，咱们把症状的词汇一个个立过，现在咱们正好回收它：卡顿与掉帧说的是屏幕到点取不到新内容，撕裂说的是直写路径上换了页，输入延迟说的是排在前面的帧太多，按键到发光的路被拉长了。这些病的共同点是节奏错了，它们的观测入口是时间线。花屏、颜色错乱、画面缺块则是另一类的病，它们的节奏没毛病，错的是内容，观测的入口是截帧：把一帧原样冻了下来，看它的内部。

症状与入口的对应整理成下表，您排查的时候回来翻：

| 症状 | 头一个入口 | 它在看什么 |
|:---|:---|:---|
| 卡顿、掉帧、帧率下台阶 | PresentMon 的帧间隔 | 相邻两次 Present 之间隔了多少毫秒 |
| 输入延迟高、手感变肉 | PresentMon 的延迟列，配 27 篇的队列闸门 | 从提交到上屏、从点击到发光的路程 |
| 撕裂 | PresentMon 的 PresentMode | 哪条路径在直写屏幕 |
| 花屏、颜色错、画面缺块 | RenderDoc 或 PIX 的 GPU capture | 一帧之内每次绘制写了什么 |
| 帧内某段慢、GPU 各阶段耗时 | PIX 的 timing capture | 管线各阶段各吃了多少时间 |
| 整个系统都卡、别的窗口拖累 | WPR 录制、WPA 分析 | 系统级的事件与调度 |
| 自家 demo 的日常健康 | 自制打点 | 帧的耗时与失效的次数 |

表里的行不用背，咱们记规律就够了：

- 节奏类的病，看的是时间线。
- 内容类的病，看的是截帧。
- 系统级的病，看的是 ETW。
- 自己代码的健康，靠的是打点。

02 篇立过的“两座钟”模型（程序的钟与屏幕的钟）您要是还留着，节奏类的病说的全是钟没对上。

症状的描述也值得说两句，因为它是分诊的原料。“拖动窗口的时候一顿一顿”就是一条好的症状，它带了触发条件与观感。“就是有点卡”却是一条坏的症状，它锁定不了任何东西。咱们把什么时候卡、卡多久、谁一出现就卡这三样问出来，工具的选择往往就已经定了。同一个现场拿几件工具交叉取证也是家常的事，入口总从最对口的那件开始就好。

还有一句提醒值得放在最前面：观测的本身也是开销，仪器开着的时候，被量的东西就变了样。PresentMon 录十秒的干扰很小，WPA 录全系统的干扰不小，RenderDoc 截帧的干扰最直观，被截的程序当场就顿给您看。咱们读到什么数字，都得想起来它是在哪台仪器的注视下产生的，这一句在重开销的那几节里都会回来。

## PresentMon 的时序视角：把一排事件读成一条时间线

PresentMon 的来历与拿法，27 篇都交代过了：它是 Intel 开源的，靠订阅 ETW 的事件拼出呈现链路，控制台的版本要提着权跑。CSV 字段的清单咱们不重念，本篇补的是读法：CSV 里的每一行对应一次 Present，行本身就按时间排好了序，咱们把它当时间线读，它就开始说话了。

头一个要破的迷信是平均值。咱们拿一组明摆着编的数字当教具：十一次 Present 带来十个间隔，九个都隔了 16.7 毫秒，剩下一个隔了 100 毫秒。平均下来的数是 25 毫秒出头，帧率的数字看着体面，您的眼睛看到的却是规律出现的大磕绊（这段教具合计约 250 毫秒，同样的节奏一秒能塞下四段），因为感官对尖刺的敏感，远超它对平均值的敏感。所以咱们读的是分布，而不是平均值：把 `MsBetweenPresents` 这一列排好了序，最大值与长尾的那几行就是卡顿的现场。您在 Excel 里排个序，一分钟也就够了。

排序之后怎么读，也定个顺手的样子：最大值咱们单独看，它是最坏的那一帧。长尾咱们看个数，超过两倍中位数的行占了多少成，卡顿的频率就从这里估。中位数的脾气比平均值稳，一两个尖刺拖不歪它的位置。三个数在 Excel 里都是现成的函数，脚本的写法也就十几行的事。

台阶的病在分布里也有自己的长相。02 篇的定点班车比喻咱们还记得：错了一班就得整个周期地等下一班，帧率从 60 踩到 30 的台阶就是这么来的。落到 CSV 上的时候，`MsBetweenPresents` 会离开 16.7 毫秒的一堆，搬到 33.3 毫秒那里另起了一堆，两堆的中间没有几行。咱们做的是纯算术，数字教具都是编的，但真录出台阶的分布，长的就是这个双堆的样子。

02 篇的两座钟，在 CSV 里咱们能认领一座。程序的那座钟就是 `MsBetweenPresents` 的倒数（27 篇给过算法）。屏幕的那一座，刷新率的设置值 CSV 里没有，咱们做环境记录的时候记下它。显示侧的节奏另有 `MsBetweenDisplayChange` 一类的列可以看。

第二个读法讲的是配对。咱们把 `MsUntilDisplayed` 跟间隔放在一起看：间隔均匀、上屏却慢半拍的现场，27 篇的机制直接给了方向，排队的帧太多。那一篇讲过的默认三帧上限、`SetMaximumFrameLatency` 的闸门、`DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` 换到手里的手柄，对照着 `MsUntilDisplayed` 的大数看，机制和数据就互为证据了。从点击算起的 `MsClickToPhotonLatency` 也住在同一张表里，手感类的问题它最有发言权。

延迟的列咱们再提防一句：02 篇交代过口径的事，输入延迟是跟着刷新率、排队深度与程序的工作量走的，量法各家有各家的口径。`MsClickToPhotonLatency` 给出的是 PresentMon 口径下的数，咱们拿它跟别人的数字比之前，口径的事得对齐。

`SyncInterval` 这一列咱们还能再用一个用场。27 篇讲过 2 到 4 的档位是主动挑低帧率的省电档，视频播放器一类的程序会拿它把帧率的顶压到内容自身的节奏。您接手一个陌生的程序，CSV 里 SyncInterval 列清一色地写着 2 的话，它多半是人家设计好的档位。咱们读数字的时候，要对得上程序设计的意图，同样的分法咱们在分诊一节已经给过。

第三个读法看的是变化。`PresentMode` 是按帧记的，咱们把一列从头读下来，中途变档的时刻自己会显出来：窗口模式里跑着 `Composed: Flip` 的链，它在某个时刻掉到了 `Composed: Copy` 一档，多半是有 GDI 互操作一类的窗口掺了进来，27 篇的判读表里，Composed 开头带 Copy 的两档，说的正是它的样子。

`SyncInterval` 还能跟咱们代码里的调用参数核对：程序递给 `Present` 的值与系统实际走的路径，两边写在了同一行里，谁也含糊不了。

至于 Present 调用自身的耗时，27 篇引过的 README 提醒过，字段是随版本有增减的，您手上是哪个版本、时长类列叫什么名字，以随仓库的 README 为准。这一列要是长起来了，27 篇给的机制就对上了：队列排满的时候，Present 的调用会就地阻塞，调用本身的耗时就是这么涨上去的。

全屏的判定也是 PresentMode 顺手的事。27 篇的全屏一节拿它判过真假独占，`Hardware: Legacy` 开头的档位说的才是程序真正接管了屏幕，`Hardware` 家族里的 Independent Flip 两档（含 `Hardware Composed: Independent Flip`）是全屏优化的直通，屏幕的所有权还在系统的手里。您给自己的程序按一次全屏，录的时候看档位换没换，27 篇的判定您就亲手过了一遍，比背下来的判读表记得牢。

CSV 的行数本身也在说话。消息驱动的程序没活就不画，录出的行稀稀拉拉，循环驱动的程序每圈都交帧，行排得密密的一串。27 篇的练习里，咱们预告过一件事：裸 demo 录出来的 CSV 几乎是空的。裸 demo 说的就是 gui 主线第一篇[具象 · 脱掉封装，把窗口立起来](../gui/01_naked_win32.md)那个消息驱动的最小窗口。您真去录的时候，看到的正是这幅稀疏的样子。所以咱们拿到一份 CSV，头一眼扫的就是行数与密度：程序到底出了多少帧，这个最粗的事实它一秒就交代了。

录制的开关，咱们在 27 篇记过两个：`--hotkey` 与 `--etl_file`。`--hotkey` 让您用组合键遥控开始与停止，现场不好重现的卡顿，等它出现了再录也来得及。`--etl_file` 让 PresentMon 直接吃录好的 etl 文件，本篇的 ETW 一节还会回到它身上。

录多久也是实际的问题。27 篇的实验给的都是十秒，看尖刺的分布已经够用。偶发的卡顿十秒里未必碰得上，那咱们就请 `--hotkey` 常驻着等它。录到几分钟的长度，行数也就是帧率乘秒数的量级，Excel 的行数上限完全够用。这道算术咱们心算就行。

咱们兑现 35 篇留的一个活。它请您拿 PresentMon 录静止的记事本，看呈现的事件录不录得着。机制上咱们能推个大概：PresentMon 订阅的是 D3D 与 DXGI 运行时的事件，老式的记事本走的是 GDI 的重定向，从头到尾是一次 Present 都不发的，按进程名过滤的时候，CSV 十有八九是空的。Windows 11 起系统自带的记事本换成了新实现，呈现走的是合成的路数，您动手录之前，把记事本的版本认清楚。DWM 替整个桌面合成的那次呈现挂在谁的名下，咱们没有验证过，不替您下断语。您录上十秒就有答案，录到了什么就记下什么，推完机制再拿数据核对的顺序，您别让它倒过来。

PresentMon 也有它的边界。它看到的是进程与系统交接的那一圈：Present 提交了没有，隔了多久，上了屏没有。咱们再往里走，一帧之内 CPU 花在哪一步、GPU 的哪个阶段吃了时间，它就看不见了。往里的世界归截帧与 timing 的工具，PIX 与 RenderDoc 的摊子在后面两节。

## PIX：微软自家的 D3D 观测套件

PIX on Windows 是微软自家的调试套件，管的是 DirectX。安装的入口在 PIX 主页（[devblogs.microsoft.com/pix](https://devblogs.microsoft.com/pix/)）的 Download 页，您用 winget 装（`winget install microsoft.pix`）也一样，文档与各版本说明咱们也到主页上去找。它是围着 D3D12 建的，支持范围的口径以官方页为准。本线的 demo 正好两路都有：D3D 段的示例踩的是 D3D11，[实战：Win32 窗口跑 Skia 渲染循环](18_skia_win32_loop.md)（下文咱们简称 18 篇）的 Skia demo 底下踩的是 D3D12，您拿着 18 篇这一路 demo，PIX 恰恰是原生对口的一家。所以 PIX 咱们认它两样看家的本事，再外带认一位它的亲戚。

头一样看家的是 GPU capture，干的就是抓一帧。它把一次完整呈现之间发生的一切原样冻住，存成了文件，之后您在界面里逐个 draw call 检视。draw call 咱们在[GPU 管线](23_gpu_pipeline.md)（下文咱们简称 23 篇）里认过的是 `Draw` 这个调用，draw call 说的就是它：一次把顶点送进管线的调用。您停在某一个 draw call 上，管线状态面板里摆着的就是那一篇讲的各阶段现场：顶点着色器与像素着色器绑的谁，渲染的目标视图是哪块，混合状态是怎么设的。资源的内容、某个像素的历史，您在界面里也都能点开，查花屏的路数跟 RenderDoc 是同宗的，咱们到下一节一并细看。

逐 draw call 检视的用处，咱们拿 23 篇的站点串一遍就具体了。管线状态面板里的每一页，对应的就是那一篇走过的站：输入装配的布局，顶点着色器绑的资源，光栅化的视口，像素着色器的采样器，输出混合的状态。咱们在代码里设过一遍的东西，PIX 原样地替咱们抄在面板上，哪一页跟您想的不一样，哪一页就值得您怀疑。

GPU capture 打开之后的走法，咱们按说明性的路子过一遍：左边的事件列表看的是全景，一帧里有多少次绘制、顺序长什么样，心里有了数。咱们在中间点住一个 draw call，右边的管线状态就换成它的现场。咱们在资源的页签里点开纹理，看到的是那一次绘制眼里的内容。哪个环节有了嫌疑，咱们就停在哪个环节，翻页的速度跟咱们读代码的速度是一个量级的。

第二样看家的是 timing capture。GPU capture 冻的是一帧的静态现场，timing capture 量的则是一段时间里 GPU 的耗时分布：哪些 draw call 贵、管线的哪一段吃时间，在时间线上咱们一眼就能挑出来。“感觉帧慢”到了它这里就成了有名字的事，贵的那一段有了名字与毫秒。两样 capture 是前后脚的搭档：timing 挑出贵的那段，咱们再切回 GPU capture 去截同类帧，查它贵的原因。

timing capture 与 PresentMon 的分工，咱们划一句话的界：PresentMon 站在进程的边界，量的是帧与帧之间的节奏。timing capture 钻进一帧的里面，量的是 GPU 干活的花销。一个管的是“隔多久交一帧”，一个管的是“一帧里谁吃掉了时间”。咱们把两份数据拼起来，“慢”才有了完整的坐标：慢的是节奏还是内容，查一下就知道了。

亲戚的名字是 System Monitor。27 篇引过的 PresentMon README 里，有一张在它之上搭起来的工具名单，微软 PIX 的 System Monitor 就在名单里：微软把 PresentMon 收了进去，做了自家的系统监视器，咱们不开控制台也能看帧率与呈现。工具的谱系到这里就全了，咱们从下往上数：底下发事件的是 ETW，中间拼呈现链路的是 PresentMon，上面把 D3D 的调试整套端给咱们的是 PIX。下一节的 RenderDoc 不在上面的谱系里，它是另立门户的，正好把 D3D11 与别的 API 的位置补上。

工具名单上的生态也值得看一眼。27 篇引过的名单里，搭在它之上的不止 PIX 一家，一串工具都把它当地基。底下的事件流是同一份，上层的皮各穿各的，咱们认得底座，换一张皮就不怵了。

## RenderDoc：开源的截帧工具

RenderDoc 是开源的图形调试器，许可证挂的是 MIT，源码住在 GitHub 的 [baldurk/renderdoc](https://github.com/baldurk/renderdoc) 名下，它把 D3D、Vulkan 与 OpenGL 全都包了。它跟 PIX 的分工，咱们一句话能说清：PIX 是微软给 D3D12 配的正牌工具，深度与系统侧的观测是它的强项。RenderDoc 是社区给主流图形 API 配的截帧工具，画面取证的本领两家都有，路线各走各的。

用法咱们按一次截帧走。装好了之后，咱们把目标程序交给它启动（界面上叫 Launch Application），等程序跑起来了，咱们按热键截下当前帧，默认的热键是 F12，您在设置里也能改。帧会存成 `.rdc` 的文件，之后咱们重新打开慢慢查。截帧的时候程序照常在跑，所以您可以等到症状出现的那一刻再按键，专门冻住出事的那一帧。

查的时候三样看家本领挨个认。事件浏览器把一帧里的每次绘制按执行顺序列成一串，您从上往下走，就等于跟着 GPU 把整帧重放了一遍。管线状态面板跟 PIX 的同款，逐 draw call 看各阶段的绑定。最对口花屏的是像素历史（pixel history）：纹理查看器里点中一个可疑的像素，它把这个像素在这一帧里被每一次绘制写过的值列出来，哪一次写入把它写坏的，前后一对比就现了形。画面缺块、颜色发疯一类的病，多数走不到第三步就已经招了。

网格查看器（Mesh Viewer）管的是顶点那一头：它把 GPU 眼里的顶点画出来，着色前与着色后的各一份，线框的模式也能切。模型的形状不对、顶点的变换出了错的时候，2D 的画面说不清的事，咱们到它这里一眼就看清了。

截帧对付不了节奏的病，原因咱们说清。花屏是内容错了，冻住出事的那一帧，错的写法就留在了里面，截帧是它对口的路数。卡顿的每一帧内容却都是对的，错的是帧与帧之间的间隔，冻哪一帧都冻不出它的影子。所以分诊表把卡顿指给 PresentMon，把花屏指给了截帧。

它跟咱们本线的画具之间还隔着一层关系，咱们把它交代清楚。[特效：Effect 图](11_d2d_effects.md)（下文咱们简称 11 篇）搭过的 D2D 交换链，底下踩的是 D3D11。18 篇的 Skia GPU 循环，底下踩的是 D3D12。RenderDoc 挂住的是 API 那一层，这两边的帧它都录得下来，录下的命令各自是 D3D11 与 D3D12 一级的。Skia 与 D2D 的调用落到 GPU 命令的时候，早就翻成了 D3D 的说法，所以您在时间线里看到的绘制命令是 D3D 的名字，纹理与缓冲也是底下那层的句柄。上层画具的抽象丢了，换回来的是管线级的全部细节，查硬件行为的时候，这样的交换是划算的。能看多细的事，您拿 18 篇的 demo 截一次就有数了。

`.rdc` 文件还有一层协作上的好处：它自己是自足的，截帧需要的资源跟命令都在里面，您把文件发给同事，他打开看到的跟您看到的一模一样。花屏的现场经常难以重现，一份能复放的截帧，比一段口头的描述值钱得多。

27 篇教过复现撕裂的三件套，咱们把它跟本篇接上：撕裂只在直写的路径上才有资格发生，而 `PresentMode` 判的正是路径。复现的实验配上观测才算落了地，光看画面的缝，咱们说不出它走的是哪条路。

截帧的开销也提一句实在的：截的那一下，程序当场就顿了一下，这是把整帧的资源与状态搬进文件要付的代价。所以量帧的时候别截帧，截帧的时候别下帧率的判断，咱们也别让两台仪器同时压一个现场。您按一次热键，存下的就是一份文件，连按几下存下的就是连着几帧的几份，间歇的病拿它抓个正着。

## ETW 与 WPA：把整个系统的活动摊开

ETW 的名字 27 篇带过一次，咱们回收一下：它的全名是 Event Tracing for Windows，也就是 Windows 内核级的事件跟踪设施，D3D 与 DXGI 的运行时干活的时候，会往外发它们的事件。PresentMon 只是事件流的消费方之一，同一条流里还有别的源头：显卡驱动内核的那一层（行话叫 DxgKrnl），DWM 一类的系统组件，发的事件也不少。前面几位工具看的都是咱们自己的进程，病根要是出在进程的外面，咱们就得直接去挖事件流的源头，本节的两位就是干这个的。

ETW 的事件是按提供方分组的，咱们把这个词也认了：provider（提供方）说的是往事件流里发事件的那一方，D3D 的运行时是一家，DxgKrnl 是单独的一家，DWM 也是单独的一家。WPA 的图表就是按这些提供方与主题组织的，您认得名字，图表的标题就不陌生。

录制与分析的两步，咱们交给分开的两个工具。录的工具是 Windows Performance Recorder（WPR），它把一段时间的系统事件写进 `.etl` 文件。看的工具是 Windows Performance Analyzer（WPA），它把 etl 里的几万行事件画成时间线的图。两者的分发随 Windows ADK 走，ADK 展开的全文是 Windows 评估和部署工具包，具体的口径以微软的文档为准。录系统级的跟踪同样要提权，道理与 27 篇说的相同：ETW 会话不是随便哪个进程都能开的。

什么活轮到它们？WPA 的强项是把整个系统摊开：哪个进程抢了 GPU 的带宽，DWM 的合成忙不忙，CPU 那边的调度挤不挤，一张时间线里全对齐了。自家进程用 PresentMon 量得干干净净、画面却还是卡的现场，病根多半在进程的外头，那就是 WPA 的主场。代价咱们也直说：录制的会话本身有开销，界面的门槛也高，图表的种类有几十种，咱们头一次打开它的时候容易迷路。所以咱们把它排在排查流程的末位，轻工具啃不动了再请它。

DWM 的卡怎么在 WPA 里看，咱们拿 [DWM：重定向表面与窗口合成](30_dwm_composition.md)（下文咱们简称 30 篇）的机制对一句：每个窗口的画面都存在重定向表面里，DWM 按刷新的节拍把它们拼成整屏。窗口叠的层数一多、透明与模糊用得重的时候，合成的那一段活就重，GPU 的图形里 DWM 忙起来的痕迹就看得到了。本进程的帧时间线干干净净、整个桌面却在掉帧的现场，查的就是它的头。

录制的时长咱们也给个顺手的量：抓眼下的卡顿，几分钟也就够了。录上一下午的 etl 又大又难开，分析的耐心比仪器的耐心耗得更快。

WPA 的入口咱们指一条道：etl 打开之后，从图形浏览器里把 GPU Usage 的图调出来，GPU 的占用与各进程的分摊就有了全景，咱们再顺着嫌疑往别的图里钻。全认完那些图是不现实的，咱们按嫌疑查图，认两三种常看的就够本篇的用了。

两边还有一座现成的桥。27 篇列过的 `--etl_file` 开关，让 PresentMon 直接吃录好的 etl 出 CSV。所以 WPA 里看到 GPU 侧有嫌疑的时候，咱们把同一份 etl 再喂给 PresentMon，就换回一条呈现的时间线，也就不用回去重录现场了。

## 自制打点：demo 的自检路子

前面四位说的都是正经仪器，仪器有仪器的成本：提权、录文件、开界面慢慢地分析，一样都省不了。咱们自己写的 demo 缺的其实是一枚常驻的体温计，咱们不指望它查得多细，只求异常的时候它能自己叫出声。05 篇教过同款思路的东西：把脏区涂上了颜色，让系统的判断自己站到屏幕上，仪器的出处是[失效、脏区与重绘](05_invalidation_dirty_region.md)（下文咱们简称 05 篇）。本节的打点量的也是两样最要紧的数：一帧耗了多久，失效发生了多少次。

计时的这一头有粗细两把尺。`GetTickCount64` 返回自系统启动以来的毫秒数，帧前帧后各取一次、相减就是一帧的毫秒，它的好处是随手就能用。糙的地方也在毫秒：60 Hz 屏幕上一帧的预算只有约 16.7 毫秒，抖动常常就藏进了毫秒之内，所以咱们正经量帧，用的是 `QueryPerformanceCounter`，它读的是高精度计数器，配 `QueryPerformanceFrequency` 把计数的差换算成秒。骨架长成下面的样子（讲解用的示意，咱们没有在本仓库编译验证）：

```cpp
// A tiny frame-time probe: high-resolution timer, batched print.
// Skeleton for illustration - not compiled in this repo.
static LARGE_INTEGER g_qpc_frequency{};
static LARGE_INTEGER g_frame_start{};

void frame_begin() {
    if (g_qpc_frequency.QuadPart == 0) {
        QueryPerformanceFrequency(&g_qpc_frequency);
    }
    QueryPerformanceCounter(&g_frame_start);
}

void frame_end() {
    LARGE_INTEGER now{};
    QueryPerformanceCounter(&now);
    const double ms = (now.QuadPart - g_frame_start.QuadPart) * 1000.0 /
                      static_cast<double>(g_qpc_frequency.QuadPart);
    // accumulate ms into a one-second window, then report
    // min / avg / max once per second - never per frame
}
```

打印的事千万别按帧做。控制台与调试输出的 I/O 本身就不便宜，每帧打印等于拿仪器污染了测量，尖刺反而被测量的动作抹掉了。咱们攒满了一秒，再报出最小、平均与最大的一组，长尾的那几笔才看得见。报的方式随您挑：控制台的 printf、`OutputDebugStringW` 送进调试器的输出窗口，都是现成的口子。

计数的骨架更短，咱们直接看（讲解用的示意，它同样没经过本仓库的编译验证）：

```cpp
// A WM_PAINT activity counter: accumulate, report once per second.
// Skeleton for illustration - not compiled in this repo.
static unsigned  g_paint_count   = 0;
static ULONGLONG g_report_tick   = 0;

case WM_PAINT: {
    PAINTSTRUCT ps{};
    HDC hdc = BeginPaint(hwnd, &ps);
    // ... the usual drawing ...
    EndPaint(hwnd, &ps);

    ++g_paint_count;
    const ULONGLONG now = GetTickCount64();
    if (now - g_report_tick >= 1000) {
        // printf or OutputDebugStringW: how many paints this second
        g_paint_count = 0;
        g_report_tick = now;
    }
    return 0;
}
```

代码里两位时钟各干各的，咱们给它们分了工：QPC 管的是量帧，因为帧的抖动藏在毫秒以内，`GetTickCount64` 管的是按秒打印，因为打印的节拍用不着那么细。一细一粗的搭配不是随意的，仪器的精度配仪器的活，配错了要么浪费、要么看不清。

计数跟 05 篇的涂色仪器是一对搭档：涂色给您看的是脏区的形状，计数给您看的是脏区的频率。形状对、频率不对的时候，病就藏在调用的那一头，咱们该去查的是谁在疯狂地报失效。

咱们把两个数合起来读，判读的路子就全了：帧的耗时正常、失效的计数爆表，病在画得太勤的这一头，05 篇的重绘风暴就是它的原型。帧的耗时爆表、计数正常，病在单帧太贵的那一头，该请截帧的工具进场了。两个数都正常的时候，画面却还是卡的，活就交到进程的外头，轮到 PresentMon 与 WPA 出场了。

性能的数字离开环境就没有意义，咱们把记录的习惯也立下：机器的配置、显示器的刷新率、窗口的尺寸、Debug 还是 Release 的构建，四样都跟着数字记了下来。同一份 demo 在 60 Hz 与 144 Hz 的屏幕上是两份答案，混在一起比就比出了冤案。您翻回 02 篇看一眼两座钟，就知道刷新率为什么排在头一排了。

打点的输出咱们也留个档：控制台的输出重定向进文件，或者 `OutputDebugStringW` 的内容在调试器里存成日志，事后再跟 PresentMon 的 CSV 对时间。两边的时钟各有各的刻度，绝对的时刻默认对不上，要对齐就拿 PresentMon 的 `--qpc_time` 一类的开关。它把每帧的时刻输出成性能计数器值，跟咱们打点用的 `QueryPerformanceCounter` 读的是同一座钟。不对接绝对时刻的时候，卡顿发生的相对位置也对得上，哪一段的尖刺两边都有，嫌疑就重了一半。

打点的能力边界，咱们也交代清楚：它量不到 Present 之后的世界。翻页、排队、合成与上屏的这些环节，要么发生在调用的深处，要么干脆发生在别的进程里，那是 PresentMon 与 WPA 的地盘。打点管的是咱们的代码为一帧干了多久。

## 一趟排查：从“感觉卡”到“落在某一关”

咱们把前面的工具串成一条路走一遍。场景设成说明性的例子：您给 18 篇的 demo 加了动画，拖着窗口走的时候画面一顿一顿。流程走的只是说明的路数，数字咱们一个不编，每一步写的是看什么、按什么分岔。

起手为什么是 PresentMon？咱们看中的是便宜：它只读边界的事件、不进程序的内部，十秒就交出了答卷。便宜的仪器回答便宜的问题，而“病在不在我的进程里”就是最便宜也最要紧的问题，答错了方向，后面的力气就全白花了。

1. 录现场。PresentMon 按进程名录上十秒，录的当口咱们故意拖着窗口走，把症状喂给仪器。
2. 判路径。`PresentMode` 这一列负责认路：停在 `Composed: Flip`，路径没毛病。掉到 `Composed: Copy` 一档的话，回头去查交换链与 GDI 的互操作，27 篇的判读表就是为此备的。
3. 判节奏。`MsBetweenPresents` 排序看分布：尖刺只出现在拖动的时刻，说明一帧的活干不完。间隔均匀、`MsUntilDisplayed` 却大的话，方向转去 27 篇的队列闸门，排队的那一段病就落在它身上。
4. 进程内定位。尖刺确认了，打点量渲染循环一帧的耗时，把慢锁在具体的某几帧。再请 RenderDoc 截下慢的那一帧，数绘制命令、看资源的尺寸，PIX 的 timing capture 则把贵的那段管线直接挑出来。走哪条岔看您手上是哪一路程序：这一趟排查走的 18 篇 demo 是 D3D12 的，RenderDoc 与 PIX 两条都通。您以后接手纯 D3D11 的程序，走 RenderDoc 顺当，PIX 的 GPU 侧观测按官方口径要 D3D12。
5. 出进程。进程内查得干干净净、画面还是卡的话，WPR 录一段 etl 交给 WPA，看系统级的调度：DWM、别的进程、CPU 的挤压，病根在自家进程之外的时候，它是唯一的现场。

排查的路也可以倒着走，从工具的发现退回机制的篇目：PresentMode 掉进 Copy 的档，咱们回 27 篇查互操作。timing 认出了贵的是像素着色器，咱们回[着色器与常量缓冲](26_d3d11_shaders.md)看代码。WPA 说 DWM 的合成忙，咱们回 30 篇数自己叠的层。工具给的是坐标，篇目给的是地图，咱们把两头合起来，下一步的动作才有了着落。

流程的心法只有一句：每一步回答的只是一个问题，答完了再花下一份力气。反过来最费的走法是一上来就录全系统的跟踪，在几万行的事件里捞一根针，捞不着的时候，咱们还不知道该不该捞。
