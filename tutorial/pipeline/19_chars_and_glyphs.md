# 字符、码点与字形

按[篇目索引](index.md)的登记，本篇开的是文本段的头一篇。Skia 的一段收在[《实战：Win32 窗口跑 Skia 渲染循环》](18_skia_win32_loop.md)。咱们再往后数，段里接着排着的[《DirectWrite：TextLayout 全解》](21_directwrite_layout.md)，跟压轴的[《测量、命中测试与光标》](22_text_metrics.md)，把文本的一段收齐。

本篇要补的其实是一处旧欠。[《Skia 的文本：SkFont 与 TextBlob》](15_skia_text.md)的 glyph 一节里，字符的编号怎么来的，当时咱们留给了本篇。整形器凭什么把字符换成字形，留给了后面的《整形》一篇。主线用一句话就能摆开：文字的世界里住着三样东西，存进内存与文件的东西叫字符，字符在名册上的编号叫码点，屏幕上画出来的图形叫字形。三样东西咱们平时随口混着叫，渲染管线却拿它们干着三份不同的活，混叫的代价到了 emoji 与光标移动的地方就会显形。

为什么渲染的教程要花一整篇讲编号？因为后面每一层的难处都从这里挂上去。Skia 那边量宽收的是字节，Win32 这边 API 吃的是单元，字体的 `cmap` 查的是码点，光标挪的是字素簇，哪一层的单位数错了，哪一层出的就是乱子，而乱子还不报错，非得画到屏幕上咱们才看得见。咱们把单位一份一份认清，后头的整形与排版才有地基建。

## 名册与编号：码点是什么

咱们从最抽象的一头看起。字符是文字世界里被人类认下来的一件东西，字节与图形都不归它管：您写下“中”的时候，落笔的是一个字符，您写下问号的时候，落笔的还是一个字符，表情里的笑脸也是同样的一员。字符本身没有什么样子，也没有什么大小，它认的只是“这是谁”，“长什么样”的事是不归它管的。字符拿到了编号，咱们才能在机器里搬动它们，干这件活的国际标准叫 Unicode，咱们把它想成一本巨大的名册就好：每个字符在册子里占的是一行，行首印着的就是它的编号。

编号的行话叫码点（code point），记法是 U+ 加上十六进制的编号，“中”的码点是 U+4E2D，问号的码点是 U+003F。编号是从 U+0000 起编的，一直编到了 U+10FFFF 才封顶，而一百一十多万个位置，眼下的册子还远没有住满。习惯上咱们还把编号分段叫平面：U+0000 到 U+FFFF 的头一段叫基本多文种平面，咱们平时说的 BMP 指的就是它，常用的汉字、字母与符号都住在这一段里。U+10000 往上的段住的是生僻字与一大批 emoji，代理对的麻烦正是从它们身上来的，咱们把这件事留到编码的一节再展开。

## Windows 手里的宽字符

咱们要把编号存进内存，就得有装它的容器。Windows 选的容器叫宽字符，类型就是您熟悉的 `wchar_t`，在 Windows 上它的宽度是 16 位，装的是 UTF-16 编码的一个单元。书架（也就是 `tutorial/native_win32/` 目录下那套带完整示例的老教程）的[窗口基础章](../native_win32/0_ProgrammingGUI_Basic.md)把这段历史讲过一遍：Unicode 诞生之前 Windows 用的是 ANSI 编码，西文的代码页一个字符一个字节，中日韩的代码页一个字符要两个字节，后来要支持多语言才引入了宽字符，函数名上 A 与 W 两套后缀就是新旧两条路留下的痕迹。内部其实 W 系才是原生的一侧，A 系的入口反倒要转成宽字符才能干活。

咱们在[裸窗口一篇](../gui/01_naked_win32.md)里写的 `RegisterClassExW`、`CreateWindowExW`、`DrawTextW`，全都是 W 系的调用，吃的就是 UTF-16 的宽字符串。也正因为走了 W 系的路，那里按钮上的 `L"显示"` 与 STATIC 标签里的中文，才能不经转换地直接显示出来。有一处跨平台的差异值得您记在心上：C++ 的标准并没有把 `wchar_t` 定死成 16 位，Linux 那边的它是 32 位，习惯直接装 UTF-32 的码点，同一段处理宽字符的代码搬到别的平台，行为就可能悄悄地变样。

## 变长的两套记法：UTF-8 与 UTF-16

码点要写成字节才算存了下来，把码点写成字节的办法叫编码。咱们常用的编码有两套，脾气各是各的。

咱们把界线画清：码点说的只是编号，下文的两套说的都是记法。

UTF-8 的单位是字节。编号小的字符占一个字节，ASCII 的全体都住在这档里，常用的汉字占三个字节，U+10000 以上的字符占四个字节，一个字符占几个字节要看编号的大小，所以行话叫变长编码。Skia 那边的字符串走的就是这套，咱们在[《Skia 的文本》](15_skia_text.md)里数过汉字的三个字节，也提过字节数说的跟字符数不是一回事。

UTF-16 的单位是 16 位的单元，也就是咱们熟悉的 `wchar_t`。BMP 里的字符咱们一个单元就装下了，“中”的 0x4E2D 原样躺进去就好。可一个单元撑死了也就数到 0xFFFF，U+10000 以上的字符怎么装？编码的设计者想了个借位的办法：拿两个单元拼起来用，拼出来的东西就叫代理对（surrogate pair）。

文件里存的 UTF-16 还带着一桩小事：一个单元占的是两个字节，就有哪个字节排在头里的讲究，Windows 的内存里走的是低字节在前的 LE 记法，文件头的 BOM（字节序标记）说的就是本文件按哪头存。咱们在内存里处理 `wchar_t` 的时候不用管它，真从文件里读宽字符的时候，头上的 BOM 要不要剥掉就得自己拿主意了。

## 代理对：一个 emoji 占两个 wchar_t

借位的办法靠的是专门划出来的空地。UTF-16 的编号空间里划出了两块：0xD800 到 0xDBFF 的一块叫高代理，0xDC00 到 0xDFFF 的一块叫低代理，两块地在 BMP 的正经字符里是空着的，解析器见到了高代理，就知道它跟后面的单元是一对。咱们把一对单元还原成码点的算式摆出来：咱们用 0x10000 打底，加上（高代理减 0xD800）乘以 0x400 的积，再加上（低代理减 0xDC00）的那一项。

乘数 0x400 值得咱们多看一眼：它就是 2 的 10 次方，高代理贡献的是 10 位，低代理贡献的还是 10 位，两个 10 位摞起来的容量是一百多万个位置，加上 0x10000 的底正好盖住到 U+10FFFF 的全部编号，多出来的一格都不浪费。咱们认清它的结构就好：每个代理背着 10 位的货，拼起来才是完整的码点。

咱们拿笑脸 emoji 亲算一遍。它的码点是 U+1F600，减去了 0x10000 剩下 0xF600，高 10 位给出的是 0x3D，加上 0xD800 得到的是 0xD83D，低 10 位给出的则是 0x200，加上 0xDC00 就得到了 0xDE00。所以它在 UTF-16 里的样子，就是 0xD83D 与 0xDE00 连着的两个单元。`wcslen` 数到它会数出来的是二，可用户眼里的它却是一个字，字符串长度与字符数对不上的来处就是它。

书架的[DirectWrite 排印章](../native_win32/32_ProgrammingGUI_Graphics_DirectWrite_Typography.md)在 `DWRITE_TEXT_RANGE` 的地方提醒过同一件事。`DWRITE_TEXT_RANGE` 是 DirectWrite 里拿来圈样式范围的参数对，记的是起点加长度。它的 position 数的是 UTF-16 的单元，代理对占的是两个 position，您给含 emoji 的文字算样式区间时得把它数进去，不然的话，样式会从半个字的中间劈开。GDI 那边同款的心眼也在：书架的[GDI 文本一章](../native_win32/21_ProgrammingGUI_NativeWindows_GDI_Text.md)强调过 `TextOutW` 的 `cchString` 数的是 `wchar_t` 的个数，按字节算就错了，从 ANSI 迁移过来的代码最容易在这里数错单位。

## 示例：亲手把码点一个个走出来

咱们不空口下断言，写一段最短的程序，拿眼睛看一遍代理对长什么样。程序的活儿只有一件：从头到尾地走完一个宽字符串，每走一步把当前的码点连同它占的单元数打印出来，代理对的解析咱们不请任何帮手，上一节的算式咱们原样摆了进去：

```cpp
#include <cstdio>

// Walk a UTF-16 string one code point at a time. Each step prints
// the code point and how many wchar_t units it occupies. No library
// helpers: the surrogate math is spelled out on purpose.
void DumpCodePoints(const wchar_t* text) {
    for (size_t i = 0; text[i] != L'\0';) {
        unsigned int code  = static_cast<unsigned int>(text[i]);
        unsigned int units = 1;

        const bool kIsHigh = code >= 0xD800 && code <= 0xDBFF;
        const unsigned int kNext = static_cast<unsigned int>(text[i + 1]);
        if (kIsHigh && kNext >= 0xDC00 && kNext <= 0xDFFF) {
            code  = 0x10000 + ((code - 0xD800) << 10) + (kNext - 0xDC00);
            units = 2;
        }

        std::wprintf(L"U+%04X  (%u wchar_t)\n", code, units);
        i += units;
    }
}
```

循环的骨架就是一遍普通的遍历，讲究却全在步进的功夫上：遇到代理对的时候 `i` 一次跨两个单元，其余的时候跨一个。判断的条件咱们分开来念：当前单元落在了高代理区里，而后一个单元落在低代理区里，两样同时成立了才算成对，只对一半的字符串（比如数据被截断了），咱们的两样判断就凑不成对，单个的高代理会被当成一个独立码点交出去，咱们在这里选了宽容而不报错的处置。

咱们手写的两个区间判断，SDK 里其实备着官方的拼法。`winnls.h` 里定义的 `IS_HIGH_SURROGATE`、`IS_LOW_SURROGATE` 与 `IS_SURROGATE_PAIR` 干的就是同样的范围检查，宏名是笔者凭记忆写下的，您以手头 `winnls.h` 的声明为准。示例里咱们仍然摆手写的区间，为的是把两块区域的编号摆在您眼前，真写工程代码时换用官方的宏更稳当，意图是一样的，拼写的事交给了 SDK。

咱们把入口也摆上，总共要写的只有三行：

```cpp
#include <cwchar>  // std::wcslen

int main() {
    const wchar_t* kDemo = L"中a😀";
    std::wprintf(L"wcslen = %zu\n", std::wcslen(kDemo));
    DumpCodePoints(kDemo);
    return 0;
}
```

本节的代码是笔者按接口含义写的骨架，没有经过编译的验证，下面的输出是咱们按算式亲手推出来的预期，您把它贴进任意一个控制台工程跑一遍，对得上就说明路子走对了：

```text
wcslen = 4
U+4E2D  (1 wchar_t)
U+0061  (1 wchar_t)
U+1F600  (2 wchar_t)
```

`wcslen` 报的是 4，可码点报出来的只有 3 个，差出来的就是笑脸 emoji 占掉的第二个单元。还有一处工程上的小事咱们交代一下：`wprintf` 打印的全是十六进制与数字，宽字符本身的显示咱们没有碰，控制台的代码页也就进不了这个示例，您真要往控制台打汉字与 emoji，那就是另一个话题了。

还有一处源码层面的小事值得交代：示例的字面量 `L"中a😀"` 依赖编译器按对的编码读源文件，MSVC 的默认行为是跟着系统代码页走，源文件存成带 BOM 的 UTF-8 或 UTF-16，或者给编译器传 `/utf-8` 的开关，字面量里的汉字与 emoji 才进得了程序。您要是发现程序里的字面量变成了问号，查的就是编码的这一环。

咱们再把循环的脚步排成表，您对着上面的输出看一遍，步进的路数就清楚了：

| 循环变量 i | text[i] 的值 | 它落在哪儿 | 还原出的码点 |
|:--:|:--:|:--|:--|
| 0 | 0x4E2D | BMP 的常规区 | U+4E2D |
| 1 | 0x0061 | BMP 的常规区 | U+0061 |
| 2 | 0xD83D | 高代理区 | U+1F600（连同 i = 3 一起） |
| 3 | 0xDE00 | 低代理区 | 被上一对捎走了 |

i 走到 2 的时候凑成了一对，一次跨到了 4，咱们看下标 3，它自己没有单独的身份，跟着前面的高代理一起走的路。表格里最值得咱们看的是末行：单元还在字符串里占着它的位置，可它的身份已经不归“一个字符”的计数管了。

## 换算的桥：MultiByteToWideChar

两套编码住进了同一个工程，换算就是躲不开的活。网络与配置文件那边流行的是 UTF-8，Win32 的 W 系 API 吃的却是宽字符，中间的桥就是 `MultiByteToWideChar`，反方向走的桥则是 `WideCharToMultiByte`。咱们看正方向的两步走法：

```cpp
#include <vector>

const char* utf8 = "汉字a";

// First call: ask how many wchar_t the conversion needs.
const int kWideLength = MultiByteToWideChar(
    CP_UTF8, 0, utf8, -1, nullptr, 0);
if (kWideLength == 0) {
    return 1;  // conversion failed, GetLastError() has the reason
}

// Second call: do the actual conversion into a right-sized buffer.
std::vector<wchar_t> wide(static_cast<size_t>(kWideLength));
MultiByteToWideChar(CP_UTF8, 0, utf8, -1, wide.data(), kWideLength);
```

咱们第一次调用传的是空缓冲，它还给咱们的却是目标缓冲该有的长度，而第二次调用干的才是真正的活，两步的走法问的是大小、取的是数据，正是 Win32 里的惯用套路。头一个参数 `CP_UTF8` 说的是源字符串按 UTF-8 读，末位的 -1 表示源串以空字符结尾，这时返回的长度把结尾的空字符也算在里面，咱们的缓冲也就不差最后一个格子。返回 0 的含义是转换失败，失败的原因就记在 `GetLastError()` 里，传进去的字符串要是带着非法字节，它走的就是失败的退路。

本节的代码同样是没有编译过的骨架，笔者按 SDK 文档的参数含义落笔，您接进工程时以编译器与运行的结果为准。书架的[GDI 文本一章](../native_win32/21_ProgrammingGUI_NativeWindows_GDI_Text.md)里有同款的包装，包装的函数名就叫 `Utf8ToUtf16`，咱们借来对一眼更放心。

## 字形：字体自家的编号与 cmap 查表

码点认完了，咱们转到屏幕那头。真正被画出来的东西叫字形（glyph），它是字体文件里存着的一个个图形，笔画、轮廓与留白都定死在了字形里。咱们把同一份文案换个字体，它就换了一副长相，变的正是字形：码点 U+4E2D 说的只是“中这个字”，微软雅黑给它的字形跟宋体的字形，笔画的粗细与转角全不一样。

咱们顺带认一个数：一款字体里 glyph 的总数，通常比它覆盖的字符数还多，连字与上下文的变体长着各自的图形，却谁也不对应一个独立的字符。所以查表的方向永远是码点找 glyph，反过来的路是没有的，单个的 glyph 说不上自己代表哪个字符。

字体内部还有自家的一套编号，行话里给它起的名字叫 glyph ID，管的是“一款字体里的第几个图形”。咱们要从码点走到 glyph ID，靠的是字体文件里自带的一张映射表，表的名字就叫 `cmap`，您把它读成“字符码查字形号”的表就好。[《Skia 的文本》](15_skia_text.md)里咱们说过 `drawString` 内部干的就是这个查表：`drawString` 把字符串收了下来，就拿着 typeface 的 `cmap` 逐个查号，查出来的 glyph ID 序列才是绘制管线真正吃的东西。`DrawTextW` 那样的系统调用把查表整个包进了黑盒，可黑盒里干的还是同一件事。

## 一与多的错位

一对一的查表在咱们中国字这边大体够用，可文字系统的世界比这大得多，码点与字形的对应关系会朝两头错开。

朝一头错的是多个码点画成一个形。在英文的排印里，f 与 i 相邻的时候，字体常把两者合成了一个连字字形，笔画也连在了一起，两个码点换来的是一个 glyph ID。更极端的例子在 emoji 的组合序列里：Unicode 里有个叫零宽连接符的字符（zero-width joiner），它的码点是 U+200D，它自己占的宽度是零，干的活就是告诉排版引擎，把我两边的字符连成了一个整体。三个成员拼出来的家庭 emoji（比如 👨‍👩‍👧）是三个成员字符加两根连接符的组合：它的码点有 5 个，折算成 `wchar_t` 的单元有 8 个（三个成员占的是三对代理，而两根连接符各占一个单元），屏幕上显示的却是一个抱团的小家庭。Unicode 里另有单码点的家庭 emoji 👪（U+1F46A），不走拼的路。

咱们再来看旗帜 emoji，它用的又是另一副拼法。它靠的是一对区域指示符，比如中国国旗用的是 U+1F1E8 与 U+1F1F3，两个码点各占的是一对代理，合起来占的是 4 个单元，屏幕上画的却是一面旗。这里没有连接符的戏份，配对的本身就是约定，两个指示符挨在了一起，排版引擎交付的就是一面旗。

emoji 的组合里还活跃着一类叫变体选择符的字符，常用的 U+FE0F（variation selector-16）自己也不占宽度，专门给前面的字符点菜：跟在心形后面的时候，要的就是彩色 emoji 的长相，不带它的时候有些平台画的是纯文本符号。它给码点序列又添了一种零宽的成员，咱们算字素簇的时候，边界也就跟着更纠缠了。

朝另一头错的是一个码点画成多个形。阿拉伯文的字母连写，要看前后的邻居去挑字形，同一个码点走到词头、词中或词尾的时候，长相就各是各的。变音符号的脾气又是第三种：法语里的 é 可以用单个码点 U+00E9 存，也可以写成 e 加组合尖音符的样子（U+0065 加 U+0301），后一种存法的两个码点在屏幕上叠成一个字。把这些错位全处理对的工序叫整形（shaping），本系列给它留了《整形：连字、kerning、BiDi》的专篇，咱们到那边再一寸一寸展开。

## 字素簇：用户眼里的一个字

错位攒得多了，就会逼出一个新的概念。用户感知的“一个字”，行话里给它起的名字叫字素簇（grapheme cluster）：它对应的东西可能是一个码点，也可能是基字符带了一串组合符号，也可能是整段 ZWJ 拼出来的家庭 emoji。光标的移动、退格的删除、鼠标的拖选，用户的预期全都落在了字素簇上，您也不会指望按一下方向键就跨过半个家庭。

同一副长相的不同存法，还有正规化的工序管着：`NFC` 把“e 加重音”并成的是单个码点，`NFD` 还原成的则是组合对。咱们知道有这道工序就好，真要比较字符串相等的时候再请它出场，编辑器保存文档的时候选哪一头，各家的做法也不一样，笔者不替它们背书。

咱们按 `wchar_t` 的单元去删，后果咱们能推出来：光标停在家庭 emoji 的中间，退格按一次砍掉的是一个单元，也就是半个成员的量，屏幕上剩下的会是一个残缺的组合，运气差的时候干脆显示成一个猜不出的方框。EDIT 一类的系统控件里，按簇移动的活已经有人替咱们代劳了，覆盖的范围笔者没有逐个控件逐个版本验证过，您要是自绘编辑器或者自己管光标，这摊活就落到了自己头上。Windows 上现成的分析帮手有 DirectWrite 的字簇分析。跨平台的常客是 ICU（International Components for Unicode，一套跨平台的 Unicode 处理库）的 BreakIterator，它的字符边界模式干的正是按字素簇切分的活。具体的接法咱们留到《测量、命中测试与光标》一篇再展开。

## 同一个字符串的四种数法

咱们要数的单元、字节、码点与字素簇，四个数说的经常不是一回事，咱们拿三个字符串把它们排开，您对着机制亲手数一遍：

| 字符串 | 单元数（wcslen） | 字节数（UTF-16 口径） | 码点数 | 字素簇数 |
|:--|:--:|:--:|:--:|:--:|
| L"中a😀" | 4 | 8 | 3 | 3 |
| 家庭 emoji 全串 | 8 | 16 | 5 | 1 |
| é 的两码点存法 | 2 | 4 | 2 | 1 |

字节数那一列说的是 UTF-16 的口径，单元乘二就是缓冲实际占的地方。家庭 emoji 那一行最见落差：缓冲里躺着的是 16 个字节，用户眼里的它却是一家人。咱们写代码的时候，心里得盘算的其实是接口要哪个数，四个数配错了不报错，咱们要等画到屏幕上才看得见错位。

缓冲的字节数咱们也别数错地方：`wide.size()` 报的是单元数，乘上 `sizeof(wchar_t)` 得到的才是字节数，两个数在咱们眼里差着一倍。咱们把单元数组直接塞给要字节数的接口，编译器是拦不住的，错的量级又恰好像一串正常的字符数，排查的时候也就格外费眼。

## 三样东西在 GUI 里的分工

三样东西咱们都认齐了，把它们放回 GUI 的现场，看看它们各自管的是哪一摊。

咱们挨层看下去。存储与协议的这一层按码点走：文件里存的、剪贴板上递的、网络上送的，装的全是编码成了字节的码点序列，UTF-8 与 UTF-16 争的只是记法，编号本身用的还是同一本名册。到了绘制的那一层，管线末梢要的就换成 glyph ID 序列了，`cmap` 与整形器干的都是从码点到字形的换算。编辑的那一层最贴着用户，光标、选区与退格到了这里就只认字素簇，单元和码点帮不上咱们的忙。

这套分工也解释了旧代码里的一类迷惑：同样打着“处理文字”旗号的不同库，给的单位却不一样，咱们拿着单元数去喂要码点数的库，或者把方向倒了过来，表面上倒是都能跑通，算出来的选中范围却悄悄偏了一两个。咱们把每一层的单位喊准，这类偏移在写代码的时候就能对上是哪一层数错了单位。

剪贴板是分工的好标本。咱们往剪贴板上放文本的时候，登记的格式是 `CF_UNICODETEXT`，交出去的就是宽字符的 UTF-16，粘贴进任何一家程序的时候都不用猜代码页。书架的[拖放一章](../native_win32/56_ProgrammingGUI_NativeWindows_DragDrop.md)里取文件路径走的也是宽字符的格式，存储按码点走的路数，在这些协议的口子上看得最清楚。

分工为什么值得咱们记下？因为前面各篇里见过的每一层，现在都能挂进咱们摆好的分工图里。[第一篇《从状态到像素》](01_status_to_pixels.md)的 `DrawTextW` 把三层全包了，宽字符串递了进去，屏幕上字就出来了，代价是咱们说了不算中间的任何一步。[《Skia 的文本》](15_skia_text.md)把绘制的那层还给了咱们：它的文字接口带一种 `kGlyphID` 的输入模式，告诉 Skia 把咱们传进来的整数序列直接当 glyph ID 解释，码点查表那一步就省掉了，这个口子等着整形后的序列进来。本篇认下的是头一层与第二层的地基，接在后面的下一篇《整形》管的正是中间那段换算，再往后的《DirectWrite：TextLayout 全解》一篇，会给咱们看一套把三层全管起来的系统排版对象。

## 动手清单

下面几处动手的活儿，原料取的全是本篇现成的代码与书架的示例，您改起来都不出几行：

1. 把示例的文案换成您的名字加一个 emoji，跑一遍，数一数 `wcslen` 与码点数的差值，再跟组合变音符号比一比，看看两类错位各差多少。
2. 把笑脸 emoji 换成家庭 emoji 再跑一遍，`wcslen` 会报 8，码点会报 5，亲眼看过一遍，单元与码点的换算也就忘不掉了。
3. 用 `MessageBoxW` 弹一个含 emoji 的宽字符串，标题栏与消息体用的字体不一样，对 emoji 的支持也不同，缺字形时系统会挑别的字体顶上，顶不上时您看到的是方框还是问号，值得亲眼看一次。
4. 给 `DumpCodePoints` 加一个统计字素簇的粗略版：组合符号（U+0300 到 U+036F）并进前一个码点，ZWJ 连着的成员并成一簇，家庭 emoji 上数出来的应该是 1。
5. 把一段 UTF-8 的汉字串用 `MultiByteToWideChar` 转成宽字符再喂给示例，转换的包装在书架的[GDI 文本一章](../native_win32/21_ProgrammingGUI_NativeWindows_GDI_Text.md)里有现成的写法，字节与单元两套单位的换算就串起来了。
6. 故意把示例字符串从中间截断，让高代理落在末尾丢了伴儿，看看宽容处置交出来的东西，再想想严格的版本该怎么报错。
7. 把 `MultiByteToWideChar` 的两步复制进示例，用“汉字a”试一遍，再把源串换成带 emoji 的 UTF-8，转换后的单元数您口算一遍，再拿 `wcslen` 对答案。
8. 用 `WideCharToMultiByte` 把宽字符转回 UTF-8，数一数汉字与 emoji 各占的字节，跟本篇讲的 3 个与 4 个对上号。
9. 拿 `winnls.h` 的官方宏替换示例里手写的两个区间判断，替换前后各跑一遍，输出对得上，就说明宏的语义没记错。

## 本篇的术语速查

这些词咱们后面每一篇都要用，咱们把它们集中列一份，您忘了的时候回来查：

| 术语 | 一句话的意思 |
|:--|:--|
| 字符 | 文字世界里被认下来的一件东西，只管“这是谁” |
| 码点 | 名册上的编号，U+ 加十六进制，从 U+0000 到 U+10FFFF |
| BMP | 基本多文种平面，U+0000 到 U+FFFF 的头一段 |
| 编码 | 把码点写成字节的办法，UTF-8 与 UTF-16 是常用的两套 |
| 单元 | UTF-16 的 16 位容器，Windows 上就是一个 `wchar_t` |
| 代理对 | U+10000 以上的字符借两个单元装自己的办法 |
| 高代理 / 低代理 | 0xD800–0xDBFF 与 0xDC00–0xDFFF 的两块空地 |
| 字形 | 字体文件里存的图形，屏幕上真正画出来的东西 |
| glyph ID | 字体内部给字形编的号，管线的口粮 |
| cmap | 字体里码点查 glyph ID 的映射表 |
| 整形 | 把码点序列变成正确字形序列的工序，连字与 BiDi 都归它 |
| ZWJ | 零宽连接符 U+200D，把两边的字符连成一个整体 |
| 变体选择符 | U+FE0E / U+FE0F，给前面的字符点文本或彩色的长相 |
| 字素簇 | 用户感知的“一个字”，光标与删除的计量单位 |

## 自查几问

您读到这里，下面几个问题应该都能凭本篇的机制答上来，答不上的那一段值得您回去再看一遍。

1. 字符、码点、字形三样东西，各自回答的是“这是谁”“编号多少”“长什么样”里的哪一件？
2. “中”的码点是多少，记法上的 U+ 说的又是什么？
3. Windows 上的 `wchar_t` 是几位，装的是哪套编码的什么单位？
4. UTF-8 与 UTF-16 的变长，各自的单位是什么，“常用汉字占三个字节”说的是哪一套？
5. U+10000 以上的字符在 UTF-16 里靠什么装下，两块代理区的编号范围各是多少？
6. 笑脸 emoji 在 UTF-16 里的两个单元各是多少，还原码点的算式怎么写？
7. `wcslen`、码点数、字形数、字素簇数，四个数在什么情况下会各不相同？
8. `cmap` 是字体里的什么表，`drawString` 内部拿它干了什么？
9. fi 连字与家庭 emoji，各是朝哪个方向的一与多错位？
10. 光标移动与退格按什么单位算，按 `wchar_t` 删家庭 emoji 会看到什么？
11. `DWRITE_TEXT_RANGE` 的 position 数的是什么单位，含 emoji 的样式区间要当心什么？
12. `TextOutW` 的 `cchString` 数的是字节还是单元，迁移代码在这里犯的通常是什么错？
13. `MultiByteToWideChar` 的两步各干的什么活，源串长度传 -1 会让返回值多算什么？
14. 家庭 emoji 全串的单元数、字节数、码点数、字素簇数各是多少？
15. 咱们手写的判断之外，SDK 在哪个头文件里备着代理判断的官方宏？
16. 为什么乘的数是 0x400，两个代理各贡献几位，合起来盖住多大的范围？
17. UTF-16 的文件头为什么要放 BOM，它在内存里的时候咱们为什么不用管？

## 下一步

字素簇的一头咱们欠着光标与命中测试的展开，另一头整形的活也该开工了。咱们的下一篇是[《整形：连字、kerning、BiDi》](20_shaping.md)，它会把码点序列变成字形序列的那段换算摊开讲：连字怎么挑，字距怎么调，从右往左的文字怎么跟从左往右的混排。本篇讲的 `cmap` 干的只是码点到字形的一对一查表，把错位全摆平的完整工序是整形。`SkShaper` 与 HarfBuzz 的名字咱们在[《Skia 的文本》](15_skia_text.md)里见过一眼，咱们到那边才算正式认识。整形认完了，`kGlyphID` 的口子就有粮可喂，《DirectWrite：TextLayout 全解》那套把三样东西全管起来的排版对象，也才有足够的地基去认。

字素簇的欠条之外，DirectWrite 的一线也等着跟咱们碰头。按登记《DirectWrite：TextLayout 全解》排在整形篇的后面，它那边的 TextLayout 把度量、命中与样式全收在一个对象里，本篇的 `DWRITE_TEXT_RANGE` 只是从它身上露出来的一角。咱们把编号认扎实，到时候认的就是整套的排版对象。
