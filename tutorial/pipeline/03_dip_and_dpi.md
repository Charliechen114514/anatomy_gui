# 坐标、DIP 与 DPI

咱们把 `gui_naked`（主线第一篇[裸窗口 demo](../gui/01_naked_win32.md)搭出来的那个程序）的窗口，拖到一台 250% 缩放的显示器上，看到的现场挺有意思：窗口在跨屏的一瞬间自己大了一圈，文字照样是清楚的，输入框也跟着变宽了，只有那个按钮还维持着原来的个头，在变宽的窗口里显得小了一号。而就在同一秒钟里，咱们看见了三样表现：糊没来、窗口没缩、按钮没跟上。它们的背后是三套机制在各干各的活。上一篇[屏幕、帧与垂直同步](02_screen_frame_vsync.md)结尾留的正是同一个问题：屏幕的物理像素，和程序里用的逻辑单位，为什么不是一回事？本篇咱们就把它接过来：三种像素各自指的是什么，而系统按什么规则在它们之间换算，换算的责任谁扛哪一段。

## 屏幕只认点，程序只写数

咱们从屏幕这一头看起。面板上的每一个小方格都能独立发光，这样的一个方格就是一个物理像素，一块 3840×2160 的面板，物理像素的数目足有八百多万个。它们是硬件那头的东西，咱们在程序代码里摸不到，而代码里能写的只是数，从数到点的中间隔着一层换算，本篇要讲的也就是这一层换算。

程序那头的数住在 Win32 的坐标里。您调 `CreateWindowExW` 时传进去的 720 和 480，还有 `GetClientRect` 拿回来的宽和高，全都是这一层的数。它们的名字叫逻辑像素（也叫逻辑坐标），名字里的逻辑两个字提醒的就是您：这个数未必一比一对应屏幕上的点。而比例是几比几，咱们得看下一位主人公的脸色。

下一位主人公的名字叫 DPI（dots per inch、每英寸点数）。96 是整个体系的基准：Windows 约定 96 DPI 的屏幕上一英寸铺 96 个点，缩放 100% 对应的是 96，150% 对应的是 144，250% 对应的是 240。您在显示设置里拨的是百分比，程序收到的是 DPI 值，两者的换算其实就一句，拿物理像素 = 逻辑像素 × DPI ÷ 96 来算就行了。咱们拿一个 120 逻辑像素宽的按钮放到 250% 的屏上算一遍，120 × 240 ÷ 96 的得数是 300，它要占的物理像素就是 300 个，看起来才能和 100% 屏上的一样大。

咱们在 DIP（device-independent pixel，设备无关像素）身上看到的，是同一思想在别的 API 里的名字。Direct2D、DirectWrite、WPF、WinUI 这些后来者把以 96 为基准的逻辑单位定成了正式单位，坐标用的是浮点数，1 DIP 名义上的长度是 1/96 英寸。您在 96 DPI 的屏上，一个 DIP 占住的恰好是一个物理像素，到了 240 DPI 的屏上，一个 DIP 得摊到的是 2.5 个物理像素。等到咱们讲 Direct2D 的那一篇时，满眼的浮点坐标全是 DIP，您到时候回来看这一句就够了。

您也许想问，咱们为什么要隔出两层单位，放着好好的像素不用。因为屏幕的点密度不归程序管，而且也不统一，各家的密度还不一样。同样是 27 寸的屏，1080p 面板的一英寸约 81 个点，4K 面板的一英寸却有约 163 个。按钮的宽度要是直接按物理像素写死 120，它在 4K 屏上就显得只有隔壁 1080p 屏上的一半大。逻辑单位把看起来多大、点了多少个点拆成了两件事，观感的一头归程序和用户约定，数目的另一头交给系统按 DPI 换算，两边各管各的。

## 系统眼里的三档程序

咱们写的程序得告诉系统自己会不会做这套换算。Windows 按声明的有无和强弱，把进程分成了几档，咱们挨个看系统对各档做了什么。分档这件事本身就是历史包袱的形状：几十年里写下的程序都默认活在 96 DPI 的世界里，而系统想推进高分屏，但是又不能让老程序集体报废，只好把会不会换算做成了一张问卷，按答卷分了档来伺候。

什么都不声明的程序是 DPI-unaware（无 DPI 感知）。它眼里的全世界都是 96 DPI，画的每一个逻辑像素都当物理像素交出去。但是系统不忍心看它在高分屏上小成蚂蚁，就把它的画面当成一张位图整体拉伸到应有的尺寸。文字和直线的边缘在这个拉伸里被揉花，这就是老程序在新屏幕上发虚的来处。咱们掂这个代价：糊换回来的是界面尺寸还算正常，对不打算改造的老程序，这算一个能用的默认值。

咱们再往上一档走，遇到的就是 system DPI aware（系统级感知）。您不挪窝，它一切正常：程序在启动时问一次主显示器的 DPI，此后布局用的都是它。窗口一旦拖到另一块缩放不同的屏上，手里那个 DPI 就过时了，系统只好又回到拉伸的老路，糊也就跟着回来了。一个值用到了头的做法，就是这一档的天花板。

最讲究的一档是 per-monitor DPI aware（每显示器感知），引进它的是 Windows 8.1。程序要是声明了自己盯得住每一块屏，系统的拉伸就停了，改成在窗口跨屏、DPI 变化的时刻发一条 `WM_DPICHANGED` 消息，把调整的活儿交还给程序。到了 Windows 10 1703，这一档又升级成了 PerMonitorV2：子窗口也收到了通知，非客户区（标题栏、边框、菜单这些系统替您画的部分）自动按新 DPI 缩放，连对话框也自动处理了。而第一版里的这些活儿全得程序自己扛。

| 档位 | 程序以为的世界 | 系统实际的做法 |
|:---|:---|:---|
| unaware | 所有屏都是 96 DPI | 画面整体位图拉伸，清晰度受损 |
| system aware | 全按启动时主屏的 DPI | 换屏后照样拉伸 |
| per-monitor V1 | 窗口所在屏的 DPI | 不拉伸，顶层窗口收到 WM_DPICHANGED |
| PerMonitorV2 | 窗口所在屏的 DPI | 顶层和子窗口都收到通知，非客户区与对话框自动缩放 |

表里的四档您留着，本篇后面咱们还会反复回到它。而声明写在哪里，就是下一节的事了。

在咱们进 manifest 之前，还得排掉两个常见的误会，它们都跟档位表有直接的关系。

头一个误会：DPI 是屏幕的物理属性，出厂就定死了。在程序的视角里其实不是。程序拿到的 DPI 来自显示设置里的缩放倍数，就算一块 4K 屏放的是 100% 缩放，系统报回去的照样是 96。物理点密度只决定的，是推荐缩放给您的默认值，报给程序的数跟物理密度可以差得很远。所以您别拿 DPI 值去反推面板规格，反推的路是不通的。

第二个误会：manifest 里声明了感知，适配就算做完了。对咱们自己摆在客户区里的控件来说，声明换来的其实只有“不被拉伸”这一项而已，尺寸的换算、字体、位图资源还都得程序自己来。主线 demo（就是开头那个 `gui_naked`）的按钮是现成的反例：声明是齐全的，咱们却没换算尺寸常数，它到了高分屏上就缩水了。还有位图资源怎么按 DPI 挑尺寸版本的问题，咱们本篇不展开。咱们要是想知道图标为什么得在一份文件里装下多个尺寸，书架（`tutorial/native_win32/` 目录下那套带完整示例代码的老教程）的[图标与位图一章](../native_win32/14_ProgrammingGUI_NativeWindows_IconCursorBitmap.md)讲过，您只要知道“资源也要挑档”就够了。

## manifest：档位声明在文件里

DPI 感知的档位声明在哪里？主线 demo 的答案是 manifest（应用清单），demo 的代码里找不到它。manifest 是随 exe 一起走的一份 XML 文件，程序依赖哪些系统组件、用的是什么兼容性设置，都写在了里面，而系统读它的时机就在进程创建之前。咱们看主线 demo 真在用的 `src/gui/app/gui.manifest`：

```xml
<application xmlns="urn:schemas-microsoft-com:asm.v3">
  <windowsSettings>
    <dpiAware xmlns="http://schemas.microsoft.com/SMI/2005/WindowsSettings">true/pm</dpiAware>
    <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2</dpiAwareness>
  </windowsSettings>
</application>
```

这里同时写了两个字段，因为新旧系统读的字段不同。`dpiAware` 是 2005 年命名空间里的老写法，`true/pm` 表示的是按显示器感知。`dpiAwareness` 是 2016 年命名空间里的新写法，认识这个值的只有 Windows 10 1703 以后的系统。新的系统会挑新的字段读，老系统不认识新字段就退回去读老的。咱们把两个字段都写上，程序在新老系统上就都能拿到正确的档位，照着主线 demo 的写法来就好。

文件怎么进 exe？咱们在主线第一篇[裸窗口 demo](../gui/01_naked_win32.md)里已经做过一遍，做法是把它列进 CMake 的源文件列表：

```cmake
add_executable(gui WIN32
    app/m1a_naked.cpp
    app/gui.manifest)
```

链接器见到 `.manifest` 文件就会把它合进最终的 exe，省了资源脚本，也省了代码里的调用。声明的这一半到此就完成了，系统从此不再拉伸咱们的画面。代价是另一半的活也跟着来了，而 DPI 每变一次，都轮到咱们自己接。

manifest 里其实还有一段依赖 Common Controls v6 的声明，它管的是按钮和输入框的样式新旧，跟 DPI 倒是没什么关系。主线第一篇把它们一并放在了同一份文件里，解决了“糊和丑”。咱们本篇只认 DPI 那两行，样式那段您回[裸窗口 demo](../gui/01_naked_win32.md)里看。

## WM_DPICHANGED：变化到来的那一刻

变化发生在两种时刻：窗口被咱们拖到缩放不同的另一块显示器上，或者用户坐在原地改了当前屏的缩放设置。在这样的两种时刻，系统给窗口发的都是同一条 `WM_DPICHANGED`。demo 里接它的分支写成了这样：

```cpp
case WM_DPICHANGED: {
    const auto* suggested = reinterpret_cast<const RECT*>(lParam);
    SetWindowPos(hwnd, nullptr, suggested->left, suggested->top,
                 suggested->right - suggested->left, suggested->bottom - suggested->top,
                 SWP_NOZORDER | SWP_NOACTIVATE);
    return 0;
}
```

消息的两个参数各带了一样东西。`wParam` 的低 16 位和高 16 位分别是新 DPI 的 X 值和 Y 值，书架示例里取值的写法是 `LOWORD(wParam)` 和 `HIWORD(wParam)` 各接一个。`lParam` 递过来的则是一个 RECT 指针，指向系统替咱们算好的建议矩形：窗口按新旧 DPI 的比例缩放之后，大概应该落在哪儿、又该占多大的地方。从 96 DPI 的屏拖到 240 DPI 的屏，建议矩形就是把原窗口整体放大 2.5 倍的结果，开头咱们看到的“窗口自己大了一圈”，正是它的效果。

为什么咱们得直接用建议矩形，自己拿旧宽高乘个比例不行吗？当然行，但系统给的矩形考虑得更多，窗口缩放之后该贴着鼠标还是留在原地，它都算进去了，具体怎么算的文档没有写死，笔者也不猜。咱们照着建议矩形调一次 `SetWindowPos`，是最省事也最稳的做法。咱们要是随手定一个不合适的新尺寸，系统还会再触发一轮新的 DPI 变化，把咱们绕进出不去的循环。

咱们跟着消息的链路往下走：执行了一次 `SetWindowPos`，窗口的尺寸就变了，系统接着发来的是 `WM_SIZE`，demo 里的 `layout_controls` 重跑一遍，控件按新的客户区宽度重新排。manifest 的声明换来的是不拉伸，后面跟着来的消息换来的是重排，整条链路是一环不缺的。主线验证记录（`todo/route.md`）里存着一组实测过的数字：在一次缩放的前后，EDIT（输入框）和 STATIC（标签）的宽度从 259 涨到了 1371，因为输入框和标签的宽度本来就取自客户区宽度减边距，窗口大了它们自然就宽了。不过那组数出自哪几轮测试、各用哪把尺子量的，记录里留的并不全，您别拿 1371 除以 259 去对缩放倍数，那样是对不上的。

书架示例在同一个消息里走的是另一条路：它不去等 `WM_SIZE` 的到来，接了消息当场就调 `RelayoutControls` 按新 DPI 重排控件，再补上的一句 `InvalidateRect` 把整块客户区标成待重画。demo 靠系统跟来的 `WM_SIZE` 间接重排，示例选的是自己动手直接重排，两条路其实都走得通，咱们看到的差别只在重排的触发点放在谁手里。

不过按钮没跟上，实测记录里它的宽度是纹丝不动的。demo 里它的宽度写的是常数 120，`SetWindowPos` 的单位是物理像素，而客户区怎么变它都是 120 个点。在 250% 的屏上，120 个物理像素折成的逻辑尺寸只有 48，它就显得比周围的控件小了一号。这就是开头那半个疑问的答案：窗口跟得上的原因在于建议矩形，跟客户区宽度走的控件也跟着沾了光，写死物理尺寸的常数谁也救不了它。咱们想让按钮跟上，要做的就是把每个布局常数按 DPI 换算，而这正是下一节的活。

要换算的常数不止按钮一个。咱们翻回 demo 的 `layout_controls` 看一眼，看到的是边距 20、间距 8、输入框高 28、按钮高 36，加上按钮宽 120 和标签高 32 的一排，连自画那行字的高度 32 也在内，这排常数全都是 96 DPI 世界里的值，在 250% 的屏上全都要缩水成四成。摆在咱们面前的选择只有要么换算、要么接受控件在高分屏上偏小，咱们没有第三条路。

## 把另一半补齐：按 DPI 换算尺寸

换算用的老伙计是 `MulDiv`，它算的是 `a × b ÷ c`，中间的结果用更宽的整数兜着，不会像咱们手写乘了再除的 int 算式那样在中途溢出。书架的示例程序 `src/tutorial/native_win32/11_dpi_aware/main.cpp` 里就是这么干的，取 DPI 和换算各包了一层小函数：

```cpp
UINT dpi = GetWindowDpi(hwnd);
int btnWidth = ScaleForDpi(120, dpi);
```

`GetWindowDpi` 是示例自己包的一层马甲，里面包的是 `GetDpiForWindow`，它问的是“这个窗口此刻落在的是哪块屏，那块屏的 DPI 是多少”，它从 Windows 10 1607 起就可用了。示例代码为了兼容老 SDK 的环境，用 `GetProcAddress` 从 user32.dll 里动态取它的地址，而取不到就退回老办法，借一个 DC（设备上下文、Windows 绘图接口的句柄）问 `GetDeviceCaps(hdc, LOGPIXELSX)`。两条路咱们拿到的都是同一个意义上的值，也就是窗口所在的那块屏的 DPI。

换算那层的原文是两个函数，方向是一正一反的，咱们一并看了：

```cpp
int ScaleForDpi(int value, UINT dpi)
{
    return MulDiv(value, dpi, 96);
}

int UnscaleForDpi(int value, UINT dpi)
{
    return MulDiv(value, 96, dpi);
}
```

正向的把逻辑尺寸放大成物理像素，是给 `SetWindowPos` 用的。反向的把物理像素折回逻辑单位，什么时候用得着它？您从系统手里拿到一个物理坐标，想在自己的逻辑布局里对齐它的时候，比如把鼠标点击的位置对到某个控件上。两个方向共用的都是 96 这个基准，绕一圈回来之后数就不会漂了。

字号咱们也得跟着换。示例里换字体那一步是这样写的：

```cpp
HFONT hFont = CreateFont(
    -ScaleForDpi(14, newDpi), 0, 0, 0, FW_NORMAL, FALSE, FALSE, FALSE,
    DEFAULT_CHARSET, OUT_DEFAULT_PRECIS, CLIP_DEFAULT_PRECIS,
    CLEARTYPE_QUALITY, DEFAULT_PITCH | FF_DONTCARE, L"Microsoft YaHei UI");
```

高度参数填的是 `-ScaleForDpi(14, newDpi)`，填进去的 14 是逻辑字号，乘的是换算系数，取的是负号。负号是 `CreateFont` 的约定：正数表示的是按单元格高算，负数表示按字符本身的字高算，咱们要的是后者。字体、控件尺寸、边距间距的全套常数都过一遍 `ScaleForDpi`，走到了这一步的程序才算把“不小”这件事做完整了。主线 demo 倒是没这么做，它把演示的机会留给了咱们这一篇。

到这儿咱们手里有两份能对照的代码了，一份是主线的 demo，一份是书架的示例，咱们把它们摆在一起看，各自做到哪一步是一目了然的：

| | 主线 demo | 书架示例 |
|:---|:---|:---|
| 声明方式 | manifest 写两条字段 | 启动时调 SetProcessDpiAwarenessContext 传 -4 |
| WM_DPICHANGED 里做什么 | 按建议矩形 SetWindowPos，重排交给跟来的 WM_SIZE | SetWindowPos 之外，当场重排控件再 InvalidateRect |
| 布局常数 | 物理像素写死，不随 DPI 换算 | 全套过 ScaleForDpi |
| 字体 | DEFAULT_GUI_FONT 一份用到底 | DPI 变了按新值重建字体 |
| 教学定位 | 把没换算的后果留在屏幕上给您看 | 把换算这条路完整走通 |

demo 的糙是咱们故意留的：按钮缩水这个现象，正是本篇开头拿来做引子的那半个疑问的实物。

咱们再记一条工程习惯：96 基准的常数集中放，咱们把乘法留到用的时候再做，别在初始化的阶段就乘好一份物理值存起来。DPI 是会变的，拖一次窗口它就换了一个值，乘好存下来的物理值在 `WM_DPICHANGED` 之后就成了旧值，下一次重排拿的还是旧尺寸，窗口也就越算越歪了。书架的专题把“缓存的 DPI 值”列为排查清单里的一项，道理就在咱们刚说的习惯里。

顺着咱们刚说的习惯，把 demo 的 `layout_controls` 改成换算版，您看它改动有多小。下面是一份示意的改法，咱们没有把它合进仓库，demo 冻结在仓库里当对照的标本：

```cpp
static void layout_controls(HWND parent) {
    if (g_edit_hwnd == nullptr) {
        return;   // 原来的守卫，第一波 WM_SIZE 来时子窗口还没出生
    }

    UINT dpi = GetDpiForWindow(parent);   // 唯一新增的一问

    RECT client{};
    GetClientRect(parent, &client);

    const int kMargin       = MulDiv(20, dpi, 96);
    const int kGap          = MulDiv(8, dpi, 96);
    const int kEditHeight   = MulDiv(28, dpi, 96);
    const int kButtonHeight = MulDiv(36, dpi, 96);
    const int kButtonWidth  = MulDiv(120, dpi, 96);
    const int kLabelHeight  = MulDiv(32, dpi, 96);
    const int kDrawnHeight  = MulDiv(32, dpi, 96);

    // 往下的加法和 SetWindowPos 一行都不用动
}
```

咱们对照着原版看：守卫和 `GetClientRect` 的部分都不用动，整段的算术一行不换，改的只有常数定义那一排，每个数从原来的直接写，变成了过一遍 `MulDiv`，外加的只有开头问一句当前 DPI。250% 的屏上 `kButtonWidth` 算出来是 300，按钮就跟上了。改动的边界这么小，是因为 demo 的布局本来就以 96 基准的常数为中心，换算只要楔进常数出口的位置就够了。字体那头是另一半的活：demo 全程用的都是一份 `DEFAULT_GUI_FONT`，咱们要跟书架示例对齐，就得在 DPI 变化时照上面 `CreateFont` 的写法重建一份。

声明的写法还有一个变体值得咱们认一认。manifest 的作用是在进程创建前定下档位，而代码里也可以在启动早期调 `SetProcessDpiAwarenessContext` 达到同样的效果。示例里传的是字面量 `(HANDLE)-4`，头文件里 `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` 这个常量的值就是它：这 -1 到 -5 的几个负数句柄各对应一档感知，-4 对应的正是本篇的主角档。而在 manifest 声明过之后，这个调用是会失败的，所以两条路咱们挑一条走就好。示例代码走的是运行时调用，是因为它的源码还要照顾拿不到新 SDK 的编译环境，咱们自己的项目里 manifest 通常更省心。

## 多显示器：每块屏各自一套 DPI

多显示器是 DPI 问题的放大器。Windows 允许咱们给每块屏单独设缩放，您完全可以左边摆一块 100% 的 1080p，右边摆一块 250% 的 4K。而在 unaware 程序那边，系统把每块屏的画面各自折算进它眼里那个 96 DPI 的世界，两块屏的折算系数并不同，坐标在屏与屏的接缝处对不齐，是老用户很熟悉的现象。而轮到 PerMonitorV2 程序，`GetDpiForWindow` 报的永远是窗口所在那块屏的值，拖动跨屏的瞬间 `WM_DPICHANGED` 到达，窗口也就按建议矩形缩放了，一切也就回到了上一节的链路。

DPI 变化的来路不只有拖窗口一条。用户在设置里改缩放、远程桌面连进一台缩放不同的机器，都会让窗口所在屏的 DPI 换值。书架的[DPI 专题](../native_win32/3_ProgrammingGUI_WhatAboutDPI.md)把这些场景列成了一份测试清单，您要做正经适配，咱们照着清单过一遍更靠谱，肉眼的碰运气是靠不住的。

## 288 是哪来的：DPI 虚拟化的一次实测

咱们讲到这里，“系统替 unaware 程序拉伸画面”这件事已经说清了，其实还有更隐蔽的一层：系统连 API 的返回值都替 unaware 进程换算好了，这套做法的名字叫 DPI 虚拟化。而 unaware 进程量世界，量到的是折算进 96 DPI 世界的值，而不是物理值。同一个 `GetWindowRect` 的调用，感知进程调它拿到的是物理像素，而 unaware 进程调它，拿到的却是虚拟化坐标，两边用的接口一样，看到的世界却是两套。主线验证记录（`todo/route.md` 的验证手法备忘）里有一次现成的实测，咱们直接借来用。

那次测量用的是 PowerShell，从 user32 调 `GetWindowRect` 去量一个 720 物理像素宽的窗口，机器的缩放是 2.5 倍。量回来的宽度是 288。咱们做个除法，720 ÷ 2.5 一除就得到了 288，正好是物理宽度除以缩放倍数的结果。PowerShell 的宿主进程自己不声明 DPI 感知，系统就把给它的坐标统统换算进 96 DPI 的世界，它量到的每一样东西都缩水了 2.5 倍。窗口其实还是那个窗口，量尺的人站的世界不一样。

这件事的教训不在 PowerShell 的身上，落在了测量本身。您以后用任何工具量窗口、量坐标，要问的都是这个工具自己属于哪一档感知。您要的是物理值，就得让测量进程声明了感知再去量。做不到的话咱们就只比相对变化，在同一个环境里用同一把尺子量的前后两次，比值是不受虚拟化影响的。反过来它也提醒咱们：unaware 进程拿到的屏幕尺寸、鼠标坐标全被系统换过，两档进程混在同一个系统里各看各的世界，写自动化脚本的人要是不知道这一点，很容易对着一个对不上的数字查上半天。

要是手头只有一个改不了声明的工具，咱们又非要物理值，系统也留了口子。`SetThreadDpiAwarenessContext`（Windows 10 1607 起）能临时切换当前线程的感知档位，书架专题里给的用法是切过去、量完、切回来：

```cpp
DPI_AWARENESS_CONTEXT old = SetThreadDpiAwarenessContext(
    DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2);
// 这个区间里量到的就是物理值
SetThreadDpiAwarenessContext(old);
```

量完就恢复的这一步是不能省的，同一个线程后面对话框、控件的行为都跟着档位走，咱们要是忘了切回去，量尺寸的临时动作就变成全程的行为改动。而它还能在创建窗口以前切档，让一个进程里新旧窗口各按各的档位生，书架专题给它起的名字叫混合模式，同时提醒了它只适合过渡期，笔者自己没有实际用过这样的做法，您真要用之前去那篇专题里把注意事项读完。

## DIP 在后面哪里等咱们

本篇认了三套名字，您可能觉得 DIP 离 Win32 最远，其实它就在前面不远等着。等到咱们讲到 Direct2D 的那一篇，渲染目标的坐标全是浮点 DIP，工厂和渲染目标还自带各自的 DPI 设置。画一个 200.0f 宽的矩形，在 96 DPI 的目标上占 200 个物理像素，在 240 DPI 的目标上占 500 个。换算是由 D2D 在内部完成的。DirectWrite 的字号同样以 DIP 计，18.0f 的字在任何屏上看起来一样大。连创建渲染目标时的属性结构里都有两栏专门的 DPI 字段，传 0 表示的是跟系统默认走，书架 D2D 那几章用的就是同样省心的传法。这些细节咱们到[工厂、设备与渲染目标](06_d2d_targets.md)里对着代码看，本篇您只要把 96 这个基准和那道乘除记牢。

书架窗口篇的[DPI 感知一节](../native_win32/2_ProgrammingGUI_NativeWindows_2.md)还给了个浮点版的换算器，核心的东西就两行，咱们原样借来：

```cpp
float dpi = GetDpiForWindow(hwnd);
scale = dpi / 96.0f;
```

这里其实有一处出入，书架原文是把这两行包在一个 DPIScale 类里的，WM_CREATE 时算好一份 scale 就存着用了，这正是前面工程习惯的告诫不让做的事，咱们只借换算本身，缓存是不借的。咱们拿到这个 `scale` 之后，像素和 DIP 之间的换算就是一次乘除，物理坐标除以它折成了 DIP，而 DIP 乘上它就落成了像素。整数的世界用 `MulDiv` 保精度，浮点的世界直接做除法，两副工具干的是同一件事，选哪副看您手里坐标的类型。

还有一件值得咱们现在记下的事。GDI（Windows 的经典绘图接口）这一路（demo 用的就是 GDI）没有 DIP，它的坐标就是整数像素，感知进程拿到的就是物理像素，所以 demo 的布局常数才要咱们自己乘 DPI。咱们面对的是两套体系：一套把换算收进了 API 内部，一套把换算留给了程序，这个差别在咱们后面对照 GDI 与 D2D 时还会反复出现。

## 您可以自己动手的三处

有三处观察您现在就能做，做完本篇的机制就落在您自己的机器上了。

头一处也是最简单的，看看您自己站在哪个世界里。打开设置里的显示那一页，您找到缩放百分比，拿它乘 96 除 100 算出来的数，就是您当前屏幕报给感知程序的 DPI。您的屏幕如果是 150%，得出来的就是 144，咱们正文里所有的乘除拿到您自己的机器上都能代入。

第二处咱们把 288 那次实测在自己机器上走一遍。照主线记录的思路，咱们用 PowerShell 从 user32 借 `GetWindowRect`，去量一个已知物理宽度的窗口，再拿量到的数跟真实宽度做除法，商就是您机器的缩放倍数。整段脚本咱们不在此贴出，借用的办法记录在 `todo/route.md` 里，您写的时候记得 `GetWindowRect` 得配一个 `RECT` 结构接结果，`Add-Type` 那一步咱们跑一次就够了。量出来的宽度要是跟物理值对不上，咱们可别急着怀疑自己，回头想想本篇讲的内容：PowerShell 是 unaware 的尺子，它量到的是 96 DPI 世界里的数。

第三处咱们亲眼看一次 `WM_DPICHANGED` 干活。您手上有多块缩放不同的显示器，就把 `gui_naked` 的窗口在两块屏之间拖，咱们会看到窗口在跨屏的瞬间自己变大或变小。您只有一块屏也行，咱们在设置里把缩放从 100% 改到 125%，感知程序的窗口当场就会走一遍咱们讲的链路。顺路再开一个不带声明的老程序做同样的事，拉伸的糊和重排的利落摆在一起，比文字的描述直观得多。老程序要是小得没法用了，右键属性里的兼容性设置能给单个程序指定高 DPI 行为，那个入口就是系统替个别程序补声明的地方。

咱们把三处做完，缩放倍数对您就不再是书上的数，是您自己量出来的。
