# 落回具象 · 同一件事，两种写法

笔者原以为这一步要拿框架把同一个 demo 重写一遍。走到这儿才发现没得写了，五层里每一层都替它把 demo 迁了过去，少迁了哪一层，那一层就验不出自己改掉了什么。仓库里跑着的两个版本摆在一处，剩下的就是一条一条地对着看。

## 五条别扭和它们的去处

笔者对着两版核了一遍，裸版留下的五条别扭在框架版里各有各的去处。

| # | 裸版的样子 | 框架版的构造 | 解决它的那一层 |
|:--:|:---|:---|:---|
| 1 | 五个文件作用域的全局变量 | `Window` 持有 `hwnd_`；demo 是它的子类，控件是成员 | 窗口对象 |
| 2 | ID 常量 + `CreateWindowExW` + `switch` 分支，三处 | 一个节点：`add_native(...)` 一行 | 控件树 |
| 3 | 窗口过程里判断"哪个是按钮、点了干什么" | 控件只表态**收不收 / 处理了没有**，路由归 `EventRouter` | 事件路由 |
| 4 | 七个常量 + 五行算术 + 四次 `set_bounds` | 每个节点声明 `preferred_size`，`StackLayout` 算位置 | 布局 |
| 5 | 改了字符串，却没人失效那块矩形 | `Property<T>` 变化 → `invalidate()` 冒泡到根 → `InvalidateRect` | 属性与重画 |

## 三处对不上的地方

笔者打开裸版，开头躺着的五个 `static` 全在文件作用域里，三个是控件的 `HWND`，另外两个管着那行自绘文字的字符串和矩形。其中 `g_drawn_rect` 的来历最没道理，它的活儿只有两件，写它的人在 `layout_controls`，读它的人在 `WM_PAINT`。

```cpp
// 裸版
static HWND g_edit_hwnd   = nullptr;
static wchar_t g_drawn_text[256] = L"（……）";
```
```cpp
// 框架版
class DemoWindow : public Window {
    NativeWidget* edit_   = nullptr;
    DrawnLine*    drawn_  = nullptr;
};
```

五个全局变量换成了类里的成员，位置也跟着从文件作用域挪进了类里，您想拿到 `edit_` 的前提是手上有一个窗口对象。

笔者在裸版上添一个控件，要动的地方有三个：`kIdLabel` 这样的常量写在文件开头，`CreateWindowExW` 的调用挤在中段，响应分支埋在另一个 `switch` 的深处，三处隔了好几百行。改了这头忘了那头，编译器不会替您拦。

```cpp
// 裸版：ID 常量在文件开头，创建在中段，响应分支在另一个 switch 里
constexpr int kIdLabel = 1003;
...
g_label_hwnd = CreateWindowExW(..., reinterpret_cast<HMENU>(static_cast<INT_PTR>(kIdLabel)), ...);
...
if (LOWORD(wParam) == kIdLabel && ...) { ... }
```
```cpp
// 框架版：一行创建，响应下一行就装上
label_ = &add_native(0, L"STATIC", L"…", WS_CHILD | WS_VISIBLE);
label_->set_handler([this](Event& e) { /* 就在这儿 */ });
```

框架版里添控件的地方只有一处，`add_native` 交回来的就是节点，您要挂的响应就在下一行，尺寸的事归 `preferred_size`。

您点一下按钮，裸版里标签立刻换成了输入框里的字，因为 `SetWindowTextW` 已经把控件标脏了。底下那行自绘的字不动，它一直停在创建时写下的那句“（这行字是本程序自己画的，还没被更新过）”。少了 `InvalidateRect` 那一句，系统手上那块矩形从头到尾都是干净的。

```cpp
// 裸版：靠人记得
lstrcpynW(g_drawn_text, text, 256);
// 然后……忘了 InvalidateRect，界面就停在旧状态
```
```cpp
// 框架版：写入点就是排重画的唯一出口
DrawnLine() { text.on_changed([this] { invalidate(); }); }
...
drawn_->text.set(kText);
```

框架版的出口就在写入点上，`DrawnLine` 的构造函数挂了一句 `on_changed`，改 `text` 的人同时也排好了重画。同样的点击落到框架版里，两行字一起变了。笔者点了几次按钮，回回都是两行字一起变的。

## 第四个控件加进去，改了三行

第 1 篇留的作业是数一数添一个控件到底改几处，真实数字现在有了。笔者真在框架版里加了一个提示用的 `STATIC`，动的就是三行：

```cpp
NativeWidget* hint_ = nullptr;                                              // ① 成员
hint_ = &add_native(0, L"STATIC", L"（我是第四个控件……）", WS_CHILD | WS_VISIBLE);  // ② 创建
hint_->set_preferred_size(Size{.width = 0, .height = 24});                   // ③ 尺寸
```

| | 数字 |
|:---|:---|
| 逻辑改动 | **3 行** |
| 物理行净增 | **4 行**（254 → 258，clang-format 折了一行） |
| 落在几处 | **1 处** —— 全在 `create_controls` 里 |
| 要不要碰事件路由 | 不用（这个控件不需要响应） |
| 要不要重算坐标 | 不用 |

净增的 4 行里没有一句新代码，`hint_->set_preferred_size(...)` 被 clang-format 折成了两行。编译过去了，控件数变成了 4，点击的链路照常。窗口的尺寸是 720 × 480，从上到下的四行原生控件是 28、36、32、24 像素，四周留着 20 像素的白边，兄弟之间留了 8 像素。新提示的高度是 24 像素、位置就在标签下面，底下的自绘行跟着往下让了 32 像素，您一行算术都没写。

> **第 3 篇那句只改一行的说法，说错了。真实的改动是 3 行。** 那句口号是笔者当时随手写下的，这里把它改掉了。
>
> 但真正的变化不在行数上。按裸版的写法，同样的改动要落在**五个地方**：ID 常量、全局 HWND、`CreateWindowExW` 的实参、`WM_SETFONT`、**布局算术**，每一处都得咱们自己动一遍。最麻烦的是布局算术，控件插在中间的时候，下面每一项的 `Top` 都得跟着重算，五处合起来您一般要动十一行。五处之间没有任何编译期上的联系，您漏掉一处，拿到的就是点了没反应的界面，或者位置怪怪的界面。
>
> `WM_SETFONT` 那一句漏了，新控件的中文就退回系统老字体，字号小了一号。框架版这三行是**集中**的。该改的地方只剩一处，这件事才是这一整套抽象真正买到的东西。

## 一共多少行

| | 总行 | 纯代码 |
|:---|--:|--:|
| 裸版（`app/m1a_naked.cpp`，冻结保留） | 277 | 140 |
| 框架版 demo（`app/demo.cpp`） | 254 | — |
| 框架层（`framework/` + `platform/`） | — | — |
| **全部（含裸版与 manifest）** | **1439** | **662** |

笔者把骨架数了一遍，从 277 行的裸版涨到 1439 行，涨出来的 777 行里，注释和空行占了大头，一大半还是仓库对头文件强制要求的 doxygen。真正动手写的代码只有 662 行。

行数涨了五倍。笔者数完这些行，发现抽象的好处并不在行数上：**抽象不压缩代码。** 它做的事情是：让每一件事有唯一该在的地方。

- 窗口的生命周期，归 `Window`
- 控件的身份与树，归 `Widget`
- 事件该交给谁，归 `EventRouter`
- 位置，归 `Layout`
- 状态变化之后谁负责刷新，归 `Property` 和 `invalidate`

五层还没叠上去的时候，这些东西分别散在全局变量、`CreateWindowExW` 的实参、一个越来越长的 `switch`、一段手算算术，还有得您自己想起来的 `InvalidateRect`。`InvalidateRect` 少写了一句，界面就停在了旧画面上，不会有谁提醒您。
